# 阶段 1 · 子阶段 7C：全局搜索命令面板（Ctrl+K）

## 1. 业务目标

平台里的资源散落在五个页面：Agent、知识库、RAG 评估数据集、模型仓库、数据集市场。
用户想找「上次建的那个评估集」时，必须先想起它属于哪一类、再进对应页面搜索。
本子阶段提供**一个入口搜全部**：

> 按 `Ctrl/Cmd + K`（或点击侧边栏「搜索」）打开命令面板，输入关键词，
> 一次请求返回五类资源的匹配项；回车直接跳到目标页面，并自动带上关键词/选中项。

它解决的是「导航成本」，不是「全文检索」：只匹配名称、说明等短字段，不碰文档正文。
这与项目现有定位一致——知识库正文检索有独立的 `kb-search` 链路，两者不混用。

设计约束：

| 约束 | 做法 |
| --- | --- |
| 权限必须由后端校验 | 五类结果都复用各领域 Holder 的可见性逻辑，前端不做任何过滤 |
| 一次请求完成 | 后端聚合五类，避免前端并发五个接口、再处理部分失败 |
| 单类失败不能拖垮整体 | 每个数据源独立 `try/catch`，失败标记 `degraded` 并跳过 |
| 不能把整张表塞进响应 | 每类最多 6 条；扫描窗口 200 / 500 行封顶 |
| 不引入新中间件 | 复用现有 Mapper 与 PostgreSQL，不加 Elasticsearch |

## 2. 交互流程

```text
用户按 Ctrl+K
      │
      ▼
GlobalSearch 组件打开遮罩（Teleport 到 body）
      │
      ├── 输入为空 → 展示提示文案，不发请求
      │
      └── 输入关键词 → 250ms 防抖 → POST /ai/api/globalSearch/search
                              │
                              ▼
                    GlobalSearchHolder（一次聚合 5 类）
                      ├── AgentConfigHolder.search(uid, ...)      仅本人
                      ├── KnowledgeBaseBeanHolder.searchVisible() 复用可见性
                      ├── RagEvalHolder.searchDatasets(uid, ...)  仅本人
                      ├── ModelsBeanHolder.search(...)            平台公开目录
                      └── DatasetsBeanHolder.search(...)          平台公开目录
                              │
                              ▼
                    返回 { keyword, total, degraded, groups[] }
                              │
                              ▼
      ┌───────────────────────┴───────────────────────┐
      │ ↑↓ 移动 / Enter 打开 / Esc 关闭 / 点击外部关闭 │
      └───────────────────────┬───────────────────────┘
                              ▼
                router.push(服务端拼好的 route)
                              ▼
        目标页读取 ?keyword= 或 ?datasetKey= / ?agentKey=
        （同路由 query 变化也要生效，见 §5.4）
```

## 3. 后端原理

### 3.1 聚合层只做编排，不重写权限

`GlobalSearchHolder` 不直接查表，而是调用五个领域 Holder 已有的查询方法：

| 分类 | 调用 | 权限口径 |
| --- | --- | --- |
| `agent` | `AgentConfigHolder.search(uid, keyword, 6)` | `lastuser = uid`，只看自己的 Agent |
| `knowledge-base` | `KnowledgeBaseBeanHolder.searchVisible(uid, keyword, 6)` | 与知识库列表一致：本人 / `public` / `partial_invisible` 黑名单；超管可见全部 |
| `rag-dataset` | `RagEvalHolder.searchDatasets(uid, keyword, 6)` | `lastuser = uid` |
| `model` | `ModelsBeanHolder.search(keyword, 6)` | 平台级公开目录 |
| `dataset` | `DatasetsBeanHolder.search(keyword, 6)` | 平台级公开目录 |

这样做的原因：可见性规则已经存在且被大量测试覆盖，如果在搜索里再写一遍，
一旦规则调整（比如知识库新增一种权限），搜索就会成为漏权限的第二个入口。

### 3.2 降级：一个分类失败不影响其他分类

```java
boolean degraded = false;
List<GlobalSearchItem> agentItems = new ArrayList<>();
try {
    for (AgentBean row : agentConfigHolder.search(uid, keyword, PER_CATEGORY_LIMIT)) {
        agentItems.add(agentItem(row));
    }
} catch (Exception e) {
    degraded = true;
    log.warn("[GlobalSearch] Agent 检索失败, uid={}: {}", uid, e.getMessage());
}
// 其余四类同样处理
```

- 失败只记 `warn`，不把异常抛给前端；
- 响应里 `degraded=true`，前端在结果下方提示「部分数据源暂时不可用」；
- 某些分类为空时不会加入 `groups`，前端只渲染有结果的分类。

### 3.3 输入与输出约束

| 项 | 规则 | 原因 |
| --- | --- | --- |
| 登录 | `uid` 为空直接拒绝 | 搜索涉及个人资源，不能匿名 |
| 请求体 | `null` → 「缺少搜索条件」 | 防止绕过关键词校验 |
| 关键词长度 | 最多 50 字符 | 与前端 `maxlength` 一致，挡住超长 LIKE |
| 空关键词 | 返回空结果 + 「请输入关键词」 | 不用空串扫全表 |
| 单类条数 | 6 | 命令面板高度有限，结果太多反而难选 |
| 扫描窗口 | 模型/数据集/知识库 500 行，Agent 200 行 | 无全文索引时的成本上限 |
| 副标题 | 截断 120 字符 | 避免超长描述撑爆单行 |
| 路由 | 服务端用 `URLEncoder` 拼接 | 中文关键词直接塞 query 会断链 |

## 4. API 与请求形态

```http
POST /ai/api/globalSearch/search
Content-Type: application/json
x-access-token: <登录态>
account: <账号>

{"data":{"keyword":"数据"}}
```

响应：

```json
{
  "resp_code": 0,
  "resp_msg": "搜索成功",
  "datas": {
    "keyword": "数据",
    "total": 2,
    "degraded": false,
    "groups": [
      {
        "category": "dataset",
        "label": "数据集",
        "items": [
          {
            "category": "dataset",
            "title": "……",
            "subtitle": "……",
            "route": "/datasets?keyword=%E4%B8%AD%E6%96%87..."
          }
        ]
      }
    ]
  }
}
```

> **框架约定**：HNSP 按方法形参名映射请求体，DTO 必须包在 `data` 字段里。
> 裸传 `{"keyword":"..."}` 会被解析成 `null`，接口返回「缺少搜索条件」。
> 这一点在 7C 联调时踩过一次：Windows Git Bash 下用内联 `-d '{...}'` 引号被吞，
> 表现和「后端不认 `data`」一模一样；改成 `--data-binary @body.json` 后一次通过。
> 排查时先用同框架的 `ragEval/getDataset` 做对照组，能快速区分「代码问题」与「请求没发对」。

## 5. 前端实现

### 5.1 状态机

组件内部只有几个关键状态：

| 状态 | 含义 | 渲染 |
| --- | --- | --- |
| `open` | 面板是否打开 | 遮罩 + 面板 |
| `keyword` | 输入内容 | 受控输入框 |
| `loading` | 请求进行中 | 输入框右侧 loading |
| `searched` | 是否已完成过一次搜索 | 区分「还没搜」与「搜了但为空」 |
| `error` | 请求失败文案 | 错误态 + 重试按钮 |
| `result` | 聚合结果 | 分组列表 / 空态 / 降级提示 |

`searched` 不能省：没有它就无法区分「初始状态」和「搜索结果为 0」，
会出现一打开面板就显示「没有找到」的错觉。

### 5.2 防抖与竞态

```ts
const DEBOUNCE_MS = 250
let debounceTimer: number | null = null
let requestSeq = 0

async function runSearch() {
  const seq = ++requestSeq
  loading.value = true
  const { data: res } = await globalSearchApi.search(query)
  if (seq !== requestSeq) return   // 迟到的旧响应直接丢弃
  ...
}
```

- 每敲一个字都清掉上一个定时器，250ms 内没有新输入才发请求；
- 请求发出后序号自增，响应回来时序号对不上就丢弃；
- 关闭面板 / 清空关键词 / 组件卸载都会 `requestSeq++`，让在途请求作废。

这解决两个真实问题：快速输入时后发先至的响应覆盖新结果；关掉面板后旧响应又把
`loading` 置回 `false`。

### 5.3 键盘与可访问性

| 按键 | 行为 |
| --- | --- |
| `Ctrl/Cmd + K` | 开 / 关面板（输入框内也生效，`preventDefault` 挡掉浏览器地址栏搜索） |
| `↑` / `↓` | 在全部结果里循环移动，自动滚入可视区 |
| `Enter` | 打开当前高亮项 |
| `Esc` | 关闭并把焦点还给触发按钮 |

ARIA：`role="combobox"` + `aria-activedescendant` 指向当前项，
结果区 `role="listbox"`，每一项 `role="option"` + `aria-selected`。
加载态 `aria-busy`，错误态 `role="alert"`，空态 `role="status"`。

### 5.4 深链：同路由 query 变化不会重挂载

搜索结果的 `route` 形如：

| 分类 | 路由 |
| --- | --- |
| Agent | `/agents?agentKey=<key>` |
| 知识库 | `/knowledge-bases?keyword=<name>` |
| RAG 评估 | `/rag-eval?datasetKey=<key>` |
| 模型 | `/models?keyword=<name>` |
| 数据集 | `/datasets?keyword=<name>` |

坑点：如果用户已经在 `/models`，再搜另一个模型，`router.push` 只改变 query，
Vue Router 不会重建组件，`onMounted` 里的初始化逻辑不会再跑。
四个视图因此都补了 `watch(() => route.query.keyword, applyRouteKeyword)`：

```ts
const route = useRoute()
const applyRouteKeyword = (value: unknown) => {
  if (typeof value !== 'string') return
  const keyword = value.trim()
  if (keyword) searchKeyword.value = keyword
}
applyRouteKeyword(route.query.keyword)
watch(() => route.query.keyword, applyRouteKeyword)
```

Agent 页略有不同：它按 `agentKey` 选中列表项，所以初次用 `agentKey` 预置
`selectedKey`，后续变化时在已加载列表里找到对应项再 `selectAgent`。

### 5.5 侧边栏折叠

`GlobalSearch` 接收 `collapsed` 属性：

- 展开：图标 + 「搜索」+ `Ctrl K` 提示；
- 折叠：只显示图标，`aria-label` 仍说明快捷键与用途。

## 6. 核心代码

### 6.1 聚合入口

`GlobalSearchHolder.search(uid, request)`：

1. 校验登录态；
2. 校验请求体与关键词长度；
3. 空关键词直接返回空结果；
4. 依次查询五类，每类独立捕获异常；
5. 只把非空分类放入 `groups`；
6. 统一 `total = 各类条数之和`。

### 6.2 路由拼接

```java
private String withQuery(String path, String name, String value) {
    return path + "?keyword=" + encode(value);
}

private String encode(String value) {
    try {
        return URLEncoder.encode(value, "UTF-8");
    } catch (UnsupportedEncodingException e) {
        return "";
    }
}
```

Agent 与 RAG 评估用各自的 key 参数（`agentKey` / `datasetKey`），不依赖名称，
避免同名资源跳错。

## 7. 异常处理与降级

| 场景 | 表现 |
| --- | --- |
| 未登录 | HTTP 200 + `resp_code=20102`（框架拦截器），前端跳登录 |
| 请求体为空 | 「缺少搜索条件」 |
| 关键词超长 | 「关键词最多 50 个字符」 |
| 空关键词 | 「请输入关键词」，空结果 |
| 单个数据源异常 | 该分类消失，`degraded=true`，其余分类正常 |
| 网络异常 | 前端错误态 + 「重试」按钮 |
| 响应非 0 | 展示后端 `resp_msg` |
| 迟到响应 | 序号不匹配，直接丢弃 |

## 9. 已知边界

1. **不是全文检索**：只匹配名称/说明等短字段，不搜文档正文；正文检索走 `kb-search`。
2. **扫描窗口有限**：模型/数据集/知识库最多扫描最新 500 行，Agent 200 行。
   超过窗口的旧数据即使匹配也不会出现。当前数据量（模型 11、数据集 8）远低于上限；
   数据量继续增长时应改为数据库 `ILIKE` + 索引，而不是无限放大窗口。
3. **没有分页**：命令面板定位是「快速跳转」，每类 6 条足够；找更多请进对应页面。
4. **大小写**：匹配时统一转小写，对中文无影响；不做拼音/首字母搜索。
5. **降级不可定位**：前端只知道「有数据源失败」，不知道是哪一类；日志里有分类与用户。

## 10. 面试题

### Q1：为什么由后端聚合，而不是前端并发调五个搜索接口？

前端并发会产生五个鉴权入口、五份错误处理，还要处理「3 个成功 2 个失败」的混合态；
后端聚合可以复用各领域 Holder 的权限判断，把「部分失败」统一成一个 `degraded` 标记，
前端只处理一种响应形状。代价是后端一次请求要串行查五类，所以每类都设了扫描上限。

### Q2：如何保证搜索不会越权？

搜索层不自己写权限 SQL，而是调用各领域已有的查询方法：
Agent / RAG 评估按 `lastuser` 过滤，知识库复用 `searchVisible` 的三种可见性判断，
模型与数据集本身就是平台公开目录。权限规则只存在一处，改规则时搜索自动跟随。

### Q3：防抖和请求序号分别解决什么问题？

防抖解决「请求太多」：连续输入只发最后一次。
序号解决「响应乱序」：即使防抖，用户停顿两次仍可能有两个在途请求，
先发的若后到，会把新结果覆盖成旧结果。两者缺一不可。

### Q4：为什么按 `Ctrl+K` 要 `preventDefault`？

Chrome / Edge 的 `Ctrl+K` 默认聚焦地址栏搜索。不阻止默认行为，
面板刚打开焦点就被浏览器抢走，用户输入会进地址栏。

### Q5：同路由 query 变化为什么需要 watch？

`router.push('/models?keyword=A')` → `'/models?keyword=B'` 只更新 query，
Vue Router 复用同一个组件实例，`onMounted` 不会再次执行。
初始化逻辑若只写在 `onMounted`，第二次搜索就不会更新页面状态。

### Q6：`degraded` 与「直接报错」怎么取舍？

命令面板是导航辅助，不是强一致查询。一个分类失败时，其余四类结果仍然有价值；
整体报错会让用户什么都拿不到。因此选择「部分成功 + 明确提示」，
同时日志保留失败分类，便于排查。

### Q7：为什么每类只返回 6 条？

面板是「快速跳转」，不是结果浏览页。每类 6 条足以覆盖大多数目标；
返回过多会让键盘导航变长、响应变大，也弱化了「去对应页面继续找」的引导。

### Q8：扫描窗口为什么定 500 行？

没有全文索引时，`LIKE '%关键词%'` 无法走索引，只能顺序扫描。
500 行是当前数据量下的成本上限；达到上限后应改用 `ILIKE` + `pg_trgm` 索引，
而不是把窗口调到全表。这个边界写进了「已知限制」，避免以后误以为是 bug。

### Q9：搜索路由为什么由服务端返回，而不是前端按分类拼？

路由格式属于页面契约。放在服务端，新增分类时前端不需要认识新路径；
同时中文关键词的 URL 编码只做一次，避免前端拼错 `?keyword=` 与 `&`。

### Q10：怎么测试一个带防抖和竞态的输入框？

测试里用 `vi.useFakeTimers()` 推进 250ms，断言请求只发一次；
竞态用两个可控 Promise，先发后到，断言最终结果仍是最新一次的关键词。
这两类测试在 `GlobalSearch.component.spec.ts` 里各有一项。
