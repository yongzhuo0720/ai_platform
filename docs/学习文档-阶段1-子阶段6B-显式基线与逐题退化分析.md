# 学习文档：显式基线与逐题退化分析（阶段 1 · 子阶段 6B）

## 1. 业务目标与范围

6A 解决了「一次运行为什么得到这个分」；6B 解决「两次运行之间到底哪里变差了」。

本子阶段交付三件事：

1. **运行记录快照用例集版本**：运行开始时把 `caseSetKey` 一起落库，之后编辑数据集不会让历史运行“看起来可比”。
2. **显式基线**：`getRun` 支持 `baselineRunKey`，用户可以手动指定参照运行；不传时自动选择更早的一次成功/部分成功运行，并优先同一用例集。
3. **可比性校验与逐题对比**：后端返回 `baselineWarnings`、`baselineCompatible`、`caseDiffs`、退化/提升计数；前端提供基线选择器和逐题清单，退化项排在前面。

不在本阶段范围内：

- 不做跨数据集对比（题目不同，指标没有可比性）。
- 不做统计显著性检验（样本量通常只有几十到两百题，先保证口径透明）。
- 不自动触发基线运行；基线仍是用户选择或系统按规则挑选的一次历史运行。

## 2. 业务流程图

```text
用户打开某次运行详情
        │
        ├─ 选择「自动」 ──> 后端 findBaseline
        │                     ├─ 只看更早的运行
        │                     ├─ 只看 success / partial
        │                     ├─ 优先 caseSetKey 相同
        │                     └─ 否则回退到最近的一次可比较运行
        │
        └─ 选择某次运行 ──> 后端 resolveExplicitBaseline
                              ├─ 不能是当前运行本身
                              ├─ 必须属于当前用户
                              ├─ 必须属于同一数据集
                              └─ 必须是 success / partial
                                        │
                                        ▼
                              构建可比性告警
                              ├─ 用例集版本未知 / 不同
                              ├─ TopK 不同
                              ├─ 指标口径未知 / 不同
                              ├─ 向量模型不同
                              └─ 检索链路不同
                                        │
                                        ▼
                              用例集版本一致？
                              ├─ 否：不计算逐题差异，只展示告警
                              └─ 是：加载基线逐题结果
                                        │
                                        ▼
                              逐题比较（按 caseIndex 对齐）
                              ├─ Recall 下降
                              ├─ 首位命中变差或消失
                              └─ 关键词命中丢失
                                        │
                                        ▼
                              排序：退化 → 有升有降 → 提升 → 持平 → 不可比
                                        │
                                        ▼
                              返回详情 + 计数 + 告警
```

关键设计：**先判断能不能比，再计算差多少**。如果两次运行的题目都不同，算出来的“退化 3 条”只是数字噪音。

## 3. 前端原理

### 3.1 基线选择器为什么放在详情头部

基线是“当前这次运行”的属性，不是数据集属性。放在运行详情头部，用户看指标卡片时能同时看到“和谁比、能不能比”。

选择器只有两类选项：

- `自动（优先同一用例集）`：默认值，后端按规则挑选。
- 历史运行列表：只列当前数据集下 `success` / `partial` 的运行，排除当前运行本身。

选项文案由 `baselineOptionLabel` 生成：时间 · TopK · 状态 · `题目一致` · 指标口径。`题目一致` 只有在候选运行的 `caseSetKey` 与当前运行相同才出现，用户在选之前就能判断可比性。

### 3.2 手动选择后为什么要重新请求

整体指标已经在当前运行记录里，但逐题对比需要基线的逐题结果。这部分只有后端能可靠拿到（并且要校验归属），所以前端只保存 `baselineRunKey`，点击选择后重新调用 `getRun(runKey, baselineRunKey)`。

没有在前端把两次 `results` 拉到内存里自己算，原因有三点：

1. 权限边界必须在后端：前端无法保证基线运行属于当前用户。
2. 口径定义只能有一份：退化判定如果前端后端各写一套，迟早不一致。
3. 结果量有上限：单次评估最多 200 题，后端一次查询成本可控。

### 3.3 轮询覆盖的竞态保护

运行详情在评估进行中会被轮询静默刷新。如果用户刚好切换了基线，旧请求可能后返回并把新基线覆盖掉。`loadRunDetail` 在发请求前记录 `baselineKey`，响应回来时同时校验：

```ts
if (state.selectedRunKey === runKey && state.baselineRunKey === baselineKey) {
  state.runDetail = res.datas ?? null
}
```

只校验 `runKey` 不够，因为同一个运行的两次请求可能带着不同基线。

### 3.4 结果表怎么读

逐题对比表固定顺序展示：

| 列 | 含义 |
| --- | --- |
| 状态 | 退化 / 有升有降 / 提升 / 持平 / 不可比 |
| 首位命中（基线 → 本次） | `第 N 位`，0 显示为「未命中」 |
| Recall 差值 | 百分比点（pp），不是百分比 |
| 变化说明 | 由后端生成，列出实际变化的信号 |

`Recall` 是 0~1 的比例，差值乘 100 才是百分点。`+50.0 pp` 表示从 0.5 升到 1.0；写成 `+50%` 会让读者误以为相对提升 50%。

### 3.5 告警与不可比提示的区别

- **黄色告警**：展示后端返回的 `baselineWarnings`，例如「用例集不同」「TopK 不同」「历史运行未记录指标口径」。
- **红色/强调文字**：`baselineCompatible === false` 时在逐题对比标题旁提示「并非严格可比」。

两者不重复：告警解释原因，标记给出结论。严格可比需要同时满足：用例集版本已知且相同、TopK 相同、指标口径已知且相同。

## 4. 后端原理

### 4.1 为什么要在运行开始时快照 `caseSetKey`

数据集编辑采用写时复制：每次保存生成新的 `caseSetKey`，旧用例行保留但不再被数据集引用。运行如果只记录 `datasetKey`，就无法回答一个关键问题：这次运行用的到底是哪一版题目。

6B 在 `startRun` 创建运行记录时写入：

```java
run.setCaseSetKey(dataset.getCaseSetKey());
```

旧运行这一列为 `NULL`。后端不会把 `NULL` 当成“相同”，而是明确告警「历史运行未记录用例集版本」。这比默认相信它可比更安全。

### 4.2 自动基线为什么要优先同一用例集

只按 `iid` 倒序找“更早的一次成功运行”，可能选中一个题目已经变过的运行。指标差值会把“题目变简单了”误读成“检索变好了”。

`findBaseline` 改成两段式：

1. 遍历更早的可比较运行，遇到 `caseSetKey` 相同的立即返回；
2. 没有同用例集的，再回退到最近的一次可比较运行，并让告警说明原因。

这样默认行为尽量给出可信对比，同时不阻断用户查看历史。

### 4.3 显式基线为什么要做四道校验

`resolveExplicitBaseline` 依次校验：

| 校验 | 失败提示 | 防的是什么 |
| --- | --- | --- |
| 不等于当前运行 | 对比基线不能是当前运行本身 | 自己和自己比恒为 0，没有信息量 |
| 存在且属于当前用户 | 对比基线不存在或不属于当前用户 | 越权读取别人的运行 |
| 同一数据集 | 对比基线必须与当前运行属于同一数据集 | 跨数据集题目不同，指标不可比 |
| 状态为 success / partial | 对比基线尚未成功完成 | 失败运行的指标是空的或只覆盖一部分 |

注意：允许手动选择比当前运行更晚的运行。用户可能回看旧运行，主动拿新运行当参照；差值方向始终是「本次 − 基线」，方向不会歧义。

### 4.4 可比性告警规则

`buildBaselineWarnings` 输出的是“为什么不能放心比”，不是简单的对错：

- 两次运行任一缺少 `caseSetKey`：题目是否一致未知。
- 两边 `caseSetKey` 都存在且不同：用例集已变更，整体指标和逐题结果都不可直接对比。
- `topK` 不同：Recall / Precision / NDCG 的分母或截断位置不同。
- `metricSpec` 缺失：历史运行没有口径版本；两边都有但不同：算法口径已变。
- `embeddingModel` 两边已知且不同：向量模型升级会直接改变召回。
- `retrievalMode` 两边已知且不同：精排开关变化是合理解释，不一定是回归。

严格可比判定 `isStrictlyComparable` 只在用例集版本已知且相同、TopK 相同、口径已知且相同时返回 `true`。告警只负责解释，不负责阻断；即使不可比，用户仍能看到差值和逐题清单，但会被明确提醒。

### 4.5 逐题退化判定：三条信号取并集

单题是否退化不是只看一个指标：

```text
Recall 下降
或 首位命中从「第 N 位」变成更靠后 / 未命中
或 关键词从命中变成未命中
```

任意一条成立就记为退化。原因是三个指标覆盖不同失败模式：

- Recall 看“期望文档有没有进前 K”；
- 首位命中看“排序有没有变差”；
- 关键词看“答案片段是否还包含关键信息”。

反过来，任意一条变好就记为提升。如果同一题既有退化信号又有提升信号（例如 Recall 升高但首位命中下降），状态记为 `mixed`，并且**退化计数和提升计数都加一**。这样汇总数字不会因为“只算一边”而掩盖问题。

### 4.6 只在同一用例集内按 `caseIndex` 对齐

`caseIndex` 是用例写入时分配的序号，在同一个 `caseSetKey` 内稳定。跨用例集没有稳定对应关系，按序号硬对齐会把不同题目配成一对。

因此 `compareCases` 的第一行就是：

```java
if (!sameKnownCaseSet(current, baseline)) {
    return new ArrayList<RagEvalCaseDiffDto>();
}
```

基线缺少某题结果时，该题状态为 `unknown`，说明写「基线运行缺少该题结果」，不会当作持平。

### 4.7 查询成本

- 当前运行逐题结果：一次查询，最多 `MAX_CASES + 1 = 201` 行。
- 基线逐题结果：仅在用例集确认一致时再查一次。
- 基线运行记录：显式选择时一次 `findRun`；自动选择时复用最近 100 条运行列表。

没有做 N+1，也没有把整个运行历史加载进内存。单数据集历史上限 100 条用于候选基线；逐题对比只处理两次运行。

### 4.8 降级与兼容

- 旧运行没有 `caseSetKey`：告警提示，不计算逐题差异，整体指标仍可查看。
- 旧运行没有 `metricSpec`：告警提示口径未知，`baselineCompatible` 为 `false`。
- 前端未传 `baselineRunKey`：完全保持 6A 的自动基线行为（只是选择规则增加了“优先同用例集”）。
- 后端未返回新增字段：前端全部按可选字段处理，不读取也不报错。

## 5. API 调用链路

### 5.1 请求

```http
POST /ai/api/ragEval/getRun
Content-Type: application/json

{
  "data": {
    "runKey": "当前运行 key",
    "baselineRunKey": "手动基线 key，可为空"
  }
}
```

Controller 把两个字段一起交给 Holder：

```java
return ragEvalHolder.getRun(uid,
        data == null ? null : data.getRunKey(),
        data == null ? null : data.getBaselineRunKey());
```

### 5.2 响应（节选）

```json
{
  "resp_code": 0,
  "datas": {
    "run": { "runKey": "r3", "caseSetKey": "set-1", "metricSpec": "rag-eval-v1" },
    "baseline": { "runKey": "r2", "caseSetKey": "set-1", "metricSpec": "rag-eval-v1" },
    "baselineExplicit": true,
    "baselineCompatible": true,
    "baselineWarnings": [],
    "caseDiffs": [
      {
        "caseIndex": 0,
        "question": "出差住宿每晚上限多少",
        "baselineFirstHitRank": 2,
        "currentFirstHitRank": 0,
        "recallDelta": -0.5,
        "status": "regressed",
        "note": "Recall 1.000 → 0.500；首位命中 第 2 位 → 未命中"
      }
    ],
    "regressedCount": 1,
    "improvedCount": 0
  }
}
```

### 5.3 前端调用

```ts
getRun: (runKey: string, baselineRunKey?: string) =>
  axios.post('/ai/api/ragEval/getRun', {
    data: { runKey, baselineRunKey: baselineRunKey || null },
  }),
```

注意 `baselineRunKey || null`：空字符串必须转成 `null`，否则后端会把它当成“手动指定了空 key”。

## 6. 数据库设计与迁移

### 6.1 新增列

表 `ragevalrunbean`：

| 列 | 类型 | 说明 |
| --- | --- | --- |
| `caseSetKey` | `varchar(64)` | 运行开始时用例集版本快照；旧运行保持 `NULL` |

没有新增表，也没有改动既有列类型。逐题对比使用的是 `ragevalcaseresultbean` 已有字段。

### 6.2 迁移语句（应用启动时自动执行）

`TableSchemaInitializer.ensureRagEvalTables()`：

```sql
ALTER TABLE ragevalrunbean
    ADD COLUMN IF NOT EXISTS "caseSetKey" varchar(64);
```

建表语句同步加入该列，保证新环境与存量环境结构一致。运维脚本 `scripts/sql/rag-eval-schema.sql` 也同步更新，两份必须保持一致。

### 6.3 上线顺序

1. 先发布后端：启动时自动补列，旧运行 `caseSetKey` 为 `NULL`。
2. 再发布前端：旧后端不认识 `baselineRunKey` 时会忽略它，前端仍能工作（只是没有新能力）。
3. 新产生的运行会自动写入 `caseSetKey`；不需要回填历史数据。

### 6.4 回滚方案

- 应用回滚：旧代码不读取 `caseSetKey`，新增列可以保留，不影响读写。
- 数据回滚：不需要删除列；`NULL` 对旧代码没有副作用。
- 如果要物理删除列，先确认没有任何新版本实例仍在运行，再执行 `ALTER TABLE ... DROP COLUMN`。

### 6.5 上线前检查

```sql
-- 列是否存在
SELECT column_name, data_type
FROM information_schema.columns
WHERE table_name = 'ragevalrunbean' AND column_name = 'caseSetKey';

-- 新运行是否开始写入快照
SELECT "runKey", "caseSetKey", "metricSpec", "startedAt"
FROM ragevalrunbean
ORDER BY "iid" DESC
LIMIT 10;
```

## 7. 核心代码与口径

### 7.1 运行快照（RagEvalHolder.startRun）

```java
run.setRunKey(runKey);
run.setDatasetKey(datasetKey);
run.setCaseSetKey(dataset.getCaseSetKey());
run.setDatasetName(dataset.getName());
```

### 7.2 自动基线（RagEvalHolder.findBaseline）

```java
if (sameKnownCaseSet(current, candidate)) {
    return candidate;
}
if (fallback == null) {
    fallback = candidate;
}
```

返回 `fallback` 时不会假装可比，后续 `buildBaselineWarnings` 会说明用例集版本不一致或未知。

### 7.3 显式基线（RagEvalHolder.resolveExplicitBaseline）

```java
if (current.getRunKey().equals(baselineRunKey)) {
    return Result.failed(null, "对比基线不能是当前运行本身");
}
RagEvalRunBean candidate = findRun(uid, baselineRunKey);
if (candidate == null) {
    return Result.failed(null, "对比基线不存在或不属于当前用户");
}
if (!Objects.equals(current.getDatasetKey(), candidate.getDatasetKey())) {
    return Result.failed(null, "对比基线必须与当前运行属于同一数据集");
}
if (!RagEvalStatus.isComparable(candidate.getStatus())) {
    return Result.failed(null, "对比基线尚未成功完成，无法用于对比");
}
```

### 7.4 可比性判定（RagEvalHolder.isStrictlyComparable）

```java
return sameKnownCaseSet(current, baseline)
        && Objects.equals(current.getTopK(), baseline.getTopK())
        && !blank(current.getMetricSpec())
        && current.getMetricSpec().equals(baseline.getMetricSpec());
```

### 7.5 逐题退化判定（RagEvalHolder.toCaseDiff）

```java
boolean recallDown = nz(current.getRecall()) < nz(baseline.getRecall()) - 1e-9;
boolean recallUp = nz(current.getRecall()) > nz(baseline.getRecall()) + 1e-9;
boolean rankDown = baselineRank > 0 && (currentRank == 0 || currentRank > baselineRank);
boolean rankUp = currentRank > 0 && (baselineRank == 0 || currentRank < baselineRank);
boolean keywordDown = ...;
boolean keywordUp = ...;
boolean down = recallDown || rankDown || keywordDown;
boolean up = recallUp || rankUp || keywordUp;
if (down && up) {
    diff.setStatus(RagEvalDiffStatus.MIXED);
} else if (down) {
    diff.setStatus(RagEvalDiffStatus.REGRESSED);
} else if (up) {
    diff.setStatus(RagEvalDiffStatus.IMPROVED);
} else {
    diff.setStatus(RagEvalDiffStatus.UNCHANGED);
}
```

### 7.6 前端基线切换（RagEvalView/index.ts）

```ts
async function selectBaseline(runKey: string) {
  state.baselineRunKey = runKey
  if (!state.selectedRunKey) return
  await loadRunDetail(state.selectedRunKey, false)
}
```

### 7.7 指标口径汇总

| 字段 | 计算方式 |
| --- | --- |
| `recallDelta` | `current.recall - baseline.recall` |
| `formatPp` | `recallDelta * 100`，保留 1 位小数，单位 pp |
| 首位命中 | `firstHitRank`，0 表示前 K 条未命中 |
| `regressedCount` | `regressed` 数量 + `mixed` 数量 |
| `improvedCount` | `improved` 数量 + `mixed` 数量 |
| `baselineCompatible` | 用例集已知且相同 + TopK 相同 + 口径已知且相同 |

## 8. 异常处理

| 场景 | 处理 |
| --- | --- |
| 手动基线不存在 / 不属于当前用户 | 返回失败提示，不加载任何逐题结果 |
| 手动基线是当前运行 | 返回失败提示 |
| 手动基线跨数据集 | 返回失败提示 |
| 手动基线是 failed / queued / running | 返回失败提示 |
| 用例集版本未知或不同 | 不计算逐题差异，返回告警 |
| TopK / 口径 / 模型 / 检索链路不同 | 返回告警，仍允许查看差值 |
| 基线缺少某题结果 | 该题状态 `unknown`，说明原因 |
| 当前或基线该题检索失败 | 该题状态 `unknown`，不参与退化/提升计数 |
| 数据库查询异常 | 统一捕获，日志记录 uid/runKey，返回“查询运行详情失败” |
| 前端请求失败 | 非静默请求提示错误；轮询失败只记调试日志，下一轮重试 |
| 基线被删除 | 清空 `baselineRunKey`，回到自动基线并刷新详情 |

- **没有在真实 PostgreSQL 执行迁移**：本机 5432 未监听，DDL 只通过单元测试和代码审查验证；`ALTER TABLE ... ADD COLUMN IF NOT EXISTS` 的实际执行结果未观测。

- **没有用真实模型跑两次评估**：逐题退化清单的数值来自构造的测试数据，不代表实际检索质量变化。

### 9.3 残余风险

1. 旧运行的 `caseSetKey` 为空，自动基线可能选中题目已经变化的运行；告警会提示，但用户仍可能忽略。
2. 手动基线允许选择比当前运行更晚的运行；如果用户把它理解成“历史基线”，差值方向可能读反。
3. 逐题按 `caseIndex` 对齐依赖同一用例集版本；如果未来支持“修改单题但不换用例集”，对齐会失真，需要在编辑流程里强制换版本。
4. 数据集历史运行只取最近 100 条作为基线候选；更早的运行无法手动选择，但删除运行记录也会删掉逐题结果，暂不构成数据丢失。
5. 逐题差异最多 200 题，单次响应体积可控；如果未来放宽用例上限，需要分页或只返回退化项。

## 10. 面试问答

### Q1：为什么运行记录要存 `caseSetKey`，直接存 `datasetKey` 不够吗？

`datasetKey` 只说明“哪个数据集”，不说明“哪一版题目”。数据集编辑会生成新的用例集版本，历史运行的指标对应旧题目；只存 `datasetKey` 会让两次运行看起来可比，实际题目已经不同。存 `caseSetKey` 是把“可比性”变成可验证的事实。

### Q2：为什么自动基线要优先同一用例集，而不是时间最近？

时间最近只保证“新”，不保证“同题”。如果最近一次运行用的是旧用例集，把它当基线会把题目变化误判成检索变化。优先同用例集能让默认对比尽量有意义；找不到时再回退，并用告警说明原因。

### Q3：为什么显式基线还要校验数据集和状态？

显式选择只代表“用户想比”，不代表“可以比”。跨数据集的题目不同，指标没有可比性；失败运行的指标为空或只覆盖部分题目，差值会失真。校验放在后端而不是前端，是因为权限和一致性都不能依赖客户端。

### Q4：同一题既有指标上升又有指标下降，为什么记为 `mixed` 而不是随便选一个？

三个指标覆盖不同失败模式，不能互相替代。Recall 升高但首位命中下降，说明“召回到了但排序变差”；只记提升会掩盖问题，只记退化会掩盖收益。`mixed` 同时计入退化和提升两个汇总数，汇总不会丢信号。

### Q5：为什么 Recall 差值用 pp 而不是百分比？

Recall 本身是 0~1 的比例。从 0.5 到 1.0，绝对变化是 0.5，也就是 50 个百分点；如果写成“提升 50%”，读者可能理解成相对提升 50%（即 0.75）。pp 的表达没有歧义。

### Q6：逐题对比为什么只在用例集版本一致时做？

跨版本的题目没有稳定对应关系。按 `caseIndex` 硬对齐，会把“第 0 题”配成两个不同的问题，算出来的退化/提升没有意义。后端返回空列表并给出告警，比返回错误的逐题清单更诚实。

### Q7：为什么不在前端把两次运行的结果拉下来自己算？

三个原因：权限（前端不能保证基线属于当前用户）、口径（退化判定必须只有一份实现）、成本（单次最多 200 题，后端一次查询足够）。把判定放在后端，也方便以后加 API 或 CI 复用同一套逻辑。

### Q8：为什么基线缺少某题结果时不当作持平？

缺少结果可能是基线那次这题检索失败，也可能是数据被部分清理。持平意味着“确实没变化”，两者语义不同。标成 `unknown` 并写明原因，避免把“没有数据”伪装成“没有变化”。

### Q9：如果以后要支持“跨数据集对比”，需要改什么？

至少需要：统一用例集（同一批问题）、统一 TopK、统一指标口径，并且明确哪些题可以跨库映射。没有这些前提，跨数据集只能比较“各自内部的变化趋势”，不能直接比较绝对值。当前实现故意不做，是为了不制造看似高级但口径不清的功能。
