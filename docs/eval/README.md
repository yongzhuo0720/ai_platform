# RAG 检索评估方案

> 目的：把「混合检索应该更好」变成**可测量、可复现、可回归**的数字。
> 没有评估集的 RAG 优化都是盲调——改 chunk size、换 embedding、加一路检索，
> 看着都"应该更好"，但没法证明，也没法发现某次改动其实变差了。

---

## 一、目录内容

| 文件 | 用途 |
|---|---|
| `seed-corpus/` | 6 篇虚构的企业制度文档，约 6500 字，可直接上传到知识库作为评估语料 |
| `golden-set.csv` | 55 道题，每题标注标准答案所在文档与必须出现的关键词 |
| `README.md` | 本文件：指标口径、运行方式、基线结果 |

语料是虚构的（公司名、金额、比例都是编的），可以自由提交到仓库。
用真实业务文档做评估时，把 `seed-corpus/` 换成自己的文档即可，**但不要提交到公开仓库**。

---

## 二、指标口径

只实现**不需要 LLM** 的检索侧指标。为什么不用 RAGAS 那套 context precision / faithfulness：

- 那些指标需要 LLM-as-judge，每次评估花钱，且**同一份数据跑两次结果可能不同**——不能作为回归门禁
- 检索侧指标是确定性的，毫秒级，能进 CI，能在每次提交时拦住"改坏了"

生成侧指标（faithfulness / answer relevancy）适合人工月度抽检，不适合放进门禁。

| 指标 | 定义 | 回答什么问题 | RAG 里为什么重要 |
|---|---|---|---|
| **Recall@k** | 相关片段中被前 k 条覆盖的比例 | 该找到的找到了吗 | **最关键**。召回不到，后面模型再强也白搭 |
| **Precision@k** | 前 k 条里相关结果的比例 | 上下文干净吗 | 太低会稀释上下文、浪费窗口 |
| **MRR** | 第一条相关结果排名的倒数均值 | 能不能一次命中 | 用户/模型只看前几条 |
| **NDCG@k** | 考虑位置的折损累积增益 | 排得够靠前吗 | Recall 相同但排序不同，NDCG 会体现差距 |

实现见 `RagEvaluator`，单测见 `RagEvaluatorTest`（16 个用例，每个指标都用**手算可验证**的例子钉住）。

> 指标算错是最危险的一类 bug：它会让"改造后效果提升了"这个结论建立在错误的数字上，
> 而且没人会怀疑——因为报告看起来很专业。

## 三、怎么跑

### 3.1 合成语料实验（确定性，进 CI）

```bash
cd backend/AIProject
mvn -o -Dtest=KbRetrievalEvalTest test
```

这个测试用**合成语料**构造 RAG 里最典型的一类失败——**语义陷阱**：

- 每个用例 8 个分块，目标分块含用户问题里的精确关键词（如型号 `BGE-M3`）
- 另有 3 个干扰分块向量与问题**更接近**（cosine 0.86-0.88 vs 目标 0.80），
  它们讲同一主题、只是型号不同
- 纯向量检索把干扰项排在前面，目标掉到第 4 位；关键词路精确捞到目标，RRF 融合后升到第 1

**实测基线（k=3，6 个用例）**：

| 方案 | Recall@3 | Precision@3 | MRR | NDCG@3 | 完全漏召 |
|---|---|---|---|---|---|
| 纯向量 | 0.00% | 0.00% | 0.250 | 0.000 | 6/6 |
| **混合检索** | **100.00%** | 33.33% | **1.000** | **1.000** | **0/6** |

> Precision@3 是 33.33% 属正常：每题只有 1 个相关片段，top-3 里塞进 1 个相关即 1/3。
> 这个数字不该拿来比较方案优劣——Recall 与 MRR 才是。

**这个实验测什么、不测什么**：测的是**排序与融合逻辑**，关键词路的召回结果（哪些分块含关键词）
作为入参直接给出，不经过 PostgreSQL。FTS 引擎本身的行为由数据库保证。所以测试是确定性、毫秒级、可进 CI。

### 3.2 真实语料评估（一键跑分）

环境准备好后（后端已启动 + 已配置向量模型），用跑分脚本一条命令完成：
灌语料 → 跑 55 题 → 出报告。

```bash
# 先干跑：只校验黄金集与参数，不联网（现在就能用）
node scripts/rag-eval.mjs --dry-run

# 校验指标实现与后端一致（离线，14 项手算用例）
node scripts/rag-eval.mjs --self-check

# 灌语料 + 跑分 + 出 Markdown 报告
node scripts/rag-eval.mjs \
  --account admin --password '你的密码' \
  --seed \
  --out docs/eval/report-2026-10-24.md

# 已有语料，只跑分
node scripts/rag-eval.mjs --account admin --password '你的密码'

# 不想给密码：从浏览器 DevTools 复制 x-access-token
node scripts/rag-eval.mjs --token <token>

# 跑完清理本次上传的文档
node scripts/rag-eval.mjs --account admin --password 'xxx' --seed --cleanup
```

常用参数：`--base-url`（默认 `http://localhost:8507`）、`--kb-name`（默认「评估语料」）、
`--k`（默认 5）。完整说明见 `node scripts/rag-eval.mjs --help`。

**踩过的坑（脚本已处理）**：CSV 若带 UTF-8 BOM，表头首字段会变成 `\uFEFFid`，
脚本读取时会剥掉 BOM。手工编辑 `golden-set.csv` 后如果脚本报"表头不符合预期"，先查 BOM。

**指标实现一致性**：脚本里的 Recall / Precision / MRR / NDCG 与后端 `RagEvaluator`
是两份独立实现。`--self-check` 用**同一批手算用例**校验两边口径一致——
否则会出现"CI 说 92%、报告说 78%"这种最难排查的不一致。

### 3.3 手动评估（不想用脚本时）

1. 把 `seed-corpus/` 的 6 篇文档上传到平台知识库（或换成自己的文档）
2. 确认已配置向量模型（「模型配置」里 `embedModel` 非空）
3. 逐题调用 `POST /ai/api/kbRag/search`，记录返回的 `items[].docName`
4. 判断命中：`items[0..k-1]` 中是否出现 `expected_doc` 对应的文档名
5. 套用 `RagEvaluator` 的公式算 Recall@k / MRR

**建议每次改动检索相关代码后都跑一遍，记录到下面的记录表里。**

### 3.4 真实评估记录表

| 日期 | 改动 | k | Recall@k | MRR | NDCG@k | 关键词命中 | 备注 |
|---|---|---|---|---|---|---|---|
| 2026-10-24 | 混合检索（向量 + PG 全文 + RRF k=60） | 3 | 待测 | 待测 | 待测 | 待测 | 合成语料 100%，真实语料待补 |
| 2026-10-26 | 混合检索（**mock 哈希向量**，本地演示栈） | 5 | 83.64% | 0.7573 | 0.7764 | 54.55% | 链路冒烟通过。向量路是纯噪声，数字基本只反映关键词路；9 题漏召清单见报告 |
| — | 换真向量模型后重跑 | 5 | 待测 | 待测 | 待测 | 待测 | 预期 Recall 应明显高于 mock（语义路开始贡献） |

**这次跑分还抓到一个指标 bug**：文档级评估下 top-k 混着同一文档的多个分块，
Precision/NDCG 把重复命中重复累加，首轮 NDCG 跑出 **1.3974**（数学上不可能 >1）。
已修：同一相关结果只计最靠前一次，Precision/NDCG 去重，Java/JS 两边同步 + 回归用例。
单测当初没抓到，是因为合成用例的 ID 全是唯一的——**真实数据一进来就露馅**。

> 真实语料上的数字会明显低于合成实验——那是正常的。合成实验是**受控对照**，
> 目的是证明"混合检索在语义陷阱场景下有结构性优势"，不是宣称线上召回率 100%。

## 四、黄金集格式

`golden-set.csv` 每列含义：

| 列 | 含义 |
|---|---|
| `id` | 题目编号 |
| `question` | 用户会怎么问（尽量用自然口语，不要照抄文档原句） |
| `expected_doc` | 标准答案所在的文档（评估时用来判断是否召回正确） |
| `expected_keywords` | 命中的分块里必须出现的关键词（用于检查召回的是否为正确段落） |
| `category` | 题型：事实型 / 数值型 / 规则型 / 列举型 / 流程型 / 解释型 |

**设计原则**：

1. **口语化提问**。用"出差回来多久内要报销"而不是"报销时限是多久"——真实用户不会照抄文档。
2. **数值型占大头**（55 题里 28 题涉及具体数字）。数值、型号、版本号是 embedding 的盲区，
   也是混合检索价值最集中的地方。
3. **覆盖 6 类题型**。列举型与流程型考验多片段召回，是 Recall@k 最容易暴露问题的地方。
4. **跨文档干扰**。6 篇文档都含金额（会议室、处罚、报销、采购），能测出检索是否真的在区分语义。

## 五、失败案例怎么用

`RagEvaluator.EvalReport` 会单独收集 `misses`——**完全没召回到相关片段**的问题。
这批问题最该优先看，因为它们通常是三类根因之一：

| 现象 | 根因 | 修法 |
|---|---|---|
| 关键词完全对不上但语义相近 | 分块把关键段落切断了 | 调 chunk size / overlap，或改父子分块 |
| 关键词对得上却没召回 | FTS 索引缺失或分词不匹配 | 检查 `idx_kbchunk_content_fts` 是否建上 |
| 召回对了但排在第 8 位 | RRF 权重或 dense 分数失真 | 调 topK 初筛数量，或引入 cross-encoder 重排 |

## 六、面试怎么讲

不要只说"我加了混合检索"，要说清三件事：

1. **为什么加**：纯向量的结构性盲区是专有名词/版本号——`BGE-M3` 与 `BGE-M2` 在向量空间几乎重合，
   差别只在最后一位数字，而这恰恰是用户最在意的。
2. **怎么验证**：构造受控对照实验，语义陷阱场景下 Recall@3 从 0% → 100%，MRR 从 0.25 → 1.0。
   **诚实说明这是合成语料上的受控实验**，真实语料数字会低得多。
3. **边界在哪**：真实召回率还没测（需要业务文档与标注成本）；重排、pgvector、父子分块是下一步。

> 能被追问"这个数字怎么来的"而答得上，比数字本身好看更重要。
