## 0. 一句话讲清楚这个项目

> 这是一个**面向企业内部的一站式 AI 能力门户**：把「智能对话、知识库问答、应用构建、模型与数据集仓库」整合到同一个平台，并按**角色 / 部门**做细粒度可见性控制。
> AI 的向量化、检索与编排由 **Dify** 承担；本平台只负责**用户体系、权限模型、多模块聚合与前端体验**。

一句话记忆：**"Dify 干脏活（向量/检索/编排），我们干门面与权限（谁能看、谁能管）。"**

## 2. 整体架构：AI 网关 + kbId 弱引用

> **2026-10-22 更新**：AI 调用已改为**后端网关默认**——浏览器只请求 `/ai/api/aiGateway/{chat|knowledgeChat|file|agent}/**`，
> 由 Spring Boot 转发到 Dify 或智能体服务，Key / Token 只存服务端，并在网关侧做限流、每日 Token 配额（仅 Dify）与审计。
> 智能体通道还会按助手可见性取凭据、覆盖浏览器认证头，并固定上游地址以防 SSRF。
> 下面 2.1 / 2.2 保留的是**早期双通道设计**，用于理解架构演进和当初的取舍；
> 现在直连通道只在 `VITE_AI_GATEWAY=0` 时启用，用于排障与兼容。

### 2.1 早期设计：AI 请求不走业务后端

> **（历史方案）AI 请求不走业务后端。**

| 通道 | 前缀 | 路径 | 特征 |
|---|---|---|---|
| **A · 直连** | `/v1/...` `/qwen/...` | 浏览器 → Nginx/Vite → **Dify / Qwen** | 带 `Bearer apiKey`，**延迟低、支持 SSE 流式**，业务后端不感知 |
| **B · 经后端** | `/ai/api/...` | 浏览器 → **Spring Boot** → PostgreSQL | 带 Sa-Token Cookie，有鉴权、能写库、留操作日志 |

```
                         ┌─────────────────────────────────────────────┐
                         │                 浏览器                        │
                         └───────────────┬───────────────┬─────────────┘
                                         │               │
                      通道 B（业务/权限） │               │ 通道 A（AI 直连）
                                         ▼               ▼
                              ┌──────────────────┐   ┌──────────────────────┐
                              │  Spring Boot :8507 │   │   Nginx / Vite 代理   │
                              │  context-path /ai  │   │  /v1 → Dify  /qwen→Qwen│
                              └─────────┬──────────┘   └───────────┬──────────┘
                                        │                         │
                              PostgreSQL + Redis            Dify(检索/编排) + Qwen
                              （只存"谁能看"）              （存文档/向量/对话）
```

### 2.2 当时的取舍，以及后来为什么改

- **早期换来什么**：AI 调用低延迟（不经后端中转）、后端零压力（SSE 长连接不占后端线程）。
- **早期代价**：
  1. 后端**无法对 AI 调用做计数、限流、审计**；
  2. **Dify 的 API Key 会下发到浏览器**。
- **改造后**：密钥收口到服务端；获得按用户限流、每日 Token 配额、审计与用量看板；
  代价是网关多一跳延迟与 SSE 代理复杂度。流式用字节级透传，逐字效果不变。

### 2.3 数据归属：kbId 弱引用（本项目最巧妙的一点）

文档、分块与向量**全部存在 Dify**，平台数据库里**一个字节的文档内容都没有**。平台只存一张"权限表"：

```
Dify                                 本平台 PostgreSQL
├─ dataset    知识库          ←────  knowledgebasebean
├─ document   文档原文         kbId  ├─ kbId            指向 dataset.id
└─ segment    分块+向量       =     ├─ ownerUid        所有者
                            dataset ├─ permissionType  可见性
                            .id     └─ unitsnos/roleiids  部门/角色黑名单
```

**平台只回答一个问题：谁能看。** 这把"重"的 AI 数据留在专业系统，平台只维护轻量的权限关系。

## 3. 前端架构

### 3.1 目录与职责

```
frontend/src/
├─ api/          接口层：axios 走 /ai/api（业务），fetch+SSE 走 /ai/api/aiGateway（网关）
├─ stores/       主题、Dify 配置缓存、接口文档状态（Pinia）
├─ views/        页面；views/Admin/* 是后台管理（用户/角色/部门/模型/配置）
├─ components/   公共组件（TagDropdown、KbChatPanel、DocumentPreviewDialog…）
├─ composables/  组合式函数（useIsAdmin、useTagBinding）
├─ config/       常量（constants.ts：SUPER_ADMIN_RID、isSuperAdmin）
├─ utils/        工具（request.ts SSE、markdown.ts 净化、url.ts 协议白名单）
├─ data/         静态平台数据（navigationSections、apiCards、knowledgeBases）
├─ types/        knowledge.ts（知识库相关类型的"单一来源"）
├─ router/       vue-router（hash 模式）
└─ layouts/      MainLayout / AdminLayout
```

### 3.2 AI 调用在前端怎么落地

- **业务接口**：`api/*.ts` 用 `axios` 请求 `/ai/api/...`，请求拦截器自动带 Sa-Token Cookie。
- **AI 网关（默认）**：`utils/request.ts` 的 `streamingRequest` 用原生 `fetch` 请求 `/ai/api/aiGateway/chat/...`，
  带 `x-access-token`（管理员页面用 `admin_loginToken`），解析 SSE 流；Dify Key 不出现在前端。
- **直连（兼容）**：设置 `VITE_AI_GATEWAY=0` 后恢复 `fetch` 直连 Dify 的 `/v1/...` 并携带 `Bearer apiKey`。
- 开发期由 `vite.config.ts` 的 dev proxy 把 `/ai` 指向 8507，与生产 Nginx 路由一一对应。

### 3.3 本次代码质量治理成果（面试被问"你做过哪些质量治理"可讲）

| 项 | 问题 | 治理动作 | 效果 |
|---|---|---|---|
| 类型重复 | `data/platform.ts` 与 `types/knowledge.ts` 各定义一套 `KnowledgeBase` 等类型，且前者字段不全 | 把 `data/platform.ts` 的重复定义改为从 `types/knowledge.ts` **转发导出**，统一到单一来源 | 消除 6 个 TS2353（对象字面量多写字段报错），总数 40→34 |
| XSS（markdown） | 部分页面用 `marked.parse` 直接解析，绕过了净化渲染器 | 统一改用 `utils/markdown.ts` 的 `renderMarkdown`（自定义 html/link/image 渲染器做转义与 URL 白名单） | 堵住存储型 XSS |
| XSS（外链） | `window.open(url)` 未校验协议 | 新增 `utils/url.ts` 的 `safeOpenUrl` / `isSafeUrl`（仅放行 http/https/mailto/tel，拦截 `javascript:`/`data:`） | 堵住 `javascript:` 伪协议执行 |
| 魔法数 | 权限超管 ID `99999` 散落多处 | 抽成 `config/constants.ts` 的 `SUPER_ADMIN_RID` + `isSuperAdmin()` + `useIsAdmin()` | 消除重复、集中维护 |

| 死代码 | 22 处未使用符号（TS6133） | 删除确认无引用的 import / 常量 / 函数（含孤儿化后连带删除） | 总数 40→26，0 个 TS2304（无回归） |

## 4. 后端架构

### 4.1 HNSP 四件套（本项目强制约定）

> 每个实体固定四件套：**Controller → Holder → Mapper → Bean**

| 件 | 职责 | 类比前端 |
|---|---|---|
| **Bean** | 实体类，对应一张表（MyBatis-Plus `@TableName`） | 类似 `types/knowledge.ts` 的接口 |
| **Mapper** | 继承 `BaseMapper<T>`，CRUD 自动生成 | 类似 `api/*.ts` 的底层请求 |
| **Holder** | **业务逻辑层**（本项目叫 Holder 不叫 Service） | 类似 `composables/*` 的业务封装 |
| **Controller** | 薄层：鉴权 + 参数校验 + 委派 Holder | 类似 `views/*` 里调 composable |

### 4.2 鉴权：Sa-Token

- 前端登录后拿到 Sa-Token 的 Cookie；后端用 `@LoginUserId String uid` 注解（来自 HNSP）**自动注入当前用户 ID**。
- 所有写操作（`create/delete/update`）第一步都是 `CheckUtils.objectCheckNull(uid, "请先登录", …)`——没登录直接拦。
- 操作通过 `@ControllerLog` 自动留痕（审计日志）。

### 4.3 权限模型（面试核心：filterVisible）

知识库三种可见性 `permissionType`：

| 值 | 含义 |
|---|---|
| `public` | 所有人可见 |
| `only_me` | 仅所有者 |
| `partial_invisible` | 部分不可见——落在 `unitsnos`（部门）/ `roleiids`（角色）**黑名单**中的用户不可见 |

**核心代码（`KnowledgeBaseBeanController.filterVisible`）**：给一组候选 `kbIds` + 当前用户上下文，返回"用户实际能看到的 ID 列表"。这就是 2.3 里"谁能看"的真正落点。

**安全设计**：权限配置解析失败时按**不可见**处理（fail-closed），避免"配错了反而全放开"。

### 4.4 一个真实 Controller（看代码风格）

```java
@RestController
@RequestMapping("/api/knowledgeBaseBean")   // 前端实际走 /ai/api/knowledgeBaseBean
@Api(value = "知识库权限", tags = "知识库权限")
public class KnowledgeBaseBeanController {
    @Autowired KnowledgeBaseBeanHolder knowledgeBaseBeanHolder;

    @PostMapping("/filterVisible")
    public Result<List<String>> filterVisible(
            @LoginUserId String uid,                       // HNSP 自动注入当前用户
            @RequestBody KnowledgeBaseFilterRequest data) {
        CheckUtils.objectCheckNull(uid, "请先登录", ...);  // 鉴权第一关
        return knowledgeBaseBeanHolder.filterVisible(      // 业务交 Holder
                uid, data.getContext(), data.getKbIds());
    }
}
```

记住三句话：**Controller 很薄（只做鉴权+委派）；Holder 写业务；Bean 是表。**

## 5. 三大核心流程（面试必画）

### 5.1 一次完整的"业务请求"（登录 / 改权限）

```
浏览器
  │  POST /ai/api/xxx   （带 Sa-Token Cookie）
  ▼
Nginx  /ai/  ──proxy_pass──▶  Spring Boot :8507  (/ai 上下文)
                                  │
                          @LoginUserId 注入 uid
                          Controller → Holder → Mapper → PostgreSQL
                                  │
                          Result<T>  (HNSP 统一返回体)
  ◀───────────────────────────────┘
浏览器拿到 Result，Pinia store 更新
```
要点：这条链路**完全不经过 Dify**，后端能写库、能审计。

### 5.2 一次 RAG 问答（知识库问答）

```
用户提问
  │  前端组装请求，带登录 token（不再携带 Dify apiKey）
  ▼
Nginx  /ai/api/aiGateway/...  ──(proxy_buffering off)──▶  Spring Boot 网关
                                                          │ 限流 / 配额 / 审计
                                                          ▼
                                             Dify /v1/chat-messages
                                          │
                                    Dify 内部：
                                    1) 召回（retrieval）：按 query 检索 dataset 的分块(segment)
                                    2) 拼接 prompt（检索到的内容 + 问题）
                                    3) 调 Qwen 生成答案
                                    4) 以 SSE 逐字流式返回
  ◀──────── SSE 流（前端 streamingRequest 解析，逐字渲染）────────┘
```
**"RAG"三个字母在哪**：Retrieval（Dify 召回 segment）+ Augmented（拼进 prompt）+ Generation（Qwen 生成）。本平台不做检索，只通过 `filterVisible` 保证**用户只能问到他有权限的知识库**。

### 5.3 一次 Agent / 工作流调用

本质与 5.2 同一条网关通道，只是 Dify 侧跑的是 **workflow / agent**（多步骤、可调用工具），前端仍走 `/ai/api/aiGateway/knowledgeChat/...` 的 SSE。区别：**Agent 会自己决定下一步调用什么工具**，而普通对话是单轮问答。

## 6. 关键代码解读（能看懂、能讲清）

### 6.1 `utils/request.ts` 的 `streamingRequest`（SSE 健壮性，本项目亮点）

- 用 `AbortController` 支持取消；
- **首字节超时 30s**：30 秒内没收到任何字节就 `controller.abort()` + 报错（防止后端/Dify 卡死导致"转圈不停"）；
- **空闲超时 90s**：流建立起后若 90s 无任何数据也中断（防止"假活"）；
- **CRLF 兼容**：按 `/\r\n|\r|\n/` 切行，兼容不同服务器的换行；
- **跨块 `eventType` 保留**：SSE 的 `event:` 行可能和 `data:` 行分在两个 chunk，需跨块拼接状态，否则事件类型丢失。

### 6.2 `utils/markdown.ts` 的 XSS 净化

`renderMarkdown` 注册自定义渲染器：
- `html()`：默认**丢弃**原始 HTML（防注入）；
- `link()` / `image()`：用 `SAFE_URL_PATTERN`（仅 `https?/mailto/tel/相对/blob/data:image`）校验，非法 URL 不渲染。

⚠️ 教训：之前有页面用 `marked.parse` 直接解析，会**绕过这些渲染器**，等于把净化关了——已统一改回 `renderMarkdown`。

### 6.3 `utils/url.ts` 的协议白名单

`safeOpenUrl(url)` 先用 `isSafeUrl` 判断：用 `new URL(url, location.origin)` 解析，只允许 `http/https/mailto/tel`，相对路径（`/`、`#`、`./`）放行，其余 `console.warn` 并返回 `null`。专门拦截 `javascript:` 和 `data:` 伪协议。

### 6.4 `config/constants.ts` 的 `SUPER_ADMIN_RID`

```ts
export const SUPER_ADMIN_RID = 99999;
export const isSuperAdmin = (rid?: number | string | null): boolean =>
  Number(rid) === SUPER_ADMIN_RID;
```
配合 `composables/useIsAdmin.ts` 的 `useIsAdmin()`（读 Cookie 的 `rid`）。所有"超管才显示的按钮/菜单"都用它判断，杜绝魔法数散落。

### 6.5 后端 `filterVisible` 的 fail-closed

权限解析异常时**默认不可见**。面试时可强调：安全系统"默认拒绝"优于"默认放行"。

## 7. Docker / Nginx 部署

### 7.1 部署拓扑

```
服务器
├─ Nginx（:80）
│   ├─ 静态资源  /            → html/dist（前端构建产物）
│   ├─ 反向代理  /ai/         → Spring Boot :8507（context /ai）
│   ├─ 反向代理  /v1/         → Dify（SSE，必须 proxy_buffering off）
│   └─ 反向代理  /qwen/       → 本地 Qwen 模型服务
├─ Spring Boot（jar，:8507，模块 app-start）
├─ PostgreSQL（库 ai）+ Redis
│   └─ 可经 Docker 运行（docker-data/postgres 提供数据卷）
└─ Dify / Qwen（AI 上游，通常独立部署）
```

### 7.2 构建

```bash
# 前端
cd frontend && npm install && npm run build      # 产物 dist/
# 后端（离线仓库在 hd_redis/ai-maven）
mvn -s settings.xml -o package                    # 打出 app-start 的 jar
```

### 7.3 Nginx 路由（AI 网关 + 直连兼容）

```nginx
location /ai/  { proxy_pass http://127.0.0.1:8507/ai/; ... }
# AI 网关：SSE 必须关缓冲，请求体也不能缓冲（文件上传）
location /ai/api/aiGateway/ {
    proxy_pass http://127.0.0.1:8507/ai/api/aiGateway/;
    proxy_buffering off; proxy_request_buffering off;
    proxy_read_timeout 600s; client_max_body_size 2000m;
    add_header X-Accel-Buffering no;
}
# 直连兼容（仅 VITE_AI_GATEWAY=0 时使用）
location /v1/  { proxy_pass http://<DIFY_HOST>/v1/;
                 proxy_buffering off; proxy_cache off; add_header X-Accel-Buffering no; }
location /qwen/ { proxy_pass http://<QWEN_HOST>/; proxy_buffering off; ... }
location /     { root html/dist; try_files $uri $uri/ /index.html; }
```

### 7.4 离线 Docker 安装

## 8. 常见问题排查

| 现象 | 可能原因 | 排查点 |
|---|---|---|
| 问答页面一直转圈、拿不到字 | Nginx 没关 `/ai/api/aiGateway/` 缓冲 | 确认 `proxy_buffering off` + `X-Accel-Buffering no` |
| 登录后业务接口 401 | Sa-Token Cookie 没带 / 过期 | 看 `/ai/api` 是否带 Cookie；Redis 是否存活（Session 存储） |
| 知识库列表能看到无权内容 | `filterVisible` 没接或权限表脏 | 查 `knowledgebasebean` 的 `permissionType` / 黑名单字段 |
| Dify 调用 401 | 服务端保存的 apiKey 错 / 过期 | 查后台「Dify 配置管理」或 `difyconfigbean` 表 |
| 对话返回 503 `gateway_not_configured` | 网关没有可用的 Dify 配置 | 填后台 Dify 配置，或配 `DIFY_CHAT_URL` / `DIFY_CHAT_KEY` |
| 对话返回 429 | 触发每分钟限流或每日 Token 配额 | 等下一分钟/次日，或后台「AI 调用治理 → 配额管理」调整 |
| typecheck 一堆 TS2353 | 多处在重复定义且字段不一致 | 统一到 `types/knowledge.ts`（本项目已治理） |
| 前端构建报 Lombok 错 | 用了 JDK 21 | 切回 **JDK 8** |

## 9. 面试追问 & 标准回答（自测用）

**Q1：为什么 AI 请求走你们后端网关？**
A：为了密钥安全与可治理：Dify Key 只存服务端，浏览器拿不到；网关做按用户限流、每日 Token 配额与审计。代价是多一跳延迟和 SSE 代理复杂度，用字节级透传保证逐字效果不变。早期是直连方案，延迟低但没法治理，现在仅保留为 `VITE_AI_GATEWAY=0` 的兼容开关。

**Q2：你们平台存文档内容吗？怎么保证权限？**
A：一个字节都不存。文档/向量都在 Dify，平台只存"权限关系表"（kbId → 所有者/可见性/部门角色黑名单）。每次列知识库都过 `filterVisible`，且解析失败默认不可见（fail-closed）。

**Q3：RAG 在你项目里是怎么发生的？**
A：本平台不实现检索，RAG 全在 Dify：召回 segment → 拼进 prompt → Qwen 生成。平台只负责"用户只能问有权限的知识库"。

**Q4：SSE 流式你们怎么保证不假死？**
A：`streamingRequest` 设 30s 首字节超时 + 90s 空闲超时（都用 AbortController 中断）；并按 CRLF 切行、跨 chunk 保留事件类型。

**Q5：XSS 怎么防的？**
A：markdown 统一走 `renderMarkdown`（丢弃原始 HTML、URL 白名单）；外链用 `safeOpenUrl` 拦截 `javascript:`/`data:` 伪协议。

**Q6：后端为什么叫 Holder 不叫 Service？**
A：沿用 HNSP 快速开发框架约定，每个实体四件套 Controller→Holder→Mapper→Bean，Holder 即业务逻辑层。

**Q7：Sa-Token 怎么拿到当前用户？**
A：登录发 Cookie；HNSP 的 `@LoginUserId` 注解在 Controller 自动注入 uid，写操作先 `CheckUtils` 判空。

**Q8：Docker 部署你做了什么？**
A：Nginx 托管 dist + 反向代理：`/ai` 走后端（其中 `/ai/api/aiGateway/` 关缓冲、放宽超时和上传大小），直连 `/v1`、`/qwen` 仅在兼容模式下使用；Postgres/Redis 用 Docker；离线环境用仓库内置 docker-ce RPM 装 Docker。
