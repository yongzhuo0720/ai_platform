## P1 问题

### P1-1 网关核心方法 `doProxy` 单方法 397 行，改动风险高
- **问题编号**：P1-1
- **所属模块**：AI 网关
- **具体位置**：`backend/AIProject/app-business/app-business-service/src/main/java/com/aiproject/ai/service/gateway/AiGatewayService.java:932-1328`（397 行；同文件 `doProxyEntry` 93 行、`doProxyOpenAiChat` 87 行、`proxyModel` 80 行；`KbDocPipelineHolder.uploadFile` 123 行）
- **问题现象**：一个方法内串联幂等、并发闸门、熔断、上游请求构造、SSE 心跳/中继、普通中继、截断判定、审计落库、预扣结算等全部逻辑，局部变量十余个（:940-972）。
- **产生原因**：中继路径的异常/计费分支高度耦合，未按职责拆分。
- **影响范围**：计费、熔断、连接释放等关键行为集中在单点，任何改动回归风险大，单测难覆盖全部分支。
- **修复建议**：按"准入 → 上游执行 → 响应中继 → 收尾结算"拆为多个私有方法，用上下文对象承载状态；**只在有测试护栏的前提下做，纯结构重排不改行为**。
- **修复优先级**：P1，但建议放在第一批末或第二批入口，不要在审查后立即动。
- **验证方法**：拆分前后跑 `mvn -o test` 全部 757 项 + `check:streaming` 14 项 + E2E 23 项；重点确认 `AiGateway*Test` 计费/熔断/断流用例全过；对比同一 mock 上游的 usage 与成本数值。

> **2026-11-19 实施结论（重要，如实记录）**：
> 逐行分析后**决定不做完整的 397 行拆分**。原因：所有状态变量（upstreamStatus/billable/actualTokens/
> relayed/parser/三个 Lease）在 try/catch/finally 之间高度共享，是"事务脚本"模式的必然特征；
> 强行拆成上下文对象需改动几乎每一行，属高风险重构，违背任务书"不允许未经分析就大规模重构"
> 与"最小必要修改"原则。该方法的注释完整、测试覆盖充分（39 项 AiGatewayServiceTest），
> 实际回归风险低于问题清单的初始估计。
> **已做的安全改进**：把异常分支里"审计状态码判定"这段纯逻辑提取为
> `AiGatewayService.resolveAuditStatus(timedOut, upstreamStatus)`，新增 3 项单测
> （`AiGatewayAuditStatusTest`），行为完全不变。完整拆分列为遗留项，需专门评估后再决定。

## P2 问题

### P2-1 全局异常处理器回显原始异常消息，含上游响应片段
- **问题编号**：P2-1
- **所属模块**：后端 / 全局异常处理
- **具体位置**：`app/app-start/.../config/GlobalExceptionHandler.java:48-55,78-84`；关联 `gateway/EmbeddingClient.java:161,167,210-216`、`holde/KbRagHolder.java:355-356`
- **问题现象**：`handleBadRequest` 返回 `"请求参数有误：" + safeMessage(e)`，而 `safeMessage` 只做 200 字**长度截断**，未做内容过滤。类注释声称"只回显安全的简短描述"，实际返回原始 `e.getMessage()`。
- **产生原因**：把异常原文当安全文案用；`EmbeddingClient` 的异常消息拼接了上游响应体片段（snippet），`KbRagHolder:355-356` 直接 `Result.failed(null, e.getMessage())`。
- **影响范围**：触发 4xx 业务异常的接口可能把向量服务上游响应片段、内部配置状态（如 `TokenCryptoUtil:51` 的密钥长度信息）回显给调用者。
- **修复建议**：`handleBadRequest` 对 `IllegalArgumentException`/`IllegalStateException` 统一返回固定文案（如"请求参数有误"），完整消息只写服务端日志；`KbRagHolder` 捕获后改通用提示。
- **修复优先级**：P2
- **验证方法**：构造一个抛 `IllegalStateException("SECRET_SENTINEL")` 的用例调接口，断言响应体不含 sentinel、日志含 sentinel；跑后端全量 + 新增该单测。

### P2-2 actuator 端点无鉴权暴露
- **问题编号**：P2-2
- **所属模块**：部署安全 / 可观测
- **具体位置**：`app/app-start/src/main/resources/application.yml:34-52`（`include: "health,info,prometheus"`）；`WebConfig.java:22-33,79-94`（拦截器前缀不含 `/actuator/**`）；全仓无 Spring Security
- **问题现象**：`/actuator/health`、`/actuator/info`、`/actuator/prometheus` 任何人可访问（env/heapdump/threaddump 已关闭，这点是对的）。
- **产生原因**：actuator 路径不在任何拦截器前缀内，也无其他安全框架兜底。
- **影响范围**：部署若直接暴露公网，prometheus 指标泄漏接口路径、调用量、实例名（`application.yml:49-52` 带 application tag）等内部运行信息。
- **修复建议**：将 `/actuator/**` 纳入 Nginx 内网白名单/鉴权，或把 prometheus 绑到独立管理端口（如 9090 仅内网）；保留三个高危端点关闭。
- **修复优先级**：P2（取决于部署网络边界；当前 compose 里 app 不映射宿主端口，风险被网络拓扑缓解）
- **验证方法**：部署后从公网 IP 直接请求 `/actuator/prometheus`，应被拒绝；从内网管理网段可访问；curl 确认 env/heapdump/threaddump 仍 404。

### P2-3 SSO state 无 nonce/过期，callback 不校验 code 与 uid 绑定
- **问题编号**：P2-3
- **所属模块**：SSO 单点登录
- **具体位置**：`controller/SsoTokenBeanController.java:118-144`（callback）、`:152-227`（`buildSignedState`/`signState`/`parseUidFromState`）；`holde/SsoTokenBeanHolder.java:329-378`
- **问题现象**：state 形如 `{uid}.{HMAC-SHA256(uid, clientSecret)}`，是确定性、永不过期的值；callback 只用 state 解析 uid，把 code 换到的 token 直接 `cacheToken(uid, tokenData)`，**从未校验 token 中用户标识（sub/id_token）是否等于该 uid**。
- **产生原因**：只做了"uid 防伪造"（HMAC），未做"一次授权请求绑定"（nonce/时间戳/单次消费）。
- **影响范围**：攻击者若获知某用户 state（URL 历史/Referer）并持有自己的有效 code，可把自己的 token 写到受害者 uid 下（Token 错绑/会话固定）。IdP 侧 code 单次使用仅缓解原样重放，不缓解替换 code。
- **修复建议**：state 改为随机 nonce，服务端保存 `nonce↔uid` 映射并设 5-10 分钟过期，callback 校验并原子消费一次；缓存前校验 token 用户标识与 state uid 一致。
- **修复优先级**：P2（利用需 state 泄露 + 自有 code，条件受限）
- **验证方法**：单测：同一 state 用两次应第二次失败；过期 state 被拒；token sub≠state uid 时拒绝写入；跑 SSO 相关测试 + 后端全量。

### P2-4 checkAdmin/isAdmin 管理员判定在 10+ Holder 重复
- **问题编号**：P2-4
- **所属模块**：代码质量 / 权限
- **具体位置**：`UnitBeanHolder:52`、`MyRoleBeanHolder:57`、`LableChildBeanHolder:110`、`LableBeanHolder:52`、`ApplicationsBeanHolder:45`、`CapabilitiesBeanHolder:47`、`DatasetsBeanHolder:46`、`DifyConfigBeanHolder:31`、`ModelsBeanHolder:54`、`ModelsConfigBeanHolder:48`；另有内联判定 `KnowledgeBaseBeanHolder:191-194,275-276,311-313`、`ModelsConfigBeanHolder:255-257`（均在 app-business-service 或 permission 的 `holde/` 下）
- **问题现象**：`if(uid==null) failed; if(!isAdmin(uid)) failed;` 的模板重复十余份；超管判定既有 `isAdmin()` 又有 `getRid()==99999L` 两种写法。
- **产生原因**：各 Holder 独立演化，未抽取公共基类/工具。
- **影响范围**：改鉴权口径（如增加角色）需改十余处，易漏改导致权限不一致。
- **修复建议**：抽取 `AdminGuard.requireAdmin(uid)` 静态方法或统一基类；统一用 `MyUserBaseDbHolder.isAdmin`（该方法已判空）。
- **修复优先级**：P2（纯内部重构，不改行为）
- **验证方法**：抽取后全量单测；确认 10+ Holder 的越权测试仍过（尤其 `MyUserBaseDbHolderTest`、`LableChildBeanAuthTest`）。

### P2-5 熔断状态进程内，多实例各自独立
- **问题编号**：P2-5
- **所属模块**：AI 网关 / 部署
- **具体位置**：`gateway/GatewayCircuitBreaker.java:49-50`（`ConcurrentHashMap`）、`:32-34`（注释明确"单实例语义，有意取舍"）
- **问题现象**：`breakers` 为 JVM 内状态，无 Redis 共享。多实例部署时一个实例熔断不影响其他实例。
- **产生原因**：有意的设计取舍（代码注释已说明）。
- **影响范围**：整体失败请求量约为"实例数 × 阈值"；与"全局治理"预期有落差。
- **修复建议**：二选一——(a) 改 Redis 共享状态；(b) 保持现状但在文档明确容量规划（如 3 副本时单实例阈值应调低）。**需产品决策，不是纯 bug**。
- **修复优先级**：P2
- **验证方法**：若改 (a)，需多实例联调：实例 A 触发熔断后实例 B 也应 503；跑 `GatewayCircuitBreakerTest` + 多实例压测。若选 (b)，只更新文档。

### P2-6 前端 API 层 248 处 `any`，削弱类型契约
- **问题编号**：P2-6
- **所属模块**：前端 / TypeScript
- **具体位置**：示例 `frontend/src/api/chunk.ts:243,358`、`document.ts:355`、`modelsConfig.ts:18`（`params: any`）；全仓非测试代码统计 248 处 `: any`/`as any`/`<any>`
- **问题现象**：`transformChunk(data: any)`、`transformDocument(data: any)` 等直接把后端字段映射为强类型返回，字段改名/类型漂移不会编译期暴露。
- **产生原因**：API 层未定义响应 DTO，依赖运行时结构。
- **影响范围**：后端字段调整时前端静默拿到 `undefined`，错误后移到运行时。
- **修复建议**：为分页/列表响应定义接口（`PageResult<T>`、`ChunkDto` 等）替换高频 `any`；渐进开启 `noImplicitAny`，不一次性大改。
- **修复优先级**：P2
- **验证方法**：每批替换后跑 `npm run typecheck` + 逻辑/组件测试；统计 `any` 数量应单调下降。

### P2-7 KbDocBean/KbChunkBean 无独立 ownerUid，借用 lastuser 当归属
- **问题编号**：P2-7
- **所属模块**：本地 RAG / 数据结构
- **具体位置**：`bean/KbDocBean.java:16-77`、`bean/KbChunkBean.java:19-52`（均无 ownerUid）；写入 `KbRagHolder.java:173,198`（强制设 lastuser=uid）

- **产生原因**：设计上省了一个字段。

### P2-8 缺少孤儿分块主动对账任务
- **问题编号**：P2-8
- **所属模块**：本地 RAG / 数据一致性
- **具体位置**：`KbRagHolder.java:215-228`（rollback）、`:237-282`（deleteDoc 先删分块后删文档）、`rag/KbDocRunner.java:233-292`（仅回收僵死文档）；全仓 grep `orphan|对账|reconcil` 仅命中注释
- **问题现象**：没有定时扫描"存在 chunk 但 doc 已不存在"的任务。
- **产生原因**：删除路径的补偿只在同步代码里；进程崩溃在"删分块与删文档之间"会留下孤儿分块。
- **影响范围**：孤儿分块仍会被检索命中，返回来源不明的旧内容。
- **修复建议**：增加定期对账（如每日 03:00，`ScheduledTaskGuard` 互斥、只读告警或删除 `docIid` 不在 `kbdocbean` 的 chunk）；先只读告警观察再决定是否自动删。
- **修复优先级**：P2
- **验证方法**：单测：造一个孤儿 chunk，跑对账任务应告警/清理；正常 chunk 不受影响；跑 RAG 全量测试。

### P2-9 RAG 评估无生成侧指标
- **问题编号**：P2-9
- **所属模块**：RAG 评估 / 能力缺口
- **具体位置**：`rag/RagEvaluator.java:17-22`（注释明确只做检索侧，生成侧适合人工月度抽检）
