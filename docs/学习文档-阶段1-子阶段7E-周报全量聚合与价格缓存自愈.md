# 阶段 1 · 子阶段 7E：周报全量聚合与价格缓存自愈

> 本阶段是第二轮深度升级的收尾项。没有新增页面、没有新增接口，只修两个「不报错但结果会悄悄错」的后端问题。
> 这类问题在生产环境里最危险：日志干净、接口 200、看板有数，但数字是错的。

## 1. 只读核实结论

动手前先确认哪些是真实缺口，避免为了改而改。

| 候选问题 | 核实结果 | 处理 |
| --- | --- | --- |
| 周报聚合固定 `while (pageNum <= 100)`，每页 500 行 | **真实缺口**：一周超过 50,000 次调用时，后面的记录被静默丢弃，快照照常落库且无任何标记 | 修复 |
| `ModelPriceResolver` 首次加载失败时把空价格表缓存 5 分钟 | **真实缺口**：数据库抖动一次，故障窗口内所有调用都会被记成 0 成本 | 修复 |

| `@Scheduled` 多实例重复执行 | 已在 7B 用 Redis 互斥解决 | 无需处理 |
| 前端把 `guard_unavailable` 当普通 503 | 提示不够精确，但「稍后重试」对用户是安全建议 | 不改，记录边界 |

两个修复都不改表结构、不改接口协议、不改调用方。

## 2. 缺口一：周报的静默截断

### 2.1 原实现

```java
int pageNum = 1;
while (pageNum <= 100) {              // 100 页 × 500 行 = 最多 5 万行
    Result<PageResult<AiCallLogBean>> result =
            callLogBeanMapper.selectPage(pageRequest, empty, where);
    if (result == null || result.getDatas() == null) {
        break;                        // 读失败也直接结束，继续走保存
    }
    // 累加本页
    if (rows.size() < PAGE_SIZE) {
        break;
    }
    pageNum++;
}
// 无论统计到多少，都会 saveSnapshot(report)
```

两个问题叠在一起：

1. **上限到了不报错**：第 100 页跑完循环自然结束，快照照常写库。
2. **读失败也算结束**：某页查询返回空结果时 `break`，前几页的合计被当成整周数据。

用户看到的是一份格式完全正常、数字偏小的周报——没有任何线索提示它不完整。

### 2.2 修复原则

> 宁可生成失败，也不能落一份自己知道不完整的数据。

统计类快照一旦落库，后续会被当成「事实」用于成本核算、容量规划和趋势对比。
缺一部分的数字比没有数字更糟，因为没有人会去怀疑它。

### 2.3 修复后的实现

```java
static final int MAX_PAGES = 1000;    // 50 万行，远超真实周业务量

int pageNum = 1;
while (true) {
    if (pageNum > MAX_PAGES) {
        log.error("[周报] {} ~ {} 的调用记录超过 {} 条，放弃生成本周快照", ...);
        return Result.failed(null, "本周调用记录超过统计上限（500000 条），暂无法生成完整周报");
    }
    Result<PageResult<AiCallLogBean>> result =
            callLogBeanMapper.selectPage(pageRequest, empty, where);
    if (result == null || result.getDatas() == null) {
        log.warn("[周报] 第 {} 页读取失败，放弃生成本周快照", pageNum);
        return Result.failed(null, "读取调用日志失败，请稍后重试");
    }
    // 累加本页
    if (rows.size() < PAGE_SIZE) {
        break;                        // 只有「读到不满一页」才是正常结束
    }
    pageNum++;
}
```

三个关键点：

1. **正常结束条件只有一个**：某页行数小于 `PAGE_SIZE`（或空页）。返回 null / 失败不再被当成结束。
2. **安全上限仍然存在**：1000 页防止异常数据导致无限循环，但它现在是「显式失败」而不是「悄悄截断」。
3. **失败不落库**：两条失败路径都在 `saveSnapshot` 之前返回，旧快照保持不变。

### 2.4 为什么保留上限

「一直翻到空页」在正常情况下没问题，但数据库里如果出现异常重复数据（例如时间字段脏数据造成分页永远取不完），
没有上限的循环会占住调度线程。安全上限的作用是给最坏情况兜底，代价是超过 50 万行/周时需要人工介入。
以本项目单周调用量衡量，这个上限只在数据异常时才会触发。

### 2.5 调用链

```
周一 02:00 / 管理员手动触发
  → AiWeeklyReportController.generate（仅超管）
  → AiWeeklyReportHolder.generate(weekStart)
  → 按 iid 升序分页扫描 aicalllogbean
      ├─ 读失败 / 超过 1000 页 → Result.failed，不写快照
      └─ 读到不满一页 → 汇总完成
  → saveSnapshot：有则更新、无则插入（唯一索引兜底并发）
```

## 3. 缺口二：价格缓存把失败粘住

### 3.1 原实现

```java
Map<String, Price> fresh = new HashMap<String, Price>();
try {
    // 查 modelsconfigbean，填 fresh
} catch (Exception e) {
    log.warn("[ModelPrice] 加载模型单价失败，沿用旧缓存: {}", e.getMessage());
    if (cache != null) {
        return cache;
    }
    // 注意：这里没有 return，继续往下走
}
cache = fresh;                        // 首次失败时 fresh 是空表
cacheAt = System.currentTimeMillis(); // 空表被缓存 5 分钟
return fresh;
```

首次加载就失败（例如启动时数据库还没就绪）时，`cache` 为 null，代码落到 `cache = fresh`，
把一张**空价格表**当成正常结果缓存了 5 分钟。这期间所有调用都查不到价格，成本全部记 0。

### 3.2 对照：同项目里的正确写法

`EmbeddingClient` 早就处理对了：

```java
try {
    return refresh(now);
} catch (Exception e) {
    // 读库失败不写缓存：下一次调用可以立即重试，而不是把故障状态粘住 5 分钟
    log.warn("[KbRag] 读取向量化模型配置失败: {}", e.getMessage());
    return null;
}
```

同一个项目、同一个缓存模式，两处实现不一致——这类问题靠读单个文件很难发现，必须横向对照。

### 3.3 修复

```java
} catch (Exception e) {
    log.warn("[ModelPrice] 加载模型单价失败，沿用旧缓存: {}", e.getMessage());
    if (cache != null) {
        return cache;
    }
    // 首次加载就失败时不能把空表缓存 5 分钟：否则故障窗口内所有调用
    // 都会被记成 0 成本，账单直接失真。返回空表但不更新 cacheAt，
    // 下一次调用会立即重试数据库。
    return fresh;
}
cache = fresh;
cacheAt = System.currentTimeMillis();
log.info("[ModelPrice] 单价缓存已加载: {} 个模型, keys={}", fresh.size(), fresh.keySet());
return fresh;
```

行为差异：

| 场景 | 修复前 | 修复后 |
| --- | --- | --- |
| 首次加载失败 | 空表缓存 5 分钟 | 本次返回空，下次调用立即重试 |
| 已有缓存后刷新失败 | 沿用旧缓存 | 沿用旧缓存（不变） |
| 正常加载 | 缓存 5 分钟 | 缓存 5 分钟（不变） |

注意这里刻意**不缓存空结果**：缓存空结果会把「暂时读不到」和「确实没有配置价格」混为一谈。
后者是正常业务状态（免费模型），前者是故障，两者的过期策略应该不同。

## 4. 异常与边界

| 场景 | 行为 |
| --- | --- |
| 周报日期格式错误 | 不查询任何数据，直接返回「日期格式应为 yyyy-MM-dd」 |
| 周报分页中途返回 null / 空 datas | 返回「读取调用日志失败」，不落快照 |
| 周报超过 1000 页（50 万行） | 返回「超过统计上限」，不落快照，日志 error |
| 周报恰好 1000 页且第 1000 页满页 | 判定可能还有数据 → 失败，不赌「刚好结束」 |
| 周报落库冲突 | 唯一索引兜底，后到者转为更新赢家行（5E 已实现） |
| 单价表首次读取异常 | 本次返回空表，不写缓存，下次调用重试 |
| 单价表已有缓存后读取异常 | 沿用旧缓存，避免影响正在进行的 AI 调用 |
| 单价表读取成功但没有配置价格 | 正常缓存空表 5 分钟（这是真实业务状态） |

## 7. 明确不做的

### 7.1 多实例配置缓存改成 Redis 版本号

现状是「本地事件失效 + 5 分钟 TTL 兜底」：A 实例改配置后，B 实例最多 5 分钟后生效。
报告里把它列为 P1，但落地前有两个前提不成立：

1. 仓库内没有多实例部署清单（无 compose replicas / K8s），无法验证真实部署形态；
2. 每次调用多一次 Redis 版本读取，对当前单实例部署是净成本。

因此记录为「已知边界」而不是现在实现。真要做时，最小方案是：
写配置时 INCR 一个版本键，读缓存前比对版本，版本变化则失效——不需要引入新中间件。

### 7.2 前端为 `guard_unavailable` 增加专用文案

`503 guard_unavailable` 目前落到「AI 服务暂时不可用，请稍后重试」。
它确实不是「额度用完」，但「稍后重试」对用户仍是正确建议；治理组件恢复后重试即可成功。
在没有更具体恢复指引之前，加一条几乎同义的文案收益很低。

### 7.3 周报改成 SQL 聚合

`COUNT / SUM / AVG` 一次查询确实比翻页快，但需要给 HNSP 生成式 Mapper 增加自定义 SQL，
收益只在超大数据量时体现，风险却落在主链路上。当前分页方案足够，保留。

## 8. 从这两个问题里能学到什么

### 8.1 「静默截断」是最危险的错误类型

程序员的直觉是：报错要处理。但真正难查的是**不报错却给出错误结果**。
分页上限、`LIMIT 1000`、采样统计里都可能藏着这种问题。判断标准很简单：

> 这个数字如果少了一部分，有没有任何地方能看出来？

如果没有，就必须让它显式失败，或者带上「是否完整」的标记。

### 8.2 失败结果不要写进缓存

缓存的前提是「这个值在一段时间内可信」。失败不是值，是状态。
把失败缓存起来，等于把一次瞬时故障放大成一段持续故障。
区分三种情况：

- 成功且有数据 → 缓存；
- 成功但确实没有数据 → 可以缓存（这是业务事实）；
- 读取失败 → 不缓存，下次立即重试。

### 8.3 相同模式要横向对照

`EmbeddingClient` 和 `ModelPriceResolver` 都是「本地缓存 + 事件失效 + TTL」，
但错误分支一个对一个错。单看任何一个文件都合理，只有并排读才能发现不一致。
代码审查时，优先检查「同一模式的多处实现是否一致」，比逐行看语法更容易发现真问题。

## 9. 面试题

1. 周报统计为什么要分页？一次性查全表不行吗？
2. `while (pageNum <= 100)` 的问题是什么？为什么它比抛异常更难排查？
