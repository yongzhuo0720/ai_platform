## 三、项目架构审查摘要（任务书第二节）

完整架构见《项目架构说明.md》。核心调用关系：

```
浏览器 → Nginx → Spring Boot(拦截器鉴权) → Controller(@LoginUserId)
  → Holder(归属/权限) → @HnMapper → PostgreSQL
  → AI 请求: AiGatewayService → 限流/配额/幂等/并发/熔断 → 上游 Dify/OpenAI 兼容
      → SSE 逐字回传 → 用量解析/计价/审计落库
```

九大模块：前端（Vue3+Pinia）、后端（3 大 Maven 模块）、数据访问（HNSP @HnMapper）、Redis（限流/配额/幂等/并发/锁）、AI 网关（核心，26 类）、Dify 集成、本地 RAG（分块→向量→混合检索→RRF→Rerank）、权限（rid=99999 超管 + Holder 内校验）、测试部署（verify.ps1 + docker-compose 多副本）。

**不确定性**：HNSP/qjava 私有框架无源码，框架自动建表、`@LoginUserId` 解析细节等标注为【推断】；所有本次问题均定位在仓库自有代码，不受此影响。

## 五、安全审查（任务书第四节）

### 5.1 逐项结论

| 检查项 | 结论 |
|---|---|
| 登录认证 | 通过：`LoginAuthInterceptor` 默认拒绝 + 白名单；解析器缺失 fail-closed |
| 接口权限 | 通过：敏感接口均带 `@LoginUserId`；`/v1/**` 由 Token 拦截器写属性 |
| 用户资源归属 | 通过：ChatConversation/ChatShare/ApiToken/KnowledgeBase/Agent/RagEval/KbRag 的 Holder 均按 uid/lastuser 收窄校验；**未发现跨用户漏洞**（结构性遗留见 P2-7） |
| API Token 安全 | 通过：`sk-` 随机 20 字节 hex，只存 SHA-256，明文只返回一次，日志只打前 10 位 |
| 模型/Dify 密钥 | 通过：查询统一脱敏出口；不进日志、不进审计表 |
| SQL 注入 | 通过：排序走 `SqlSortGuard` 白名单；唯一对外 queryPage 已保护；全文检索参数转义 |
| XSS | 通过：marked 输出经 DOMPurify.sanitize；用户消息转义 |
| 文件上传下载 | 通过：`getCanonicalFile` + 已登记根目录前缀比较，越界 403 |
| 敏感信息泄露 | **发现问题 P2-1**（异常回显原始消息含上游片段）、**P2-2**（actuator 无鉴权） |
| SSO | **发现问题 P2-3**（state 无 nonce/过期、code 与 uid 未绑定）；Token 加密存储本身通过 |

### 5.2 安全小结

**核心安全面是稳固的**：认证、越权、Token、密钥、注入、XSS、文件穿越七类高风险项逐项核对均未发现漏洞。三个 P2 属纵深防御细节：异常回显、监控端点暴露、SSO 授权绑定——都需要修，但不是"现在能被直接打穿"的漏洞。
