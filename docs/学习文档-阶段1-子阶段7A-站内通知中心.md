# 阶段 1 · 子阶段 7A：站内通知中心

## 1. 业务目标

文档处理流水线与 RAG 评估都是**异步任务**：用户点下「上传」或「开始评估」之后，任务可能在后台跑几十秒到几分钟。在通知中心之前，用户只能一直停在页面上等，关掉页面就再也不知道结果。

本子阶段补齐这条「异步任务售后」链路：

- 任务进入终态（完成 / 失败 / 部分完成 / 超时回收）时，系统给发起人写一条站内通知；
- 顶栏铃铛展示未读数，30 秒轮询一次；
- 打开面板能看通知列表、标记单条或全部已读；
- 点击通知跳到对应业务页面（知识检索页 / RAG 评估页对应数据集）。

它不是新增一个静态页面，而是把「异步任务结果」真正落到数据库、接到真实事件、再由前端呈现的完整闭环。

设计取舍：

| 决策 | 原因 |
| --- | --- |
| 只接异步任务，不接 Agent | Agent 是同步 SSE，执行过程本身就在页面上，再发通知是重复打扰 |
| `eventKey` 唯一索引做幂等 | 任务重复收尾、恢复任务与正常收尾并发时，不能出现两条「完成」 |
| 通知失败不影响主任务 | 通知是售后，不能因为写通知失败把已成功的文档处理回滚成失败 |
| 每用户最多 200 条 | 通知是短期提醒，不是审计日志，避免表无限增长 |
| 归属全部走后端 | 查询、已读、全部已读都强制带 `lastuser = 当前登录用户`，没有跨用户入口 |

## 2. 业务流程图

```text
文档上传 / RAG 评估启动
        │
        ▼
后台 Runner 执行任务
        ├── 文档流水线 KbDocRunner
        │      ├── ready   → 文档处理完成（success）→ /kb-search
        │      ├── failed  → 文档处理失败（error）  → /kb-search
        │      └── stale   → 文档超时回收（warning）→ /kb-search
        └── 评估执行 RagEvalRunner
               ├── success → RAG 评估完成（success）
               ├── partial → RAG 评估部分完成（warning）
               └── failed  → RAG 评估失败（error）
                              → /rag-eval?datasetKey=xxx
        │
        ▼
NotificationHolder.push(uid, notice)
        ├── 校验登录用户与标题
        ├── 生成/规范化 eventKey（缺省用 UUID）
        ├── 级别归一化（非法值降级为 info）
        ├── 截断标题 200 / 正文 2000 / 链接 255 / eventKey 128
        ├── install 写库
        │      └── eventKey 唯一索引冲突 → 幂等失败，不重试、不报错
        └── trimOverflow：超过 200 条从最旧开始删
        │
        ▼
用户打开页面
        ├── 铃铛启动：立即查一次未读数，之后 30 秒一次
        ├── 页面隐藏：跳过轮询；重新可见：立即补一次
        ├── 打开面板：拉列表（含未读总数），面板打开期间轮询改为刷新列表
        └── 点击通知：先标记已读（乐观更新），再站内跳转
```

## 3. 前端原理

### 3.1 文件分工

| 文件 | 职责 |
| --- | --- |
| `frontend/src/api/notification.ts` | 四个接口的请求封装，轮询请求带 `silent` |
| `frontend/src/utils/notification.ts` | 时间解析/相对时间、跳转链接安全过滤 |
| `frontend/src/stores/notification.ts` | Pinia 状态、轮询、乐观已读与回滚、请求序号防竞态 |
| `frontend/src/components/NotificationBell/index.vue` | 铃铛按钮、面板、空态/加载/错误、键盘与点击外部关闭 |
| `frontend/src/layouts/MainLayout.vue` | 把铃铛挂到侧边栏底部 |
| `frontend/src/api/axios.js` / `axios.d.ts` | 新增 `silent` 请求配置，轮询失败不弹全局提示 |

### 3.2 状态与轮询

```ts
const POLL_INTERVAL_MS = 30_000
const LIST_PAGE_SIZE = 20

state: items / unreadCount / listLoading / listError / loadedOnce
       panelOpen / listSeq / countSeq
```

关键点：

- **引用计数**：`startPolling()` 让 `consumers++`，只有第一个消费者创建定时器；`stopPolling()` 归零才清理，避免布局与组件重复挂载时出现多个定时器。
- **页面隐藏跳过**：`pollTick()` 在 `document.visibilityState === 'hidden'` 时直接返回；`visibilitychange` 回到可见时立即补一次，避免后台标签页空转请求。
- **面板打开时轮询列表**：让新通知不仅更新角标，也能出现在已经打开的面板里。
- **请求序号**：`listSeq` / `countSeq` 每次请求自增，响应回来先比对序号，旧响应直接丢弃。标记已读时调用 `invalidatePendingReads()`，让在途读请求作废，防止旧数据把乐观更新覆盖回去。
- **乐观更新与回滚**：单条已读先改本地状态并减未读数，请求失败恢复原状态；全部已读先快照全部条目与未读数，失败逐条恢复。

### 3.3 已读的语义

单条已读接口在「已经是已读」时也返回成功（幂等），前端对已读条目再次点击不会再发请求。

**全部已读的成功响应返回的是本次标记的行数**，不是剩余未读数。前端在成功后直接把本地未读数清零；期间新到的通知交给下一轮计数修正。这个点是在浏览器端到端验证时抓到的真实缺陷，见第 9 节。

### 3.4 跳转安全

通知里的 `link` 来自后端数据，前端仍然做一层收口（`normalizeNotificationLink`）：

- 必须是以 `/` 开头的站内路径；
- 拒绝 `//`、反斜杠、控制字符、`javascript:` 等绝对或伪协议地址；
- 超长截断到 255。

### 3.5 可访问性

- 触发按钮：`aria-label`（含未读数）、`aria-expanded`、`aria-haspopup="dialog"`；
- 面板：`role="dialog"`、`aria-label="通知列表"`、`tabindex="-1"`，打开后焦点进入面板；
- 未读条目额外输出屏幕阅读器文本「（未读）」，不只靠颜色区分；
- `ESC` 关闭并回焦触发按钮；点击面板外部关闭、内部不关闭；
- 加载态 `aria-busy`、空态 `role="status"`、错误态 `role="alert"` + 重试。

## 4. 后端原理

### 4.1 分层

沿用项目四件套：

```text
NotificationController（取登录用户、转发）
        ▼
NotificationHolder（校验、幂等写、分页、已读、清理）
        ▼
NotificationBeanMapper（HNSP 通用 Mapper）
        ▼
NotificationBean（@SqlBean 自动建表映射）
```

`NotificationTypes` 统一收口类别、级别、已读状态字符串，生产方与查询方不再各写各的字面量。

### 4.2 写入幂等

```java
public boolean push(String uid, NotificationBean notice) {
    if (notLoggedIn(uid) || notice == null) return false;
    String title = limit(trim(notice.getTitle()), MAX_TITLE_CHARS);
    if (title.isEmpty()) return false;
    try {
        NotificationBean row = new NotificationBean();
        String eventKey = limit(trim(notice.getEventKey()), MAX_EVENT_KEY_CHARS);
        row.setEventKey(eventKey.isEmpty() ? UUID.randomUUID().toString().replace("-", "") : eventKey);
        row.setCategory(defaultIfBlank(notice.getCategory(), NotificationTypes.CATEGORY_SYSTEM));
        row.setLevel(normalizeLevel(notice.getLevel()));
        row.setTitle(title);
        row.setContent(limit(trim(notice.getContent()), MAX_CONTENT_CHARS));
        row.setLink(limit(trim(notice.getLink()), MAX_LINK_CHARS));
        row.setReadStatus(NotificationTypes.READ_STATUS_UNREAD);
        row.setLastuser(uid);
        row.setEnable(Boolean.TRUE);
        if (notificationMapper.install(row) <= 0) return false;
        trimOverflow(uid);
        return true;
    } catch (Exception e) {
        log.warn("[Notification] 写入通知失败, uid={}, eventKey={}: {}",
                uid, notice.getEventKey(), e.getMessage());
        return false;
    }
}
```

`push` 不抛异常：主任务已经成功，不能因为通知写失败把主任务也拖成失败。`eventKey` 冲突属于正常幂等路径，只记一条 warn。

### 4.3 事件键设计

| 事件 | eventKey | 级别 |
| --- | --- | --- |
| 文档处理完成 | `doc:<docIid>:ready` | success |
| 文档处理失败 | `doc:<docIid>:failed:<attempt>` | error |
| 文档超时回收 | `doc:<docIid>:stale` | warning |
| 评估终态 | `rag-eval:<runKey>:terminal` | success / warning / error |

失败事件带 `attempt`：同一次重试失败不应被上一次失败的幂等键挡住。

### 4.4 查询与归属

列表、未读数、单条已读、全部已读全部以 `lastuser = uid` 为强制条件：

- 列表按 `iid desc` 分页，页大小夹在 1~50；
- 单条已读先按「iid + 当前用户 + unread」更新，更新 0 行时再确认「iid + 当前用户」是否存在，保证已读幂等又不泄露他人通知是否存在；
- 未读数统计失败只记 warn 并返回 0，不把整个列表查询拖垮。

### 4.5 保留上限

每次写入后 `trimOverflow`：统计当前用户总条数，超过 200 时按 `iid asc` 取最旧的 `total - 200` 条删除。正常规模下只在第 201 条时触发，避免每次写入都做大批量删除。

## 5. API 流程

HNSP 控制器按**方法形参名**从 JSON 请求体取字段，前端请求体需要包一层同名 key。

| 接口 | 请求体 | 返回 |
| --- | --- | --- |
| `POST /ai/api/notification/list` | `{ "query": { "pageNum": 1, "pageSize": 20, "onlyUnread": false } }` | `NotificationListResult`：`items`、`unreadCount`、`totalSize`、`pageNum`、`pageSize` |
| `POST /ai/api/notification/unreadCount` | 无 | `Integer` 未读数 |
| `POST /ai/api/notification/markRead` | `{ "data": { "iid": 123 } }` | `Boolean` |
| `POST /ai/api/notification/markAllRead` | 无 | `Integer` 本次标记行数 |

全部接口由登录拦截器保护，`@LoginUserId String uid` 由框架注入；未登录返回 `resp_code=20102`。

典型时序：

```text
页面加载
  └─ POST /unreadCount            → 角标
打开面板
  └─ POST /list                   → 列表 + unreadCount
点击未读
  ├─ 本地乐观改为已读、角标 -1
  ├─ POST /markRead { data: { iid } }
  │     ├─ 成功：保持
  │     └─ 失败：回滚本地状态
  └─ router.push(link)
点击全部已读
  ├─ 本地全部改已读、角标清零
  ├─ POST /markAllRead
  │     ├─ 成功：角标保持 0
  │     └─ 失败：快照回滚
  └─ 面板保持打开
```

## 6. DB 设计

表 `notificationbean`：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `iid` | bigserial PK | 自增主键 |
| `eventKey` | varchar(128) | 幂等键 |
| `category` | varchar(32) | `doc` / `rag-eval` / `system` |
| `level` | varchar(16) | `success` / `warning` / `error` / `info` |
| `title` | varchar(200) | 标题 |
| `content` | text | 正文 |
| `link` | varchar(255) | 站内跳转地址 |
| `readStatus` | varchar(16) | `unread` / `read` |
| `readAt` | int8 | 首次已读毫秒时间戳 |
| `lastuser` | varchar(255) | 归属用户 |
| `createtime` / `updatetime` / `enable` / `app` | — | 框架通用字段 |

索引：

```sql
CREATE UNIQUE INDEX IF NOT EXISTS idx_notification_event
    ON notificationbean ("eventKey");            -- 幂等
CREATE INDEX IF NOT EXISTS idx_notification_user_time
    ON notificationbean ("lastuser", "iid");      -- 面板按用户倒序翻页
CREATE INDEX IF NOT EXISTS idx_notification_user_unread
    ON notificationbean ("lastuser", "readStatus"); -- 角标按用户数未读
```

迁移分三层，两份 DDL 必须同步：

1. `NotificationBean` 的 `@SqlBean` 注解：框架自动建表；
2. `TableSchemaInitializer.ensureNotificationTable()`：应用启动时幂等补表与索引；
3. `scripts/sql/notification-schema.sql`：不重启应用时由 DBA 手工执行。

### 7.2 轮询调度

```ts
async pollTick() {
  if (typeof document !== 'undefined' && document.visibilityState === 'hidden') return
  if (this.panelOpen) {
    if (this.listLoading) return
    await this.fetchList({ silent: true })
    return
  }
  await this.fetchUnreadCount()
}
```

### 7.3 乐观已读与竞态防护

```ts
async markRead(iid: number) {
  const item = this.items.find((row) => row.iid === iid)
  if (!item) return false
  if (item.readStatus === 'read') return true

  const previousStatus = String(item.readStatus ?? 'unread')
  const previousCount = this.unreadCount
  this.invalidatePendingReads()
  item.readStatus = 'read'
  this.unreadCount = Math.max(0, previousCount - 1)

  try {
    const { data: res } = await notificationApi.markRead(iid)
    if (res.resp_code === 0) return true
    this.restoreReadState([{ iid, readStatus: previousStatus }], previousCount)
    return false
  } catch (err) {
    this.restoreReadState([{ iid, readStatus: previousStatus }], previousCount)
    return false
  }
}
```

### 7.4 全部已读

```ts
const { data: res } = await notificationApi.markAllRead()
if (res.resp_code === 0) {
  // 后端返回的是本次标记的行数，不是剩余未读；全部已读后本地清零，
  // 期间新到的通知交给下一轮计数修正
  this.unreadCount = 0
  return true
}
this.restoreReadState(snapshot, previousCount)
```

## 8. 异常处理

| 场景 | 处理 |
| --- | --- |
| 未登录 / uid 为空 | 四个接口统一返回「未登录或登录已过期」，不查库 |
| 通知标题为空 | `push` 返回 false，不写无效数据 |
| eventKey 重复 | 唯一索引冲突 → 幂等失败，只记 warn，不重试 |
| 通知写入异常 | 只记日志返回 false，主任务继续成功 |
| 级别非法 | 归一化为 `info` |
| 正文/标题/链接过长 | 按上限截断，不因超长导致写库失败 |
| 超过 200 条 | 从最旧开始清理，清理失败只记 warn |
| 查询通知异常 | 返回「查询通知失败，请稍后重试」，不泄露堆栈 |
| 未读数统计失败 | 返回 0 并记 warn，列表仍可用 |
| 单条已读：已读 / 不存在 / 不属于本人 | 已读幂等成功；不存在或他人返回「通知不存在或不属于当前用户」，不区分二者 |
| 全部已读影响 0 行 | 成功返回 0，前端幂等 |
| 前端轮询失败 | `silent` 请求不弹全局提示；保留上一次角标值 |
| 前端标记已读失败 | 恢复本地已读状态与未读数 |
| 前端跳转链接不安全 | 拦截跳转，但已读标记照常提交 |
| 页面隐藏 | 跳过轮询；重新可见立即补一次 |

### 9.3 端到端发现并修复的两个真实缺陷

1. **文档通知跳错页面**：原链接写死 `/knowledge-bases`（Dify 知识库页，本地未配置时是空壳），真实异步文档流水线界面在 `/kb-search`。已改为 `/kb-search`，并在 KbDocRunnerTest 中断言 link。
2. **全部已读后角标不清零**：后端 `markAllRead` 返回本次影响行数，前端误当作剩余未读数，角标停在 1。已改为成功后本地清零，并把 Store 测试的模拟返回值从 0 改为 2，防止回归。

## 10. 已知边界

- 通知只覆盖文档流水线与 RAG 评估；Agent 是同步 SSE，没有接入。
- 未读数是 30 秒轮询，不是 WebSocket 推送；对「秒级看到结果」没有强需求。
- 面板一次加载 20 条，没有做「加载更多」；超过 20 条时当前只显示第一页。
- 每用户最多保留 200 条，超出从最旧删除；通知不是审计日志，需要审计请看操作日志。
- 通知写库失败只记日志，不进入重试队列；主任务结果仍以业务表状态为准。
- 清理旧通知在写路径同步执行，规模变大后可改为定时任务。

## 11. 面试题

**Q1：为什么用 eventKey 唯一索引，而不是在业务代码里先查后插？**

先查后插在并发下存在竞态窗口：两个线程同时查到「不存在」，然后都插入。唯一索引把幂等交给数据库的原子约束，冲突时按正常路径处理即可。任务重复收尾、恢复任务与正常收尾并发都不会产生重复通知。

**Q2：通知写入失败为什么不让主任务失败？**

通知是主任务的「售后」，不是主任务的一部分。文档处理和评估的结果已经落在业务表里，通知失败不应该回滚已经成功的工作。这里采用「尽力而为 + 日志留痕」，而不是把两个可用性不同的写操作绑死。

**Q3：未读数轮询怎么避免后台标签页空转和旧响应覆盖新状态？**

页面隐藏时 `pollTick` 直接返回，重新可见时立即补一次；每次请求带自增序号，响应回来先比序号，旧响应丢弃；标记已读前先让在途读请求作废，避免旧列表响应把乐观更新覆盖回去。

**Q4：全量已读的返回值为什么容易踩坑？**

「影响行数」和「剩余未读数」是两个语义。后端返回本次 UPDATE 命中的行数（例如 1），前端如果直接拿来当未读数，角标就会停在 1。正确做法是明确接口语义：要么后端返回剩余未读数，要么前端成功后本地清零。本项目选择后者，并用测试把「返回 2 行仍应为 0」固化下来。

**Q5：为什么通知链接要在前端再做一次安全过滤？**

后端数据也可能被污染（历史数据、其他写入方）。前端只允许以 `/` 开头的站内路径，拒绝 `//`、反斜杠、控制字符和伪协议，避免通知变成开放重定向或 `javascript:` 注入入口。

**Q6：每用户 200 条上限怎么实现，为什么放写路径？**

每次写入后统计总数，超过 200 就按 iid 升序删最旧的溢出部分。放在写路径可以保证「写完即收敛」，不需要额外定时任务；正常规模下只有第 201 条触发一次删除。规模变大后可以迁移到定时清理，避免写请求承担批量删除成本。
