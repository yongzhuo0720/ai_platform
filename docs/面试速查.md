# 面试速查 · AI 聚合平台

> 用法：面试前一天过一遍「3 分钟稿」和「高频追问」，考前 10 分钟只看「能说/不能说」和「补救话术」。
> 所有内容均基于本项目真实代码，不要背不属于你的部分。

---

## 一句话定位

> 一个面向企业内部的 AI 能力门户，把对话、知识库问答、应用构建、模型和数据集仓库聚合到一个平台，
> 并按角色和部门做细粒度权限控制。AI 的检索和编排由 Dify 承担，我负责平台层的用户体系、权限模型和前端交互。

**这句定位的作用**：主动交代"AI 不是我自研的"，把战场拉到你真正做得了主的地方。

## 3 分钟介绍稿（照着说，控制在 3 分钟内）

**第 1 段 · 背景（20 秒）**
> 这是我大三暑假实习做的项目，团队做一个内部 AI 平台，要让各部门的人都能用上 AI，
> 但不同部门能看到的知识库不一样，所以权限是核心需求之一。

**第 2 段 · 架构（60 秒，这段是加分项）**
> 架构上最关键的一个决策是**把 AI 调用收口到后端网关**：
> 对话、知识库、文件上传、智能体助手统一走 `/ai/api/aiGateway/**`，由 Spring Boot 转发到 Dify 或智能体服务。
> 这样 Dify Key 和智能体 Token 都只存在服务端，浏览器拿不到；同时后端能做按用户限流、每日 Token 配额、完整审计，
> 后台还有一张用量看板。
>
> 流式输出用「边读边写」透传，不缓冲 SSE，所以逐字效果和直连一样；
> 治理部分是 Redis 计数器 + PostgreSQL 审计表，网关出错不会阻断 AI 请求本身。
>
> 早期版本是浏览器直连 Dify 的双通道，延迟低但没法治理；后来为了密钥安全和可计量，改成了网关默认、直连保留为兼容开关。

**第 3 段 · 我做的（80 秒，重点）**
> 我主要负责三块：
>
> 一是**知识库权限模型**。设计了三档可见性——公开、仅自己、部分不可见，
> "部分不可见"是配部门和角色黑名单。解析失败时按不可见处理，不让它因为配置出错反而全放开。
>
> 二是**数据和权限的分离**。文档和向量全在 Dify，我们库里只存权限，用 kbId 关联 Dify 的知识库。
> 所以我们自己的库很轻，也不关心索引和向量化这些事。
>
> 三是**安全和稳定性治理**。我排查并修了一批问题，印象比较深的有几个：
> 平台上的能力广场、模型库这些目录，前端按钮本来只给管理员显示，但后端接口完全没校验，
> 任何人直接调接口就能删——我给写操作加了超管校验；
> 还有个文件下载接口直接接收绝对路径，能读到服务器上的任意文件，我改成必须落在已登记的数据集目录内；
> 另外源码里有几处硬编码的真实密钥，也清掉了改成配置下发。
>
> 四是**AI 调用治理网关**（上面说的架构改造）。除了转发，我还处理了两个容易踩的坑：
> 一是 SSE 必须字节级透传、不能按行读完再写，否则会改变分包和到达时序；
> 二是文件上传经过网关时原始 multipart 流可能已被框架消费，我改成从已解析的 Part 重建请求体发给上游。
> 后来我又把智能体助手也接进同一个网关：内置助手的 Token 放服务端环境变量，自定义助手从数据库按可见性取凭据，
> 浏览器伪造的 Authorization 和 X-Agent-Id 会被网关覆盖；上游地址只用服务端配置，避免 SSRF。

**第 4 段 · 收尾（20 秒）**
> 项目还有不完善的地方。后端原先一个测试用例都没有，前端类型检查也没进构建流程。
> 我后来补了鉴权、知识库权限、SSO state、网关 usage 解析的单元测试，现在 30 个用例全部通过；
> 类型检查也加进了 npm scripts，历史错误还在继续清。

> **为什么第 4 段要说不足**：主动说短板 = 有自我认知。但一定要跟着"我正在怎么改"。

## 高频追问 · 逐题答法

### Q1：RAG 是你做的吗？检索、向量化这些？

**这是最关键的一题，答不好整条经历作废。**

> 不是自研的。RAG 的向量化、索引、检索是 Dify 提供的能力，我们做选型时选了 Dify 作为 AI 底座。
>
> 我做的是平台层：
> - 多知识库的**权限体系**，这是 Dify 没有的
> - 本系统知识库和 Dify dataset 的**映射与生命周期管理**，用 kbId 弱引用关联
> - 前端 **SSE 流式**的接入和 Markdown 渲染
> - 上传 → 索引 → 检索 → 回答整条链路的**串联和状态处理**

**别狡辩，别硬说"我参与了 RAG 调优"。** 大方承认选型，然后把平台层的活讲扎实。

### Q2：API Key 怎么管的？放前端不安全吧？

> 早期确实是直连方案，key 下发到浏览器，登录用户 F12 就能拿到，而且后端限不了流、也撤不回。
> 后来我把它改成了**后端网关**：key 只存数据库或服务端环境变量，浏览器只带登录 token 打网关。
> 智能体助手的 Token 也一样收口了：内置助手走服务端环境变量，自定义助手从数据库读取，网关会覆盖浏览器传来的认证头。
>
> 网关这一层做了三件事：
> - 按用户每分钟限流（Redis 计数器），超了返回 429；
> - 按用户每日 Token 配额，配额从上游 usage 里累计；
> - 每次调用写审计表，记录状态、tokens、耗时、模型、会话 ID 和客户端 IP，后台有看板。
>
> 流式体验没有牺牲：SSE 是边读边写透传的，不是攒完再发。
> 直连模式保留了一个开关 `VITE_AI_GATEWAY=0`，只用于排障和兼容旧行为。

**三段式：认历史局限 → 讲现在的方案 → 讲怎么验证效果。** 比背概念更有说服力。

### Q3：越权怎么防的？举一个具体例子

> 举能力广场那个。前端的增删改按钮全都用 `rid === 99999` 控制，只给超管看，
> 但后端接口完全没有校验——任何人直接 POST 删除接口就能清空整个广场，这是典型的"只有前端鉴权"。
>
> 我的处理是先判断这些实体有没有归属字段：
> 知识库、助手这类是"某个用户的资源"，就逐条校验所有者；
> 能力广场、模型库这类是平台级目录，没有归属字段，就限制只有超管能写。
>
> 还有个坑：收紧之后启动时的初始化数据会写不进去，因为注册器没有登录态，
> 所以我给每个 Holder 留了一个内部方法专门给启动逻辑用，不暴露到 HTTP 接口上。

**这题答出"先分类再决定加固方式"和"想到内部调用方"，基本就稳了。**

### Q4：SSE 流式怎么做的？

> 分两段。浏览器侧用 fetch 读流式响应，逐块解析 SSE 事件，把内容增量拼到界面，
> 同时做了 `<think>` 标签剥离和错误事件兜底。
> 后端网关侧是**字节级透传**：每读到一块立刻 flush 给浏览器，同时旁路按行嗅探 usage 和错误，
> 不能按行读完再转发，否则会改变分包和到达时序，逐字效果就没了。
> 部署时 Nginx 要关 `proxy_buffering` 和 `proxy_request_buffering`，并留足读超时。

### Q5：kbId 弱引用会有什么问题？

> 两边没有外键约束，所以 Dify 那边删了知识库，我们这边会留下孤儿权限记录。
> 反过来，Dify 里有但没在我们这登记的库，怎么处理可见性也需要定规则。
> 这个我们是知道的，属于"谁是权威来源"的问题，当时还在跟业务方确认。

**答出代价 = 证明你真的理解，不是只会写代码。**

### Q6：遇到过什么难点？

挑一个真讲过的，不要编。建议讲**越权加固**或**任意文件读取**：

> 文件下载那个接口，签名是接收一个字符串路径，直接 new File 就读了。
> 只要用 text/plain 传个裸路径，就能把服务器上的配置文件下下来，里面还有数据库口令。
> 修的时候不能简单过滤 `..`，那是能绕过的；
> 我是先 `getCanonicalFile()` 规范化，再跟已登记的数据集根目录做前缀比对，越界就 403。
>
> 顺带还发现一个功能 bug：前端传的是 JSON 对象，后端接的是字符串，
> 两边对不上，这个下载功能其实一直是坏的。

### Q7：你负责哪些模块？

> 知识库权限、能力广场和模型库这几个模块的接口鉴权、Dify 配置的接入、
> 文档预览和流式对话的前端交互，还有一批安全和稳定性的问题排查。

**只说你真的动过的。** 用户管理、角色部门那些是 HNSP 生成的，别说。

### Q8：有量化结果吗？

实习项目很难有硬指标，可以这么说：

> 修了大概 20 个缺陷，其中两个是高危——一个是任意文件读取，一个是越权删改平台目录数据。
> 前端类型错误从 120 降到 26，typecheck 也加进了构建脚本；
> 后端补了 30 条单元测试，覆盖超管判定、知识库可见性、SSO state 和网关 usage 解析
> （重点包括"权限配置解析失败必须按不可见处理"这种安全默认值），项目之前是零测试。
> 另外把 AI 调用从浏览器直连改成了后端网关，Dify 与智能体凭据都收口服务端，做了限流、配额和审计。
> 我没有具体的性能指标，因为项目部署在隔离网络环境，我离职时还没上量。

**没有就直说，不要编数字。** 面试官追问细节时会露馅。

### Q9：如果重做，你会改什么？

> 三个：
> 一是继续扩大测试覆盖，现在覆盖了鉴权、权限模型、SSO 和网关解析，其余业务模块还没有；
> 二是智能体助手虽然已接入网关，但还没有按 Token 计量，助手 Token 也仍是明文存库，下一步应该补齐计量和加密；
> 三是知识库的两边数据一致性，应该加个同步或清理机制，而不是靠人工。

### Q10：Java 基础

**这会是硬伤，必须提前补。** 面试官一定会问：
- `@Autowired` 的原理、Spring 的 IoC
- Spring Boot 自动配置
- HashMap / ConcurrentHashMap
- 线程池参数
- synchronized 和 Lock 的区别

这些跟项目无关，但**答不上来，前面讲得再好也作废**。

## 能说 / 不能说（诚信边界）

| ✅ 能说 | ❌ 不能说 |
|---|---|
| AI 网关改造（密钥收口、限流、配额、审计）与取舍 | "我设计了整个系统架构"（这是团队/既定决策） |
| 知识库权限模型的实现 | "我实现了 RAG 检索"（是 Dify） |
| 后端 SSE 透传 + 前端流式解析 | "我做了向量化和 embedding" |
| 越权、文件读取、密钥治理这些修复 | HNSP 生成的 CRUD 接口 |
| 类型检查引入、类型错误清理 | 用户管理/角色部门模块（生成器产出） |
| 文档预览、Markdown 渲染 | 性能提升了 XX%（没数据别编） |

**判断标准**：面试官追问到第三层还能答上来，才算是你的。

## 被问住的补救话术

不要瞎编，用这三句：

1. **"这个具体数字我记不清了，但逻辑是这样……"** —— 转到你能讲清的部分
2. **"这块是框架生成的，我当时没深入改，我的理解是……"** —— 诚实，但给出理解
3. **"这个我没做到，后来复盘觉得应该……"** —— 把不会变成"有反思"

**最忌讳**：硬答一个错误的答案。面试官一追问就穿帮，比承认不会严重得多。
