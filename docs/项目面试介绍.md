# NexusAI 项目面试介绍（2026-11-19）

> 用途：项目维护与面试表达参考。基于本次升级后的真实代码状态。

## 一、一句话定位

企业 AI 能力平台：把 Dify 和多家大模型收口到统一网关，做鉴权、限流、配额、熔断、计费和请求追踪；上层提供知识库、文档异步流水线、RAG 评估工作台和 Agent 工作台。

## 二、项目规模（真实数字）

- 后端：782 项单元测试，3 大 Maven 模块，310 个 Java 文件，25 个 Controller
- 前端：27 逻辑测试文件 309 项 + 30 组件测试文件 301 项 + 23 项浏览器冒烟

- 观察：Prometheus 业务指标（调用量/成本/延迟/失败数，按模型维度）

## 三、核心技术亮点（ interviewer 会追问的点）

### 1. AI 网关的治理链路
一次 AI 请求要穿过：幂等（防重复执行）→ 并发闸门（防打爆）→ 熔断（防雪崩）→ 上游转发 → SSE 逐字回传 → 用量解析 → 成本计价 → 审计落库。
- **难点**：SSE 流式场景下 usage 只在最后一帧给，客户端中途断开时拿不到真实用量
- **解法**：预扣 + 结算机制——请求前按预估 token 预扣，拿到真实 usage 后多退少补；中途断开按预扣值结算（防止"让它说完再停"白拿回答）
- **fail-closed**：Redis 挂了直接拒绝请求，不放行（因为登录态也在 Redis）

### 2. 本地 RAG 的完整流程
文档上传 → 异步分块 → 真实向量化（硅基 bge-m3）→ 混合检索（内存余弦 + PostgreSQL 全文检索）→ RRF 融合 → 可选 Rerank → 注入 system 消息。
- **证据**：带知识库的请求 prompt_tokens 从 35 涨到 685，证明检索内容真的注入了 prompt，不是模型记忆
- **一致性**：另有孤儿分块对账任务（只读告警），检测"文档删了但分块还在"的数据不一致

### 3. 权限与越权防护
- `@LoginUserId` 注入 uid → **Holder 内**做归属校验（Controller 不承接权限判断）
- 超管判定统一走 `AdminGuard`（本次升级抽取），rid=99999
- 知识库三态可见性：public / only_me / partial_invisible，解析失败 fail-closed
- 越权测试覆盖 20+ 用例（A 用户读写 B 用户资源被拒）

### 4. 计费系统
- 单价按"分/百万 token"配置，成本用"毫分"整数运算（避免浮点误差，1 分=1000 毫分）
- 另有每日成本预算 + 超支告警（对标 LiteLLM budget）：达到阈值发 warning、超预算发 error
- 告警 eventKey 带日期+级别，靠通知中心唯一索引幂等，同一天同级告警只发一条

## 四、本次升级做了什么（可作为"持续改进"素材）

对项目做过系统性审查 → 分批加固，而不是一次性大改：
- **审查**：逐项核对 26 Controller / 25+ Holder，发现 0 个 P0、1 个 P1、9 个 P2；历史报告里 6 个高危线索回源码核验（4 已修、2 确认非问题）
- **安全加固**：异常回显脱敏、actuator 端点收敛、SSO state 防重放（时间戳+nonce+签名+token sub 校验）
- **工程改进**：统一超管校验（消除 10+ Holder 重复）、前端 any 类型收敛 64 处、孤儿分块只读告警
- **专业判断**：doProxy 397 行拆分经分析后决定不做（高风险重构），改做安全局部提取——体现"不为凑工作量而重构"

## 六、诚实的边界（被问到时如实说）

- 熔断是进程内状态，多实例各自独立——是有意取舍，文档已给出容量规划
- 孤儿分块只告警不自动删——破坏性操作需人工评估
- MockMvc 全 Controller 权限矩阵未做——有的是 Holder 级越权单测 + 逐项审计
- 私有框架 HNSP/qjava 无源码，部分内部机制是推断

> 面试原则：讲清"做了什么、为什么这么做、验证结果、哪些没做及原因"，比堆功能更有说服力。
