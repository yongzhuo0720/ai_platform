# 阶段 1 · 子阶段 7B：定时任务多实例互斥

## 1. 业务目标

项目里有两个后台链路依赖 `@Scheduled`：

| 任务 | 频率 | 作用 |
| --- | --- | --- |
| `AiWeeklyReportScheduler.generateWeekly` | 每周一 02:00 | 生成上一自然周 AI 调用周报 |
| `KbDocRunner.recoverStaleDocs` | 每 5 分钟 | 回收卡在 queued/chunking/embedding 的文档 |
| `RagEvalRunner.recoverStaleRuns` | 每 5 分钟 | 回收卡在 queued/running 的 RAG 评估 |

单机部署时 `@Scheduled` 天然只执行一次；一旦水平扩到两个实例，**每个实例都会各跑一遍**：

- 周报有两个实例同时做全量聚合，虽然唯一约束挡住了重复记录，但多了一份数据库压力，冲突方还会打出无意义的异常日志；
- 僵死回收每轮最多扫描 `500 × 2` 条 RAG 运行、`500 × 3` 条文档，两个实例重复扫描、重复 CAS；
- 两个实例可能同时盯上同一条僵死任务，虽然状态 CAS 保证只有一方更新成功，但通知、删分块等副作用会有一方做无用功。

本子阶段的目标不是引入新的调度中间件，而是用项目已有的 Redis 做一层**最小够用的互斥**：

> 同一轮定时任务，多实例中只有一个执行，其余实例直接跳过；Redis 不可用时退化为单机执行，任务不能因此停摆。

这条也正好补齐阶段 3 验收里遗留的「两实例定时任务只执行一次」。

设计取舍：

| 决策 | 原因 |
| --- | --- |
| 用现有 `StringRedisTemplate`，不引入 Redisson / ShedLock | 需求只是「同一时刻只跑一个」，自实现 20 行足够；避免为一个锁引入新依赖和新的运维面 |
| `SET NX` + 过期时间，而不是先 `setnx` 再 `expire` | 两条命令不是原子的，中间宕机会留下永不过期的锁 |
| owner token + Lua 比较后删除 | TTL 过期后锁可能已被别的实例重新拿到，直接 `del` 会误删 |
| Redis 故障时 fail-open（照常执行） | 三个任务在数据库层都是幂等的；单实例 + Redis 故障时因为锁而停掉周报，代价更大 |
| 锁只包「定时入口」，不包手动入口 | 管理员手动生成周报是显式操作，应该立即执行，由数据库唯一约束兜底 |

```text
@Scheduled 触发              @Scheduled 触发
      │                           │
      ▼                           ▼
ScheduledTaskGuard.run(task, ttl, body)
      │
      ├── SET ai:sched:<task> <owner> PX ttl NX
      │

      │        │                          │        │
      │        ▼                          │        ▼
      │   执行任务体                       │   日志：另一实例正在执行，跳过本次
      │        │                          │
      │        ▼                          │
      │   Lua: get==owner ? del : 0       │
      │                                   │
      └───────────────┬───────────────────┘
                      ▼
              下一轮调度（5 分钟后）
```

三个任务共用同一个守卫，只是任务名与 TTL 不同：

```text

```

## 3. 前端视角：本子阶段没有用户可见改动

这次改的是后台调度层，前端没有新增页面、接口或状态：

- 用户能感知到的变化是「同一份周报不会生成两次」「同一批僵死任务不会被重复回收」，而不是新的按钮；
- 锁的状态不暴露给前端。它是运维观测项（Redis 键 `ai:sched:*` + DEBUG 日志），不是产品功能；
- 通知中心、文档流水线、RAG 评估页的交互完全不变。

刻意不做「定时任务管理页」：在没有真实的多租户调度需求前，一个只展示 Redis 键的页面属于为了技术名词而加功能。

## 4. 后端原理

### 4.1 单机 `@Scheduled` 的边界

Spring 的 `@Scheduled` 默认使用**单线程** `TaskScheduler`：

- 同一个应用上下文里，多个定时任务会排队执行，不会并发；
- 但这只是**进程内**的串行。两个 JVM 各有一个调度线程，互相不知道对方存在；
- `fixedDelay` 表示「上一次结束后再等 5 分钟」，`fixedRate` 表示「按固定频率」，两者都不解决多实例重复。

所以多实例协调必须依赖进程外的共享存储：这里选 Redis。

### 4.2 守卫的数据结构

```text
Key:   ai:sched:<task>
Value: <owner>            // 32 位无连字符 UUID，每次执行不同
TTL:   ttlSeconds         // 抢锁时一起写入，避免死锁
```

抢锁：

```java
Boolean acquired = stringRedisTemplate.opsForValue()
        .setIfAbsent(redisKey, owner, ttlSeconds, TimeUnit.SECONDS);
```

`setIfAbsent(key, value, timeout, unit)` 对应 Redis 的 `SET key value PX ttl NX`，是**一条原子命令**：

- 键不存在才写入（`NX`）；
- 写入的同时带上过期时间（`PX`）；
- 不存在「先 setnx 成功、进程崩溃、expire 没执行」的窗口。

释放：

```lua
if redis.call('get', KEYS[1]) == ARGV[1] then
    return redis.call('del', KEYS[1])
else
    return 0
end
```

Lua 在 Redis 内单线程执行，`get` 与 `del` 之间不会被其他命令插入。只有 value 仍等于自己的 owner 才删除，避免：

1. A 拿到锁，任务卡住超过 TTL；
2. 锁自动过期，B 拿到同一把锁开始执行；
3. A 终于结束，如果直接 `del`，会把 B 的锁删掉；
4. C 趁虚而入，出现 B、C 同时执行。

带上 owner 比较后，A 的释放脚本因为 value 不匹配而什么都不做。

### 4.3 为什么是 fail-open

守卫的降级策略分三种情况：

| 情况 | 行为 |
| --- | --- |
| 容器里没有 `StringRedisTemplate`（未配置 Redis） | 直接执行，等价单机 |
| 抢锁抛异常（连接失败、超时） | WARN 日志 + 直接执行 |
| `setIfAbsent` 返回 `null` | WARN 日志 + 直接执行，且不释放 |

理由：

- 三个任务在数据库层幂等：周报有 `week_start` 唯一约束；文档回收用状态 CAS（`where status = 旧状态`）；RAG 运行按 `runKey` 更新；
- 单实例部署是当前默认形态。如果 Redis 抖动就让周报不生成、僵死任务不回收，可用性损失大于「多实例时偶尔重复执行」；
- fail-open 的代价被明确记录：多实例 + Redis 故障时可能重复执行，此时靠唯一约束 / CAS 保证数据正确，只浪费算力。

反过来，如果这是「扣款」「发券」这类**不幂等**的任务，就应该 fail-closed（拿不到锁就不执行），这是面试里常问的取舍。

### 4.4 TTL 的取值

| 任务 | 正常耗时 | TTL | 调度间隔 | 说明 |
| --- | --- | --- | --- | --- |
| 周报 | 秒级到分钟级 | 1800s | 一周 | 给全量聚合并发足余量 |
| 文档回收 | 毫秒级到秒级（最多 1500 条扫描） | 240s | 300s | TTL < 间隔，保证本轮异常退出后下一轮一定能重新抢锁 |
| 评估回收 | 毫秒级到秒级（最多 1000 条扫描） | 240s | 300s | 同上 |

原则：

- **TTL 必须大于任务正常耗时**，否则任务还没跑完锁就过期，互斥失效；
- **TTL 应小于调度间隔**（对 fixedDelay 任务），否则一次进程崩溃会让后续几轮全部跳过；
- 任务如果可能超过 TTL，需要 fencing token 或看门狗续期。本项目的回收任务有 500 条/状态的上限，240s 足够，暂不引入续期。

### 4.5 接入方式

三个入口都只保留「一行守卫调用」，原方法体抽成包级私有方法：

```java
@Scheduled(fixedDelay = 5 * 60 * 1000, initialDelay = 2 * 60 * 1000)
public void recoverStaleDocs() {
    scheduledTaskGuard.run("kb-doc-stale-recovery", RECOVERY_LOCK_TTL_SECONDS,
            this::recoverStaleDocsOnce);
}

void recoverStaleDocsOnce() {
    // 原来的扫描 + CAS + 通知逻辑
}
```

好处：

- 调度方法与业务逻辑分离，单测可以直接调 `recoverStaleDocsOnce()`，也可以像现在这样调 `recoverStaleDocs()` 验证守卫链路；
- 包级私有方法不扩大 API 面；
- 周报的异常捕获放在 body 内：即使任务失败，守卫也会在 `finally` 中释放锁，且异常不会被 `@Scheduled` 打成未处理异常。

## 5. API 流程

本子阶段不新增 HTTP 接口。涉及的三条触发链路：

```text
① 周报（定时）
   Spring Cron（周一 02:00）
     → ScheduledTaskGuard.run("weekly-report", 1800)
       → AiWeeklyReportHolder.generate(null)
         → 聚合 ai_call_log → upsert ai_weekly_report（week_start 唯一）

② 周报（手动）
   POST /api/aiWeeklyReport/generate
     → AiWeeklyReportController → holder.generate(weekStart)
     （不经过守卫：用户显式操作应立即执行）

③ 僵死回收（定时）
   Spring fixedDelay（5 分钟）
     → ScheduledTaskGuard.run("kb-doc-stale-recovery", 240)
       → KbDocRunner.recoverStaleDocsOnce()
         → 按状态分页扫描 → CAS 置 failed → 删残片 → 推通知
     → ScheduledTaskGuard.run("rag-eval-stale-recovery", 240)
       → RagEvalRunner.recoverStaleRunsOnce()
         → 按状态分页扫描 → 按 runKey 置 failed → 推通知
```

## 6. 数据库设计

**没有表结构变更，也不需要迁移脚本。** 守卫完全运行在 Redis 上，数据库侧只保留原有的「第二道防线」：

| 数据 | 幂等机制 | 作用 |
| --- | --- | --- |
| `ai_weekly_report` | `week_start` 唯一约束 | 两个实例都执行时也只有一条记录 |
| `ai_kb_doc` | 状态 CAS：`where status = queued/chunking/embedding` | 只有一方能把僵死任务改成 failed |
| `ai_rag_eval_run` | 按 `runKey` 更新 + 活动运行唯一索引 | 重复回收不会产生第二条终态 |
| `ai_notification` | `eventKey` 唯一索引 | 重复回收不会给用户发两条通知 |

这正是 fail-open 的前提：即使锁没起作用，数据仍然正确。

## 7. 核心代码

### 7.1 `ScheduledTaskGuard`

```java
@Slf4j
@Component
public class ScheduledTaskGuard {

    private static final String KEY_PREFIX = "ai:sched:";

    private static final DefaultRedisScript<Long> RELEASE_SCRIPT = new DefaultRedisScript<>(
            "if redis.call('get', KEYS[1]) == ARGV[1] then "
                    + "return redis.call('del', KEYS[1]) else return 0 end",
            Long.class);

    /** 可选依赖：没有 Redis 时退化为单机执行，不会让定时任务停摆 */
    @Autowired(required = false)
    StringRedisTemplate stringRedisTemplate;

    public boolean run(String task, long ttlSeconds, Runnable body) {
        if (task == null || task.trim().isEmpty() || body == null) {
            return false;
        }
        String redisKey = KEY_PREFIX + task.trim();
        String owner = UUID.randomUUID().toString().replace("-", "");
        boolean locked = false;

        if (stringRedisTemplate != null) {
            try {
                Boolean acquired = stringRedisTemplate.opsForValue()
                        .setIfAbsent(redisKey, owner, ttlSeconds, TimeUnit.SECONDS);
                if (Boolean.TRUE.equals(acquired)) {
                    locked = true;
                } else if (Boolean.FALSE.equals(acquired)) {
                    log.info("[Scheduled] 另一实例正在执行，跳过本次: {}", task);
                    return false;
                } else {
                    log.warn("[Scheduled] 获取锁返回空，按单机模式执行: {}", task);
                }
            } catch (Exception e) {
                log.warn("[Scheduled] 获取锁失败，按单机模式执行, task={}: {}",
                        task, e.getMessage());
            }
        }

        try {
            body.run();
            return true;
        } finally {
            if (locked) {
                release(redisKey, owner, task);
            }
        }
    }

    private void release(String redisKey, String owner, String task) {
        try {
            stringRedisTemplate.execute(RELEASE_SCRIPT,
                    Collections.singletonList(redisKey), owner);
        } catch (Exception e) {
            log.warn("[Scheduled] 释放锁失败, task={}: {}", task, e.getMessage());
        }
    }
}
```

## 8. 异常处理

| 场景 | 行为 | 用户/运维可见结果 |
| --- | --- | --- |
| 未配置 Redis（bean 缺失） | 直接执行任务体 | 与单机行为一致 |
| 抢锁抛异常（连接失败/超时） | WARN，直接执行，不释放 | 任务不停摆；多实例下可能重复，靠数据库幂等兜底 |
| `setIfAbsent` 返回 `null` | WARN，直接执行，不释放 | 同上 |
| 没抢到锁 | INFO，跳过，返回 `false` | 另一个实例正常执行 |
| 任务体抛异常 | `finally` 先释放锁，再向上抛 | 锁不会占着；周报任务体内部已捕获，回收任务逐条捕获 |
| 释放脚本抛异常 | WARN，忽略 | 键在 TTL 后自然过期，最多影响一轮 |
| 参数非法（task 为空 / body 为 null） | 返回 `false`，不碰 Redis | 编程错误尽早暴露 |
| 任务耗时超过 TTL | 锁自动过期，可能被另一实例重新拿到 | 依赖幂等（CAS/唯一约束）；这是已知边界 |

### 9.2 真实 Redis 并发验证

用打包后的依赖启动一个一次性校验程序（不进仓库），两个 `ScheduledTaskGuard` 实例同时抢同一把锁，任务体各睡 700ms：

```text
CONCURRENT firstRan=false secondRan=true bodyRuns=1 lockReleased=true
HELD ran=false bodyRuns=0 ownerIntact=true
LIVE-CHECK PASS
```

结论：

- 两实例并发只有一方执行，任务体总执行次数为 1；
- 执行结束后锁键被释放；
- 预先由「别的实例」持有的锁，本次执行直接跳过，且未改动锁的 value。

用新 jar 重启后端（8507），再用一个一次性探针（不进仓库）以 5ms 间隔轮询应用实际使用的 Redis DB 11，在定时任务触发窗口捕到：

## 10. 已知边界

1. **不是分布式调度器**：每个实例仍会被 cron 唤醒，守卫只保证「同一时刻只有一个执行」。唤醒本身的开销很小，但没有「只让一个实例唤醒」的能力。
2. **没有锁续期**：任务耗时超过 TTL 时锁会提前释放，可能出现重叠执行。当前任务的扫描量有上限（每状态 500 条），240s/1800s 足够；若未来出现长任务，应引入看门狗或 fencing token。
3. **Redis 故障时 fail-open**：多实例 + Redis 故障会退化为重复执行。数据正确性依赖数据库唯一约束与 CAS，但会浪费算力。
4. **Redis 主从切换**：异步复制下锁可能丢失（主库写入未同步就切走）。本项目的任务幂等，影响可控；对强互斥任务应使用 RedLock 或带 fencing token 的方案。
5. **手动入口不受锁保护**：`POST /api/aiWeeklyReport/generate` 是显式操作，重复提交由唯一约束挡住；这是有意的产品语义。
6. **无锁状态可视化**：只能通过 Redis 键 `ai:sched:*` 与 DEBUG 日志观察，没有管理页面。当前没有多租户调度运维需求。
7. **单实例内多任务仍串行**：Spring 默认调度线程池只有一个线程；如果未来某个任务变慢，会推迟其他任务。需要时可通过 `ThreadPoolTaskScheduler` 调大池，但那时更要确认任务之间没有共享状态。

## 11. 面试题

### Q1：单机 `@Scheduled` 部署两个实例会发生什么？

每个实例都有独立的 Spring 容器和调度线程，cron 到点后两个 JVM 各执行一次。`@Scheduled` 没有任何跨进程协调能力。解决方式：数据库行锁、Redis 分布式锁、或专门的调度中心（XXL-JOB、ElasticJob）。

### Q2：为什么用 `SET key value NX PX ttl`，而不是 `SETNX` + `EXPIRE`？

`SETNX` 与 `EXPIRE` 是两条命令，不是原子操作。如果 `SETNX` 成功后进程崩溃 / 网络中断，`EXPIRE` 没执行，这把锁就永不过期，后续所有实例永远拿不到锁。`SET NX PX` 一条命令同时完成「不存在才写」和「设置过期」，是 Redis 官方推荐的锁获取方式。

### Q3：为什么释放锁必须校验 owner？

因为锁可能已经过期并被别人重新获取。如果 A 执行时间超过 TTL，B 已经拿到锁，A 结束时直接 `DEL` 会删掉 B 的锁。用 UUID 作为 value，释放时先比较再删除，且比较和删除要放在同一个 Lua 脚本里保证原子性。

### Q4：TTL 应该怎么定？任务超过 TTL 怎么办？

TTL 要大于任务正常耗时、小于调度间隔。任务可能超时的情况下，常见方案：

- 看门狗续期（Redisson 的 watchdog，默认每 1/3 TTL 续一次）；
- fencing token：每次抢锁生成递增 token，下游资源只接受更大的 token，防止旧持有者继续写；
- 把长任务拆小，或改成队列消费。

### Q5：fail-open 和 fail-closed 怎么选？

看任务是否幂等、以及不执行的业务代价：

- 幂等 + 不执行代价高（周报、僵死回收）→ fail-open；
- 不幂等 + 重复执行代价高（扣款、发券、扣库存）→ fail-closed，宁可不执行也不能重复。

本项目三个任务都有数据库幂等兜底，所以选 fail-open。

### Q6：为什么不用 Redisson 或 ShedLock？

需求只有「同一时刻一个实例执行」，自实现约 20 行；项目已有 `StringRedisTemplate`，不引入新依赖、不增加新的运维组件。Redisson 提供看门狗、可重入、多种锁类型，ShedLock 提供注解式封装，适合更复杂的场景。选型要看需求边界，不是越重越好。

### Q7：定时任务的幂等性怎么保证？

三道防线：

1. 数据库唯一约束（周报 `week_start`、通知 `eventKey`）；
2. 状态 CAS（`update ... where status = 旧状态`）；
3. 分布式锁（减少重复执行的频率，但不承担正确性）。

锁解决「性能与噪音」，唯一约束和 CAS 解决「正确性」，两者不能互相替代。

### Q8：`fixedDelay` 和 `fixedRate` 的区别？

- `fixedDelay`：上一次执行**结束**后开始计时，任务耗时不会导致堆积；
- `fixedRate`：按固定频率触发，任务变慢时可能出现排队甚至重叠（取决于线程池大小）。

回收任务用 `fixedDelay`，避免慢任务把调度器压垮。

### Q9：怎么测试分布式锁？

分三层：

1. 单元测试：mock Redis，覆盖抢到 / 没抢到 / 异常 / 释放失败；
2. 真实 Redis 并发测试：两个守卫实例用 `CountDownLatch` 同时抢锁，断言任务体只执行一次、锁最终释放；
3. 多实例部署测试：两个应用实例 + 同一个 Redis，观察只有一个实例输出执行日志。

本次 7B 做了第 1、2 层，第 3 层在当前单机演示环境下用第 2 层替代。

### Q10：Redis 主从切换会丢锁吗？

会。Redis 主从复制默认异步：客户端在主库写入锁成功，主库还没同步就宕机，从库升主后锁不存在，另一个客户端可以再次拿到锁。RedLock 通过「多数派节点同时加锁」降低概率，但仍有争议（Martin Kleppmann 与 antirez 的著名辩论）。对正确性要求高的场景，应该使用 fencing token 或数据库行锁，而不是只依赖 Redis 锁。
