### 1.2 架构：三条通道（这是理解整个项目的钥匙）

```
A 通道 · AI 网关（默认）   浏览器 → /ai/api/aiGateway/{module}/**  → Spring Boot → Dify / OpenAI 兼容上游
                                     SSE 逐块透传、限流、每日 Token 配额（并发预扣+结算）、审计日志、成本核算
B 通道 · 平台业务接口       浏览器 → /ai/api/**  → Spring Boot → PostgreSQL
                                     @LoginUserId 注入身份 + Holder 内权限校验
C 通道 · 浏览器直连（兼容）  VITE_AI_GATEWAY=0 时启用；凭据已从前端彻底移除（在制改动），实际已不可用
```

**数据归属有两条互不相通的链路**，面试和排障都必须先问"走的是哪条"：

- **Dify 托管**：原文/分块/向量都在 Dify，本地 `knowledgebasebean.kbId` 只是指针。
- **本地 RAG**：浏览器抽文本 → `KbRagController` 4 个接口 → 后端分块 + 调向量模型 → `kbdocbean`（元数据）+ `kbchunkbean`（正文 + 向量 JSON）→ 检索时**把向量捞进 Java 里算余弦**，与 PostgreSQL 全文候选做 RRF 融合，可选 Rerank 后注入直连模型。

## 5. 优化方案

### 5.1 后端

**安全门禁（S1）**
1. 把 `LoginAuthInterceptor` + `SqlSortGuard` + `WebConfig` 改动 + `app-start/src/test/**` **作为一个 commit 提交**（这批是一个整体，拆开提交等于把 CI 打红或把门禁注释）。
2. 补 `spring-boot-starter-validation`，给高频入参加 `@Valid` + Bean Validation；`permissionType` 收敛为枚举白名单（当前写错值会被静默判"不可见"，用户体验是"我的库凭空消失了"）。
3. `GlobalExceptionHandler` 增加 `HttpMessageNotReadableException` → 400 明确文案；`safeMessage` 不再回显 `IllegalArgumentException` 原文。
4. 网关：上游异常返回固定中文文案 + `requestId`，原始细节只进日志。

## 7. 每项功能的验收标准（可机器验证优先）

| 类别 | 验收标准 |
|---|---|
| 门禁 | 未登录 curl 访问 `POST /ai/api/chatConversation/save`、`/api/knowledgeBaseBean/query` 等 → `resp_code=20102`，且日志有拒绝记录 |
| 越权 | 用户 A 用 B 的 iid 调 update/delete → 被拒；A 查询列表看不到 B 的 `only_me` 资源；矩阵用例覆盖 22 个 Controller |
| 数据集下载 | 越出登记根目录的路径 → 403；构造 `../` 变体 → 403；普通用户看不到他人数据集 |
| 配额 | Redis 停掉 → 返回 `guard_unavailable` 且**不放行**；跨天预扣不残留在昨日 key |
| 参数校验 | `permissionType` 传非法值 → 400 明确文案（不是静默不可见）；空体/坏 JSON → 400 而非 500 |
| 前端三态 | 人为让接口返回 500 → 页面出现错误横幅 + 重试按钮，控制台无未捕获异常 |
| token 落地 | `grep -rE "#[0-9a-fA-F]{6}" src/views \| wc -l` < 50（并有一致性检查进 CI） |
| 首屏 | `npm run build && npm run check:bundle` 通过，预算维持 ≤260 kB gzip |
| 性能 | 给出 5000 分块 / 10 万日志两组前后计时数字（不许只写"优化了"） |
| 迁移 | 在存量库副本上执行完整迁移脚本 → 成功，且能按预案回滚 |
| 模型连接测试 | 正确配置 → 显示上游模型列表/延迟；错误 key → 中文"认证失败"；错误地址 → 中文"地址不可达"且**不泄漏内网拓扑** |
| 批量上传 | 10 文件（含 1 个坏文件）→ 9 成功 1 失败，失败项有原因与"重试"，重试后状态正确 |
| 智能体执行 | 一次 3 步执行，第 2 步失败 → 页面定位到第 2 步并显示原因，执行记录可查到该次 |
| 文档 | 每个阶段结束更新 `docs/` 与 README 的对应数字（禁止只改代码不改文档） |

### D.3 待批准的三条（按风险从低到高）

**① 只瘦身，不改历史（低风险，可回退）**

```powershell
git reflog expire --expire=now --all
git gc --prune=now
```

把约 220 MB 不可达的 squash 前旧历史从本机删除，pack 预计降到 ~25 MB。
代价：那些旧提交本机就没了（公司 GitLab 上仍有，但我们刚把那个远端摘了）。
附带好处：**"本机还留着原公司完整历史"这件事一并解决**。

**② filter-repo 重写 + 强推 GitHub（破坏性、影响所有 clone）**

```powershell
pip install git-filter-repo
# 回滚点：先打包当前全部引用
git bundle create ..\ai_platform-pre-filter.bundle --all

# 第 1 步：按内容抹掉口令/盐/真名（会重写所有历史版本的文件内容）
#   replacements.txt 每行一条，形如：  <真实口令>==>***LOCAL-SECRET***
#   这个文件写在仓库外、也不入库（它本身就是口令清单）
git filter-repo --replace-text <仓库外的 replacements.txt 绝对路径>

# 第 2 步：整文件从历史消失（真值配置 + 客户截图）
git filter-repo --invert-paths `
  --path backend/AIProject/app/app-start/src/main/resources/application-dev.properties `
  --path docs/ui-capabilities-after.jpg

# 验证：三条都必须为 0 / 无命中，才允许推送
git log --all --oneline -S'<真实口令>' | Measure-Object -Line
git log --all --oneline -- '*application-dev.properties'
git push --force github master
```

影响面（必须知情）：
- **103 个提交 hash 全变**，任何已 clone 的人只能重新 clone；
- GitHub 侧旧 commit 仍会**短期缓存**（`/commit/<sha>` 与 PR diff 可访问），要真正失效需向 GitHub 提 remote deletion 请求——**这一步不是 filter-repo 能代劳的**；
- 强推前必须确认 `git bundle` 回滚点存在且可读（`git bundle verify`）。

**③ 换新库（最干净的替代方案）**

`git checkout --orphan` 把当前 HEAD 做成唯一初始提交，推到一个新仓库，旧仓库转 archived。
好处：不碰 filter-repo、不留任何旧 blob、不需要找 GitHub 删缓存；
代价：**丢掉 103 个提交的演进史**——对求职展示是实打实的损失，commit 历史本身就是"会迭代"的证据。

### D.4 我的建议顺序

先 **①**（瘦身让 filter-repo 快一个量级），再 **②**，② 之后按 D.3 的三条验证命令确认无残留才推送。**在你逐条批准之前，①②③ 一条都不执行，也不推送任何东西。**
