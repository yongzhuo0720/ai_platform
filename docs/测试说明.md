# 测试说明：可重复执行的命令清单

最后更新：2026-10-29
适用于：本地 Windows + Git Bash / PowerShell 环境

这份文档的目的是让**任何人（包括三个月后的你自己）**都能用一条命令把项目的质量门禁跑一遍，
不需要回忆当时是怎么配的环境。

---

## 0. 先确认环境（最容易踩的坑）

| 检查项 | 要求 | 怎么确认 |
|---|---|---|
| JDK | **必须是 8**，不能是 21 | `java -version` 应显示 `1.8.x` |
| Maven | 3.6+ | `mvn -v` |
| Node | 18+ | `node -v` |
| 前端依赖 | 已安装 | `frontend/node_modules` 存在 |

### ⚠️ 坑一：默认 JAVA_HOME 是 JDK 21，但项目要 JDK 8

本机默认 `JAVA_HOME` 指向 JDK 21，而项目目标是 Java 8。
用 JDK 21 跑会失败，且**报错信息具有误导性**（Lombok 相关的奇怪错误）。

```bash
export JAVA_HOME="/d/DevTools/Java_jdk 1.8"
export PATH="$JAVA_HOME/bin:$PATH"
java -version   # 确认输出 1.8.x
```

### ⚠️ 坑二：直接 `mvn test` 会失败，必须指定离线 settings

默认的 `~/.m2/settings.xml` 里配置了 `<mirrorOf>*</mirrorOf>`，
它会把**所有**仓库请求（包括私有框架仓库）转到阿里云，
于是 `com.heneng.hnsp` 系列依赖解析不到：

```
Could not find artifact com.heneng.hnsp:hnsp-public-common-croe:jar:1.2.3-SNAPSHOT
```

项目自带了一份正确的 settings（`hd_redis/ai-maven/conf/settings.xml`），
它的 `<mirrorOf>central</mirrorOf>` 不会拦截私有仓库。**必须显式指定它。**

### ⚠️ 坑三：`mybatis` 版本被框架声明成 `LATEST`

私有框架 `hnsp-public-common-croe` 在自己的 pom 里写的是
`<version>LATEST</version>`，Maven 会去拉当前最新版。

2026-10-29 实测：当天 16:55 构建正常，16:57 元数据刷新后拉到
`mybatis 3.6.0`（Java 11 编译，class 版本 55.0），JDK 8 直接编译失败：

```
class file has wrong version 55.0, should be 52.0
```

已在根 `pom.xml` 用 `dependencyManagement` 锁定 `3.5.19`。
**这个锁定不要移除**，否则构建会在任意时刻自己坏掉。

## 1. 后端测试（一次跑完）

```bash
export JAVA_HOME="/d/DevTools/Java_jdk 1.8"
export PATH="$JAVA_HOME/bin:$PATH"
cd /d/ai_project/ai_platform/backend/AIProject

mvn -s "D:/ai_project/ai_platform/hd_redis/ai-maven/conf/settings.xml" \
    "-Dmaven.repo.local=D:/ai_project/ai_platform/hd_redis/ai-maven/pro" \
    -B test
```

PowerShell 写法：

```powershell
$env:JAVA_HOME = 'D:\DevTools\Java_jdk 1.8'
$repo     = (Resolve-Path hd_redis/ai-maven/pro).Path
$settings = (Resolve-Path hd_redis/ai-maven/conf/settings.xml).Path
Set-Location backend/AIProject
mvn -s $settings "-Dmaven.repo.local=$repo" test
```

**预期结果（2026-10-29 基线）**：

| 模块 | 用例数 |
|---|---|
| app-common | 7 |
| app-business-permission | 35 |
| app-business-service | 123 |
| **合计** | **165，0 失败** |

只看汇总：

```bash
mvn ... test 2>&1 | grep -E "Tests run:|BUILD"
```

首次运行需要联网下载 `surefire-junit-platform`；之后可加 `-o` 离线执行。

## 2. 前端检查与构建

```bash
cd /d/ai_project/ai_platform/frontend

npm run typecheck        # TypeScript 类型检查（strict 模式）
npm run check:streaming  # SSE 流式回归：14 项
npm run check:markdown   # Markdown 渲染与 XSS 消毒回归：10 项
npm run build            # 生产构建
```

**预期结果**：全部通过。构建会有 `element-plus` 分包 1.05MB / gzip 331KB 的警告，
属已知项，不影响功能，暂未处理。

### 关于 `check:markdown` 的一段历史

这个脚本在 2026-10-29 之前**一直是失败的**，报错：

```
TypeError: purify_default.sanitize is not a function
```

原因是 `markdown.ts` 用 DOMPurify 做 XSS 消毒，而 DOMPurify 在**模块导入时**
就要读 `window`；Node 里没有 `window`，于是拿到未初始化的实例。

**这意味着那 10 条 XSS 断言从来没真正执行过** ——
"防住了 `javascript:` 链接"、"防住了 `<img onerror=...>`" 这些结论此前是没有验证的。

修复方式：在导入 `markdown.ts` 之前用 `jsdom` 注入 DOM 环境（见
`scripts/check-markdown.mjs` 顶部）。`jsdom` 是**仅测试用**的 devDependency，不进生产包。

## 5. 测试覆盖了什么，没覆盖什么

### 已覆盖

| 领域 | 说明 |
|---|---|
| 权限与越权 | 知识库可见性 fail-closed、助手归属、角色查询收敛、部门/标签写接口鉴权 |
| AI 网关 | 身份覆盖、上传转发、畸形/超大请求拒绝、usage 解析、模型路由 |
| 本地 RAG | 向量对齐、指标算法、黄金集一致性 |
| 会话同步 | 旧快照拦截、带版本条件更新、保存失败不报成功 |
| SSE | 首字节超时、空闲超时、取消、跨 chunk 拼接 |
| Markdown/XSS | `javascript:` 拦截、`onerror` 拦截、URL 白名单、表格包裹 |

### 未覆盖（诚实清单）

| 缺口 | 原因 |
|---|---|
| Controller 层 / API 集成测试 | 没有引入 MockMvc，也没有独立测试库 |
| 真实越权端到端验证 | 需要起服务 + 普通账号 + 独立测试库 |
| SSE 真实断流与压测 | 需要 mock 上游 + 并发场景 |
| 配额并发击穿 | 需要并发请求验证 |
| 前端组件单元测试 | 未引入 vitest / @vue/test-utils |
| 真实上游质量与容量 | 不连接真实 Dify / 生产数据库 |

**不要把这些未覆盖项说成"已验证"**，面试时尤其要注意。

## 6. 改动代码后的最小自检

```bash
# 只跑后端
mvn -s <settings> "-Dmaven.repo.local=<repo>" -B test

# 只跑前端
cd frontend && npm run typecheck && npm run check:streaming && npm run check:markdown && npm run build
```

CI（`.github/workflows/ci.yml`）目前只跑前端，后端因依赖私有 Maven 私服暂未接入；
本地请用上面的后端命令或 `scripts/verify.ps1` 兜住。
