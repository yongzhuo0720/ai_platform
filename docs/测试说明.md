# 测试说明：可重复执行的命令清单

最后更新：2026-10-30
适用于：本地 Windows + Git Bash / PowerShell 环境

这份文档的目的是让**任何人（包括三个月后的你自己）**都能用一条命令把项目的质量门禁跑一遍，
不需要回忆当时是怎么配的环境。

---

## 0. 先确认环境（最容易踩的坑）

| 检查项 | 要求 | 怎么确认 |
|---|---|---|
| JDK | **必须是 8**，不能是 21 | `java -version` 应显示 `1.8.x` |
| Maven | 3.6+ | `mvn -v` |
| Node | 22+（jsdom 30 官方要求 ≥22.22；本机 22.20 实测可跑，CI 用最新 22） | `node -v` |
| 前端依赖 | 已安装 | `frontend/node_modules` 存在 |

### ⚠️ 坑一：默认 JAVA_HOME 是 JDK 21，但项目要 JDK 8

本机默认 `JAVA_HOME` 指向 JDK 21，而项目目标是 Java 8。
用 JDK 21 跑会失败，且**报错信息具有误导性**（Lombok 相关的奇怪错误）。

```bash
export JAVA_HOME="/d/DevTools/Java_jdk 1.8"
export PATH="$JAVA_HOME/bin:$PATH"
java -version   # 确认输出 1.8.x
```

### ⚠️ 坑二：直接 `mvn test` 会失败，必须指定离线 settings

默认的 `~/.m2/settings.xml` 里配置了 `<mirrorOf>*</mirrorOf>`，
它会把**所有**仓库请求（包括私有框架仓库）转到阿里云，
于是 `com.heneng.hnsp` 系列依赖解析不到：

```
Could not find artifact com.heneng.hnsp:hnsp-public-common-croe:jar:1.2.3-SNAPSHOT
```

项目自带了一份正确的 settings（`hd_redis/ai-maven/conf/settings.xml`），
它的 `<mirrorOf>central</mirrorOf>` 不会拦截私有仓库。**必须显式指定它。**

### ⚠️ 坑三：`mybatis` 版本被框架声明成 `LATEST`

私有框架 `hnsp-public-common-croe` 在自己的 pom 里写的是
`<version>LATEST</version>`，Maven 会去拉当前最新版。

2026-10-29 实测：当天 16:55 构建正常，16:57 元数据刷新后拉到
`mybatis 3.6.0`（Java 11 编译，class 版本 55.0），JDK 8 直接编译失败：

```
class file has wrong version 55.0, should be 52.0
```

已在根 `pom.xml` 用 `dependencyManagement` 锁定 `3.5.19`。
**这个锁定不要移除**，否则构建会在任意时刻自己坏掉。

### ⚠️ 坑四：`hd_redis/` 不入库，克隆仓库≠能跑后端测试

`.gitignore` 第 44 行把整个 `hd_redis/` 排除掉了（里面是离线 Maven 仓库、
绿色版 PostgreSQL 与 Redis，体积大且带私有框架 jar）。所以新机器 `git clone`
下来后端是**跑不动**的——这是后端进不了 GitHub Actions 的同一个根因。

要么从开发机把 `hd_redis/ai-maven` 拷过去，要么在有私服的机器上跑。
`scripts/verify.ps1` 已经改成缺目录时直接给出这句话，而不是抛一串 `Resolve-Path`
英文异常。

### API 密钥自助页（2026-11-01 新增）

前端「用量中心 → API 密钥」补了两处测试：

| 文件 | 用例 | 守的是什么 |
|---|---|---|
| `src/api/__tests__/aiApiToken.spec.ts` | 2 | 直接盯 axios 的 `post(url, body)`：写操作必须包一层 `data`，键名与后端方法参数名对齐 |
| `src/views/ApiKeysView/__tests__/ApiKeysView.component.spec.ts` | 11 | 列表口径（前缀省略号 / 空白名单=全部模型 / 过期与停用都算不可用）、名称为空不发请求、有效期按天数换算、明文只在创建弹窗出现且关闭后从状态里抹掉、编辑不下发 `expireAt`（做不到清空）、开关成功要动 / 失败要回滚、删除取消与确认两条路、异常后 loading 收掉 |

两个坑值得记住：

1. **组件测试 mock 掉 api 层，就测不到 api 层自己的契约。** 最初把「请求体包一层 data」
   写进组件用例，断言 `create` 收到 `{ data: {...} }` —— 而组件传出去的本来就是扁平对象，
   包装发生在被 mock 掉的那一层。这类断言只在 mock 里自证，改成直接 mock `../axios` 才有效。
2. **受控组件会造成「绿色但从未执行过」的假绿。** 开关写的是 `:model-value="row.enable !== false"`
   （不是 v-model），点击事件里不回写 `row.enable` 就**界面永远不动**；而用例只断言
   `is-checked` 仍在，把回滚代码整行删掉测试照样绿。补了「停用成功：开关要落下、状态列与计数同步」
   之后，删掉回写 → 该用例红，删掉回滚 → 失败回滚用例红，两边都咬住了。
   验证方式照旧：改坏源码跑一遍，确认红的正是对应那一条，再复原。

浏览器实测（后端 `:8507` + Vite `:5173`，真库真接口）走过：新建 30 天有效期 → 明文弹窗
（43 字符、`readonly`、示例里带上 origin 与明文）→ 开关停/启两轮 → 编辑后到期时间不变
（`2026-12-01 17:28`）→ 删除的取消与确认两条路。测完把新建的那把 `ui-check` 删掉了，
库里只剩 curl 实测留下的 4 把。

> 附带发现：`evaluate_script` 里点 `.el-message-box` 的按钮要取**最后一个**，
> 页面处于 hidden 状态时 Element Plus 的弹层过渡不结束，旧节点会滞留在 DOM 里，
> 按 `querySelector` 拿到的是已失效的第一层。

### 操作日志读接口（2026-11-01 新增）

后台「操作日志」页原来调的是框架模块里的 `/userControllerlog/getControllerLogByTimeAdmin`，
而那个模块在 `app-business-permission/pom.xml` 里是注释掉的 —— 接口根本不存在，页面一直是 404。
补了本项目自己的 `POST /ai/api/controllerLog/query`（只读、仅超管），配套三个测试类/文件：

| 测试类 | 用例 | 守的是什么 |
|---|---|---|
| `ControllerLogHolderTest` | 15 | 非超管与未登录**在校验阶段就返回、连 SQL 都不发**（`verify(never())`）；只填一头日期、格式不对、起止颠倒全部拒绝；`pageSize` 收到 999999 收敛到 200、`pageNum` ≤ 0 回落到 1；排序固定 `iid desc`（请求体里没有 order/desc，注入面就不存在）；日期先解析成 `LocalDate` 再格式化，条件里只剩规范化后的数字；mapper 返回 null 记成「查询失败」而不是 NPE |
| `ControllerLogSqlShapeTest` | 2 | 框架给这个实体生成的查询列：必须含页面要用的 `uaccount/action/clientip/serverip/url/res/time/createtime/iid`，必须不含 `params`（请求参数快照，可能带明文口令）和表里根本没有的 `lastuser/updatetime/enable/key1-3`；`@SqlBean.value` 与 `@HnMapper.tablename` 都必须是 `usercontrollerlog` |
| `src/api/__tests__/log.spec.ts`（前端） | 2 | 直接盯 axios 的 `post(url, body)`：URL 必须是本项目的 `/ai/api/controllerLog/query`，请求体必须只有 `query` 这一个键。这条契约在组件测试里**测不到**（`@/api/log` 被 mock 掉了），而漏掉包装的后果不是报错、是「筛选永远不生效」——后端把裸传的条件解析成 null，安静地返回全量第一页 |

变异验证（新用例必须能红）：把 `log.ts` 里的 `{ query: params }` 改回裸传 `params` →
`log.spec.ts` 两条全红；复原后全绿。

两个坑：

1. **`@SqlBean` 的表名属性是 `value`，不是 `table`。** 反编译 `SqlFieldTools.getTableName(Class)`
   看到的逻辑是「`value` 非空就用它，否则取类名（`tolow` 为真时小写）」。本项目其他 Bean 的表名
   恰好等于类名小写，所以从没写过 `value`，也就从没人验证过这个属性——第一次给这张框架表写实体，
   把 `value` 当成「显示名」写成中文，`getTableName` 就返回了「操作日志」。形状用例现在钉住了这一条。
2. **单测证明不了 SQL 能在真库跑。** 上面两类都是 mock mapper 的纯逻辑用例。所以额外做了两件事：
   用 psql 手工执行框架那条形态的 SQL（同样的列清单 + `createtime between` + `order by "iid" desc`
   + `limit/offset`）确认真库接受并返回数据；启动后查 `pg_indexes` 确认
   `idx_usercontrollerlog_createtime` 确实由 `TableSchemaInitializer` 建出来了。

**接口侧拒绝（curl，2026-11-01 实跑）**：匿名 `POST /ai/api/controllerLog/query` 返回
`200 + resp_code:20102（请先登录）`（不是 404，说明路由已注册）；伪 `uaccess` 同样 `20102`；
带上起止颠倒日期的请求也被登录拦截在先——鉴权发生在进 Holder 之前。

**超管正向用例（2026-11-02 已闭环）**：用超管账号在浏览器里实跑 `#/admin/logs`，
逐条对上——

| 检查 | 实测 |
|---|---|
| 列表 | 表头 8 列（序号/操作/操作接口/客户端IP/操作结果/执行接口耗时/操作者账号/操作时间），首屏 20 行真实数据，`共 11658 条` |
| 时间格式化 | `createtime` 真库返回的是 `"2026-11-02 16:33:59"` 字符串（**不是**毫秒数），页面渲染成 `2026-11-02 16:33:59`；毫秒数分支由组件用例覆盖，两条都在 |
| 只填一头日期 | 点搜索弹「请同时选择开始日期与结束日期」，且**没有发出请求**（分页计数仍是 11658） |
| 日期区间 | 起止都填当天 → 后端条件生效，`共 9 条`，全部行都是当天；清空后回到 `共 11658 条` |
| 翻页 | 第 2 页首行变成 `2026-11-01 17:35:47 删除平台API密钥`，与第 1 页（当天）不同 |
| 线上请求体 | 拦住 XHR 抓到的是 `{"query":{"pageNum":1,"pageSize":20}}` / `{"query":{"pageNum":2,"pageSize":20}}` —— `{ query: ... }` 包装在真实链路上成立 |
| `params` | 接口返回体与页面 DOM 里都没有 `params`（实体不映射，SQL 层就没 SELECT） |

> 顺带记下这次为什么之前跑不了：本机 PostgreSQL 没启动（Redis 是服务 `RedisAI`，一直在跑）。
> 后端 jar 起来后并不会失败退出，而是停在 Druid `create connection ... Connection refused`
> 的重试里，8507 一直不监听；把 PG 拉起后它**自己就绑上端口了**，不用重启 JVM。

### 关于图标注册（2026-10-30 新增）

`main.ts` 此前用 `import * as ElementPlusIconsVue` 把 **293 个图标全部全局注册**，
不论页面用没用到都会进首屏。实际模板与导航数据只用到 56 个，改为：

- 组件内直接 `import { Xxx } from '@element-plus/icons-vue'`（默认做法）；
- 只有 `data/*.ts` 的字符串图标和组合式函数返回给模板的图标，才登记到 `main.ts`
  的 `globalIcons`（当前 23 个）。

这样 Element Plus 分块从 1,052.14 kB 降到 922.89 kB（gzip 331.25 → 296.83 kB）。

代价是"模板用了图标但忘了 import"不会再报错，只会**静默留白**。所以新增
`npm run check:icons`：逐文件核对模板里的图标标签与 `icon: 'Xxx'` 字符串，
既没 import 也没全局注册就失败；同时禁止 `import *` 回归。
已用临时探针文件验证过它能拦住漏注册的情况。

### 关于 `check:markdown` 的一段历史

这个脚本在 2026-10-29 之前**一直是失败的**，报错：

```
TypeError: purify_default.sanitize is not a function
```

原因是 `markdown.ts` 用 DOMPurify 做 XSS 消毒，而 DOMPurify 在**模块导入时**
就要读 `window`；Node 里没有 `window`，于是拿到未初始化的实例。

**这意味着那 10 条 XSS 断言从来没真正执行过** ——
"防住了 `javascript:` 链接"、"防住了 `<img onerror=...>`" 这些结论此前是没有验证的。

修复方式：在导入 `markdown.ts` 之前用 `jsdom` 注入 DOM 环境（见
`scripts/check-markdown.mjs` 顶部）。`jsdom` 是**仅测试用**的 devDependency，不进生产包。

| `preloadRecovery` | 发布后旧 chunk 404 触发一次节流重载；storage 异常时降级不抛错 |

两点实现说明：

1. `vitest.config.ts` 独立于 `vite.config.ts`，只挂 `@` 别名与 jsdom，不加载 Vue 插件和样式处理。
2. 逻辑层会 `import { ElMessage } from "element-plus"`，真实包会拉起整套组件树；
   测试里通过 alias 指向 `src/test/element-plus-stub.ts`，不产生真实 UI。

**这套测试上线时就抓到一个真实缺陷**：xlsx 的 MIME
（`application/vnd.openxmlformats-officedocument.spreadsheetml.sheet`）包含
`officedocument`，被 Word 分支抢先命中，Excel 文件一直显示成 Word 图标。
已调整 `getFileTypeEmoji` 的判定顺序并加用例锁定。

实现上拆出 `vitest.component.config.ts`：加载 `@vitejs/plugin-vue` 与

配置里的 `server.deps.inline: ["element-plus"]` 不是性能选项，而是正确性修复：
Element Plus 的表单校验 `import AsyncValidator from "async-validator"`，该包只发布
CJS 入口（`module.exports = { default: Schema }`）。Vitest 默认把 node_modules
外部化交给 Node ESM 加载，Node 不识别 `__esModule`，默认导入拿到的是整个导出对象，
`new AsyncValidator(...)` 抛异常后被 FormItem 的 catch 吞掉——表现为**每个字段校验
静默失败、`el-form.validate` 恒为 true**。内联后由 Vite 套用默认导出互操作，
校验行为才与浏览器构建一致。若以后新增「表单校验」相关断言，务必保留这一行。

> **jsdom 下 `isVisible()` 不可靠**：首次渲染后再改 `v-show`，VTU 的
> `isVisible()` 仍返回旧值（与真实 DOM 不符）。消息区用例改为断言 Vue 写入的
> inline `display: none`，避免出现「测试骗人」。

### 关于硬编码色值棘轮（2026-11-02 新增）

主题 token 体系（`src/styles/tokens.css`，深色 `:root` + `:root[data-theme="light"]`）
2026-10 就建好了，但组件里继续抄旧文件的字面色，等于两套体系并行：新写的越多，
token 越收不拢，浅色主题的覆盖清单也永远补不完。

一步清零不现实——实测存量是 **48 个文件 / 2102 处**（hex 3/4/6/8 位与 `rgb()/rgba()`），
一次性换成 `var(--xxx)` 会同时改动大量视觉细节，风险远大于收益。所以做成棘轮：

- 基线写在 `scripts/check-styles.baseline.json`，**按文件**记录当前数量；
- 任一文件超过自己的基线即失败——总量下降但某个文件变差也算变差；
- **新文件不在基线里，允许额度是 0**，写一句 `#fff` 就直接红，这是门禁的主要价值；
- 改干净后跑 `node scripts/check-styles.mjs --write` 重算基线，数字只会越改越小；
- `tokens.css` 豁免：它是色值的定义处，本身就要写字面色。
  `theme-light.css`（各页浅色适配）和 `element-override.css`（EP 运行时覆盖）**不豁免**，
  它们不是 token 源头，同样是待清理对象。

扫描范围是 `src/` 下的 `.vue/.ts/.css/.less/.scss`。每条正则前后都带断言
（`(?<![\w#])` 与 `(?![0-9a-zA-Z_-])`）：前者防止把标识符尾巴里的 `#abc` 认成色值，
后者保证 `#4f7bff` 不会同时被 6 位和 3 位规则数两遍。CI 与 `scripts/verify.ps1`
都接了这一步，放在组件测试之前——它不需要 DOM，秒级完成。

顺带纠正一处文档错误：《项目全面审查与升级方案》里原来写的「约 488 处」是估的，
无法复现也无法当基线；现在这个数字由脚本给出，任何人 clone 下来都能跑出一样的结果。

### 关于产物体积预算（2026-10-30 新增）

`npm run build` 只会对单个 chunk 超过 500 kB 给警告，不会失败；而「全量注册
293 个图标」这种膨胀此前就是靠人肉发现。`scripts/check-bundle.mjs` 改为可执行门禁：

- 从 `dist/index.html` 读 entry 与 `modulepreload`，把 gzip 后的 JS/CSS 计为**首屏**；
- 单独检查任意主线程分包，防止某个页面把大依赖拖回入口；
- `*worker*.js`（PDF 解析 worker）走独立线程且按需加载，不计入单分包预算。

当前实测与预算（gzip）：

| 项 | 实测 | 预算 |
|---|---|---|
| 首屏 JS（entry + vendor-vue + highlight） | 202.8 kB | 260 kB |
| 首屏 CSS | 58.2 kB | 80 kB |
| 单个主线程分包上限（最大是 lazy 的 pdf.min 116.3 kB） | — | 320 kB |

element-plus 曾在 `manualChunks` 里被固定成一个 922.89 kB 的 vendor 包，导致
聊天页首屏也要下载管理台的 Table / DatePicker / Tree。去掉该固定分组后，
Rollup 按路由动态 import 自然切分（el-table 27.1 kB、el-date-picker 26.8 kB、
el-select 10.6 kB 等只在进入后台时加载），首屏 JS gzip 从 417.0 kB 降到 202.8 kB。
代价是入口 chunk 内含少量共享组件，业务改动会让这部分缓存失效——换来首屏少下载一半。

预算只留约 25% 余量。要放宽必须在提交说明里写清楚原因，否则门槛会慢慢失效。
CI 在 `npm run build` 之后执行；`verify.ps1 -SkipBuild` 时自动跳过这一步。

### 关于发布后旧页面自愈（2026-10-30 新增）

前端是 hash 路由的 SPA，构建产物带内容哈希。发布新版本后，仍停留在旧页面的用户
手里是旧清单：下一次点击懒加载路由，请求的 chunk 已被替换成 404，页面卡死
（控制台 `Failed to fetch dynamically imported module`）。

Vite 5 在动态 import 失败时会派发可取消的 `vite:preloadError`。
`src/utils/preloadRecovery.ts` 接管该事件并重载一次——重载后拿到新的
`index.html`，绝大多数情况立即恢复。为避免「资源真的缺失 → 无限重载」，
用 sessionStorage 记 30 秒节流窗口；隐私模式下 storage 抛异常时**不节流**
（宁可多刷一次也不能卡死）。5 项单测覆盖首次重载、窗口内抑制、
窗口外放行、storage 异常降级与标记写入。

### 关于 RAG 引用一致性（2026-10-30 新增）

修复前：直连 + 知识库模式下，浏览器调用 `/api/kbRag/search` 拿引用，
网关转发时又检索一次做上下文注入。两次检索默认 topK 不同、结果可能不同，
**界面上展示的引用不一定等于模型真正读到的片段**，还多了一次检索开销。

现在网关在转发上游 SSE 之前，先写一帧来源事件：

```
event: kb_sources
data: {"items":[{"docIid":1,"docName":"手册.md",...}]}
```

前端 `directModel` 解析该事件，经 `onKbSources` 写回消息；`useChatDirect`
删掉了自己的检索请求。`X-KB-Hits` 保留，值等于实际注入的片段数。

顺带修正 SSE 解析：`event` 字段此前从不复位，自定义事件之后的上游增量块
会被误判；现在每个 data 事件处理完立即复位，并有单测锁定。

### 关于模型配置缓存失效（2026-10-30 新增）

`RerankResolver`（精排服务）、`ModelPriceResolver`（单价表）、`EmbeddingClient`
（向量模型配置）与 `ModelGatewayResolver`（直连模型路由）都对 `modelsconfigbean`
做 5 分钟 TTL 的进程内缓存。
此前后台保存配置后，停用 rerank、更换密钥或修改单价最长要等 5 分钟才生效——
管理员看到「保存成功」，线上请求却还在用旧配置。

现在 `ModelsConfigBeanHolder` 在 install / update / delete 成功后发布
`ModelConfigChangedEvent`，四个组件通过 `@EventListener` 立即丢弃缓存。
用事件而不是互相注入，是为了避免 Holder ↔ Resolver 的循环依赖；监听方只做缓存失效，
广播异常只记日志，不会把已经成功的写操作报成失败。

`EmbeddingClient` 的缓存另有两点约定：未配置向量模型时的 `null` 结果同样缓存——
否则没配模型的知识库每次提问都会落一次空查询；但**读库失败不缓存**，
下一次调用可以立即重试，不会把故障状态粘住 5 分钟。

`ModelGatewayResolver` 缓存的是「全表快照」（iid → 直连配置）：直连对话每次请求
都要按 iid 取一次配置，逐条查库在最热路径上纯属浪费，而配置表规模很小；未配置的
iid 直接命中快照里的空结果。读库失败时回退上一次快照——一次抖动不应该让所有对话
不可用。

测试分两层：

- `ModelsConfigBeanHolderTest`：成功写才广播；非超管、落库失败不广播；广播异常不影响返回值。
- `ModelConfigCacheInvalidationTest`：用真实 `AnnotationConfigApplicationContext`
  验证 `@EventListener` 接线，停用 rerank、改价、更换向量模型、删除/轮换直连模型
  都在事件后立即生效；并验证 `EmbeddingClient` 与 `ModelGatewayResolver`
  连续取值只查一次库、空配置同样命中缓存。

### 关于首 Token 延迟口径（2026-10-30 新增）

治理看板的「平均首 Token 耗时」原来按「首个 SSE 字节到达」计时。上游常见先发
心跳注释、`role` 帧或末尾的 `usage` 帧，这类帧不包含任何回答内容，却会把准备时间
算成模型延迟。现在 `streamSse` 逐行嗅探，只有 `choices[0].delta.content`
（含 DeepSeek 的 `reasoning_content`）或 Dify `event=message/agent_message`
的非空 `answer` 才记为第一个 token；全程没有正文（例如上游报错）则保持 `null`，
不再用一个「首字节」冒充。

### 关于知识库检索降级诊断（2026-10-30 新增）

1. `search` 原来的顺序是「向量化问题 → 查分块 → 空库返回」，空知识库也要先付一次
   embedding 调用；现在先查分块，空库直接返回「知识库为空」，也不会再因向量服务故障
   把空库误报成「检索失败」。
2. 切换向量模型后，旧分块的向量维度与当前模型不一致。`hybridRank` 原来直接跳过这些块，
   语义路整段失效却没有任何提示。现在会统计跳过数，`KbSearchResult` 新增
   `skipped` / `warning`：维度不一致与向量解析失败分开计数，检索页用 `el-alert`
   提示「请重新上传文档」。**注意：同一维度下更换向量模型仍无法识别**——
   彻底解决需要把模型标识与版本写进分块表（涉及数据库变更，尚未做）。

新增 3 项单测：空库不调用 `embed`、维度不一致时返回提示、跳过原因分开计数。

### 关于流式中断（2026-10-30 新增）

浏览器点「停止」时只是关掉连接，网关必须自己感知并收尾。此前只有代码里的
`isClientAbort` 判定，没有测试证明「上游真的被关掉」——而这决定了上游会不会
继续生成、继续计费。

`AiGatewayServiceTest#clientAbortMidStreamClosesUpstreamAndRecordsAborted`
用本地 `HttpServer` 模拟慢速 SSE 上游，响应侧模拟第一次写入就
`Connection reset by peer`，断言三件事：

1. `proxy` 正常返回，不把断连异常抛给容器；
2. 审计记为 `aborted`，且 `httpStatus` 记录上游真实状态（200）——修复前这里
   统一写 502，导出 CSV 时会把「用户主动停止」误读成「网关故障」；
3. 5 秒内上游写入失败（latch 触发）、生成块数未跑满，证明连接已被关闭。

并发配额预留（高并发下「先查后加」的瞬时超额）仍未做，属于独立治理项。

### 日志编码：脚本会强制 UTF-8

中文 Windows 默认代码页是 GBK（936）。PowerShell 用系统代码页解码子进程输出、
再按同一代码页写出，而 node / vitest 输出的本来就是 UTF-8，两者混排后重定向到文件
就成了「`Bundle: 浣…`」这种不可读乱码。`verify.ps1` 现在在开头做两件事：

```powershell
[Console]::OutputEncoding = [System.Text.Encoding]::UTF8   # PowerShell 自己的中文与子进程解码
$env:MAVEN_OPTS += ' -Dfile.encoding=UTF-8'                # JDK 8 的 Maven 进程按平台默认编码写 stdout
```

因此重定向的日志整体是 UTF-8，可以直接 `grep -a '通过：'`。
只读日志、不改脚本的老办法是 `iconv -f GBK -t UTF-8//IGNORE`，现在不必了。

> 运行期日志同理：`logback-spring.xml` 里 `FILE` 一直是 UTF-8，
> 但 `ERROR_FILE` 漏了 `<charset>`，同目录下两份日志编码不一致（2026-11-01 补齐）。
> `STDOUT` 故意不设 charset——跟平台默认走，Windows 控制台（GBK）里看中文才不乱。

### ⚠️ `verify.ps1` 必须存成「UTF-8 with BOM」

Windows PowerShell 5.1 读**没有 BOM** 的 UTF-8 `.ps1` 时按系统代码页（GBK）解码，
中文注释的字节会破坏引号配对，脚本连解析都过不去，报的是「表达式缺少右」这种
完全看不出根因的错误（写临时验证脚本时踩过一次）。
编辑这个文件别去掉 BOM，也不要用 `working-tree-encoding` 之类的属性去动它。
改完先做纯解析检查，不用真跑：

```powershell
$t=$null; $e=$null
[System.Management.Automation.Language.Parser]::ParseFile((Resolve-Path .\scripts\verify.ps1), [ref]$t, [ref]$e) | Out-Null
$e.Count   # 0 才是语法通过
```
