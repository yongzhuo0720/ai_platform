# NexusAI 项目说明（通俗版）

> 面向第一次接触这个项目的人：不用先懂 RAG、网关、熔断这些词，也能明白它是做什么的、怎么运转、这次升级解决了什么。
> 需要命令和目录细节时，再看 `README.md` 与 `docs/部署手册.md`。

---

## 一、一句话认识它

**NexusAI 是一个企业内部的 AI 能力聚合平台：员工在一个界面里用聊天、知识库问答和智能体；管理员在同一套后台里管模型、管成本、管权限、看质量。**

它不训练模型，也不自己造大模型。它做的是把外部模型（Dify 应用、OpenAI 兼容接口、本地向量检索）收拢到一个入口，然后在中间加一层"门卫 + 记账 + 质检"。

可以把它想成公司里的**AI 总机和财务室**：

- 总机：不管员工要打给哪家模型，都先拨这个号码；
- 门卫：查工牌（登录）、查权限、查今天还有没有额度；
- 财务：每通电话记时长、记成本、月底出报表；
- 质检：知识库答得准不准，用一套固定题库反复测。

## 二、它解决什么问题

如果每个团队各自直连模型，会出现四个典型问题：

| 问题 | 现实表现 | 平台的做法 |
|---|---|---|
| 钥匙乱放 | 每个项目各存一份 API Key，离职了还在用 | 密钥只由服务端持有，客户端拿不到 |
| 账单糊涂 | 只知道总花费，不知道谁、哪个部门、哪个模型花的 | 每次调用记 tokens、耗时、请求 ID、成本 |
| 故障放大 | 上游模型一挂，所有页面一起转圈 | 熔断、限流、并发闸门、超时护栏 |
| 效果靠感觉 | "我觉得这个知识库还行" | 固定数据集 + 明确的指标公式 + 基线对比 |

所以它不是"又一个聊天页面"，而是把 AI 调用变成**可管、可算、可测**的基础设施。

## 三、三类使用者

1. **普通员工**：聊天、选模型、传图片、建自己的知识库、用智能体查资料。
2. **知识库维护者**：上传文档，看解析/分块/向量化进度，失败能重试；用评估工作台判断检索质量有没有变差。
3. **管理员**：配置模型与 Dify 应用、看健康面板和连接测试、查调用日志与成本、收到后台任务完成通知、看周报。

权限不是前端"藏按钮"，而是后端逐接口校验：平台级目录（模型、数据集、能力、应用、Dify 配置）的写操作限超管；用户自己的资源逐条校验所有者；知识库支持公开、仅自己、按部门/角色黑名单三种可见性。

## 四、一条 AI 请求的旅程

以"员工在聊天页问一句话"为例：

```
浏览器
  │  ① 带登录票据、请求 ID、幂等键
  ▼
AI 网关（后端）
  │  ② 认人：登录是否有效、有没有权限
  │  ③ 查额度：每分钟次数、当天 tokens、部门配额
  │  ④ 查状态：这个上游是不是刚连续失败，要不要熔断
  │  ⑤ 选上游：Dify 应用 / 直连模型（地址与密钥都在服务端）
  ▼
上游模型
  │  ⑥ 边生成边回传（SSE 流式），前端逐字显示
  ▼
AI 网关
  │  ⑦ 收尾记账：tokens、耗时、成本、成功或失败
  │  ⑧ 记账失败不丢：进补偿队列稍后重试
  ▼
浏览器
     ⑨ 出错时给"能看懂的原因 + 请求 ID"，而不是一句"网络错误"
```

关键点：

- **入口统一**：Dify、OpenAI 兼容模型、对外 `/v1` 调用共用同一套治理，不会出现"这个入口有额度、那个入口没额度"的漏洞。
- **失败策略明确**：限流/配额/登录这类涉及安全的检查，后端不可用时**拒绝放行**（宁可 503，不能绕过）；只有价格查询这类不影响安全的缓存才允许沿用旧值。
- **可追踪**：每个请求有 ID，前端错误横幅会显示编号，排查时能对上后端日志与调用记录。

## 五、六个核心模块（是什么、怎么转、难在哪）

### 1. 聊天与 Dify 应用

- **是什么**：一个聊天界面，既能直连模型，也能调 Dify 应用。
- **怎么转**：直连模式由网关拼 OpenAI 兼容请求；Dify 模式由网关转发应用参数。应用参数（输入框、下拉框、必填项）由服务端配置驱动，前端动态渲染。
- **难在哪**：两套协议的流式格式不同、报错文案不同；还要保证客户端中途关页面时上游连接被及时关闭。

### 2. 知识库与本地 RAG

有两条链路，别混：

- **Dify 知识库**：文档在 Dify 侧管理，本平台做入口与权限映射；
- **本地 RAG**：文档在平台自己的数据库里。

本地 RAG 的流水线：

```
上传 → 解析 → 校验 → 去重 → 排队 → 分块 → 向量化 → 就绪
                                  │
                            失败可重试，状态与进度可见
```

- 文本类文件（txt/md/csv/json/log）由后端解码（兼容 UTF-8/GBK/BOM）；PDF/DOCX 由浏览器先提正文，避免后端背重型解析库。
- 正文做 SHA-256 去重；分块与向量存 PostgreSQL；检索时把"向量相似度"和"全文关键词"两路结果融合（RRF），可选再走一遍精排（Rerank）。
- **难在哪**：上传不是"传完就算"，而是有明确状态机的异步任务；删除文档要级联清理分块与向量，不能留孤儿数据；检索必须限定当前用户，不能串库。

### 3. RAG 评估工作台

- **是什么**：给知识库出一套"考试"：固定问题 + 标准答案片段，反复跑，比较版本。
- **指标不是随口说的**：
  - **Recall@K**：标准答案片段有没有出现在前 K 条检索结果里；
  - **MRR**：第一个命中的位置越靠前分越高；
  - **命中率**：有多少道题至少命中一次。
  每次运行都会保存当时的配置快照（Top-K、是否精排、用例集），否则两次结果没有可比性。
- **这次补的能力**：结果详情能看到第几位命中；可以显式选一个历史运行作为基线，逐题看"哪些题变好、哪些题退化"；可以只改精排策略再跑一次做 A/B。
- **难在哪**：如果指标口径、用例集、参数有一个没落库，"提升 10%"就无法复现。所以运行快照比界面更重要。

### 4. Agent 工作台

- **是什么**：配置一个会"多步做事"的助手：先想，再调工具，看结果，再决定下一步。
- **怎么转**：后端执行循环负责调用模型、解析工具请求、执行工具、把每一步作为事件流推给前端；前端实时显示步骤与工具结果。
- **难在哪**：要防止重复收费（断流不自动重试）、要能定位失败发生在哪一步、要复用网关的限流与配额，而不是另开一条无治理的通道。

### 5. 模型可观测与治理

- **健康面板**：今天的调用量、成功率、tokens、成本；哪些模型配置不完整；一键连接测试。
- **成本口径**：统一按"分"存储、按页面需要换算展示；单价有缓存，但缓存不能把"加载失败"记成"免费"。
- **稳定性**：按模块限流、并发闸门快速 429、流式总时长护栏、上游熔断与半开恢复、幂等键防重复提交、请求 ID 贯穿前后端。
- **难在哪**：这些能力单独看都简单，放在一起会出现顺序问题——比如先扣配额还是先熔断、流式超时后怎么结算、记账失败怎么补偿。顺序错了，账就不平。

### 6. 平台治理与体验

- **站内通知**：文档处理完成/失败、评估完成等事件推送；铃铛轮询未读数，点开直达对应页面。
- **定时任务互斥**：多实例部署时，同一个定时任务同一时间只允许一个实例执行。
- **周报**：统计一周调用量、tokens、成本；要么完整落库，要么明确失败，不保存"只统计了一半"的快照。
- **全局搜索**：Ctrl/Cmd + K 一次搜 Agent、知识库、评估数据集、模型、数据集；单个数据源坏了只标记降级，不影响其他分类；结果直达对应页面并自动带筛选条件。
- **前端错误兜底**：Vue 渲染异常和未处理的 Promise 异常统一进顶部横幅；按需加载的 chunk 失效单独走重载；接口错误仍走原来的提示，不重复弹。

## 六、这次第二轮升级做了什么

按"先修地基，再加能力"的顺序推进，每一项都先核实真实缺口，再改代码、补测试、写学习文档。

| 方向 | 原来的问题 | 这次的做法 | 结果 |
|---|---|---|---|
| 仓库与基线 | 公开仓库有脱敏残留；测试数字过期 | 清理历史、补门禁、重跑全量 | 公开仓库不含内部依赖与敏感配置 |
| 网关可靠性 | 计费口径不一致；失败结算会丢；没有并发闸门/熔断 | 统一 usedTokens 口径、补偿队列、按模块限流、流式护栏、熔断半开 | 账单可对、故障不放大 |
| RAG 评估 | 只有一次运行的结果，无法比较 | 命中明细落库、运行快照、显式基线、逐题对比、精排 A/B | "变好还是变差"可复现 |
| 文档流水线 | 上传同步处理，大文件卡住请求 | 异步任务 + 状态机 + 进度轮询 + 失败重试 + 级联删除 | 上传可观测、可恢复 |
| Agent | 只有数据层，没有真实执行闭环 | 执行循环、工具执行、SSE 事件、工作台与历史 | 多步任务能看到每一步 |
| 模型可观测 | 只有调用日志，没有健康视图 | 连接测试、健康面板、成本单位统一 | 管理员能定位"是配置错还是上游挂" |
| 通知与定时任务 | 后台任务完成没人知道；多实例会重复跑 | 事件通知、未读轮询、任务互斥 | 任务状态可见、不会重复执行 |
| 周报 | 5 万行处静默截断；中途失败也落库 | 读到不满一页才结束；超限或读失败显式失败且不落库 | 不再保存"看起来正常"的残缺统计 |
| 单价缓存 | 首次加载失败会把空表缓存 5 分钟 | 失败不更新缓存时间，下次立即重试；有旧缓存则沿用 | 故障窗口内不会把成本全记成 0 |
| 全局搜索 | 找资源要靠逐个页面翻 | 一次聚合五类资源、服务端拼深链、单源降级 | Ctrl+K 直达目标页 |
| 前端错误 | 渲染异常白屏、只在控制台报错 | 全局兜底横幅 + 错误编号 + chunk 重载 | 出错有提示、可恢复 |

学习文档在 `docs/学习文档-阶段1-子阶段*.md`，每个子阶段一篇，写清楚"发现什么、为什么这样改、怎么验证、还差什么"。

## 七、质量怎么保证

不是"跑通一次就算"，而是四层验证：

1. **单元测试**：后端覆盖计费、限流、熔断、配额、状态机、权限、周报聚合、价格缓存等关键分支；前端覆盖错误解析、命令面板、流式收尾等逻辑。
2. **组件测试**：真实渲染 Vue 组件，验证加载、空态、错误态、重试与交互。
3. **浏览器冒烟**：真实 Chromium + 接口 mock，走登录守卫、SSE、图片压缩、配额提示、RAG 评估详情、Agent 事件链路、404 兜底等完整路径。
4. **真实接口回归**：把新包重新部署到本地后端，用真实数据库登录后调用新增接口（全局搜索、通知、健康面板、周报生成），确认不是"只在 mock 里成立"。

最近一次实测（2026-11-06）：

| 项目 | 结果 |
|---|---|
| 后端单元测试 | 629 项 / 57 份报告，0 失败 / 0 错误 / 0 跳过 |
| 前端 TypeScript、图标、色值门禁 | 全部通过 |
| 前端逻辑 / 组件测试 | 286 项 / 300 项通过 |
| 浏览器冒烟 | 21 项通过 |
| 流式与 Markdown/XSS 回归 | 14 项 / 10 项通过 |
| 生产构建、首屏体积、产物密钥扫描 | 全部通过 |
| 真实接口回归 | 登录、全局搜索（命中模型/数据集）、通知未读、健康面板、周报生成均正常 |

门禁的意义是"防回退"：新增硬编码色值会失败、模板用了未注册图标会失败、构建产物扫出密钥会失败、首屏超过体积预算会失败。

## 八、怎么把它跑起来

最短路径见 `README.md` 的"运行测试"，部署细节见 `docs/部署手册.md`。概括：

- 后端：JDK 8 + Maven（必须用项目自带的离线 settings），默认端口 8507，上下文 `/ai`；
- 前端：Node + Vite，开发端口 4317；
- 存储：PostgreSQL + Redis；
- 模型：管理员在后台配置 Dify 或 OpenAI 兼容模型，密钥只在服务端使用。

本地一键验证：`scripts/verify.ps1 -JavaHome '<JDK 8 路径>'`，会依次跑门禁、单测、构建，并检查"测试是否真的执行了"——一份后端报告都没生成就直接判失败，专门防"测试被跳过但构建显示绿色"。

## 九、现在还没做什么（如实说明）

一个项目说明如果只说优点，反而不值得信。当前明确的边界：

1. **评估数据集偏小**：指标公式是真的，但结论的统计置信度取决于题库规模；目前适合做版本对比，不适合对外宣称"准确率 95%"。
2. **SSE 读循环是同步阻塞的**：上游静默时，最坏要等读超时（默认 300 秒）才进入收尾；已在审查报告里列为待修项。
3. **配置缓存是最终一致**：多实例下，管理员改配置最多 5 分钟生效；仓库目前没有多实例部署清单，所以暂未引入配置广播。
4. **没有接生产级监控**：目前是健康面板 + 调用日志 + 周报，未接 Prometheus/告警平台。
5. **Dify 与真实模型需要管理员填密钥**：没有密钥时页面会明确提示"未配置"，不会用假数据冒充成功。

## 十、如果拿它去面试，怎么讲

一句话版本：

> 我做了一个企业 AI 聚合平台：把 Dify 和多家模型收口到一个网关，做统一鉴权、限流、配额、熔断、计费和请求追踪；上面有知识库、文档异步流水线、RAG 评估工作台和 Agent 工作台；用 629 个后端测试和 21 项浏览器冒烟保证不回退。

更值钱的讲法不是列功能，而是讲**取舍**：

- 为什么配额检查要 fail-closed，而价格缓存可以 fail-open；
- 为什么评估结果必须存运行快照，否则"提升"无法复现；
- 为什么周报超过上限要整份失败，而不是保存前 5 万行；
- 为什么前端错误兜底要和 axios 的 toast 分工，避免同一次错误弹两遍。

这些取舍就是"会写页面"和"能做系统"的区别。
