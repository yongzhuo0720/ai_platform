# NexusAI 项目架构说明（2026-11-19 审查）

> 本文档基于**当前源码逐文件核对**生成，不是照抄 README。
> 标注约定：【源码确认】= 实际读取代码确认；【推断】= 依赖私有框架内部、无法从仓库源码完全核实。
> 私有框架 HNSP（`com.heneng.hnsp:*:1.2.3-SNAPSHOT`）与 qjava 无源码在仓库内，其内部机制均标注【推断】。

## 一、总体架构

```
浏览器 (Vue 3 + Pinia + vue-router, hash 模式)
   │
   │ axios.js / request.ts
   │  - 站内业务: x-access-token + account
   │  - AI 请求: X-Request-Id + Idempotency-Key + x-access-token
   ▼
Nginx (宿主 8083, /ai/ 反代后端, SSE 关缓冲)
   │
   ▼
Spring Boot 2.6.8 / Java 8 (context-path=/ai, 端口 8507)
   │  WebConfig 注册两个拦截器:
   │   ├─ LoginAuthInterceptor  → /uaccess/**, /api/**  (默认拒绝未登录)
   │   └─ ApiTokenAuthInterceptor → /v1/**  (Bearer sk-, 真实 401/503)
   ▼
Controller (@LoginUserId 注入 uid) → Holder (归属/权限校验) → @HnMapper → PostgreSQL
   │
   └─ AI 类请求 → AiGatewayService → 上游 Dify / OpenAI 兼容模型 → SSE 逐字回传
```

## 二、前端架构（frontend/）

### 2.1 技术栈【源码确认，来源 package.json】
| 类别 | 依赖 |
|---|---|
| 框架 | Vue 3.5、vue-router 4.3、Pinia 2.1 |
| 构建 | Vite 5.1、TypeScript 5.3、vue-tsc 1.8 |
| UI | Element Plus 2.13、@headlessui/vue |
| HTTP | axios 1.15（站内）+ 原生 fetch（Dify/模型流） |
| 文档解析 | mammoth(docx)、pdfjs-dist、marked、dompurify、highlight.js |
| 测试 | Vitest 2.1、Playwright 1.64、@vue/test-utils 2.5 |

### 2.2 目录职责
- `src/api/` — 请求封装。两个核心文件：`axios.js`（Sa-Token 拦截，注入 token/account）、`request.ts`（Dify/fetch 流处理，兼容站内与 OpenAI 两种错误信封）。其余按域拆分（chat/agent/kbRag/ragEval/aiGatewayAdmin 等）。
- `src/stores/` — Pinia 仅 3 个 store：`difyConfig`（网关模式/配置/请求头）、`notification`、`theme`。
- `src/views/` — 16 个一级页面目录（ChatView / AgentView / RagEvalView / Admin 等）；`src/router/index.ts` 单一路由，hash 模式。
- `src/components/` — 全局组件（GlobalSearch、KbChatPanel、NotificationBell、StateBlock 等）。
- `src/composables/useIsAdmin.ts` — 超管判定（cookie `rid === 99999`）。

### 2.3 双 HTTP 通道与网关开关【源码确认】
- **站内业务**走 axios，`resp_code === 0/200` 判成功，`20102` 或含"先登录"跳登录页。
- **AI 请求**走 fetch，`gatewayRequestHeaders()` 生成 `X-Request-Id`、`Idempotency-Key`、`x-access-token`。
- **网关模式开关** `VITE_AI_GATEWAY`（`stores/difyConfig.ts:38`，默认开启）：开启时浏览器只请求同源 `/ai/api/aiGateway/**`，密钥不出服务端；关闭时直连 Dify 仅作排障，且后端不下发 apiKey，实际不可用。
- 提交门禁 `check:secrets` 扫构建产物，防 `VITE_*_KEY` 被 Vite 内联泄露。

### 2.4 路由与权限守卫【源码确认】
- `beforeEach`（router/index.ts:166-188）：`/admin/**` 需 `admin_loginToken` 且 `admin_access === '1'`；其余路径需 `loginToken`。
- 前端门控是体验层；真正的数据权限在后端 Holder（见第六节）。

### 3.3 私有框架依赖【源码确认 + 推断】

- `com.heneng.hnsp:hnsp-public-common-croe:1.2.3-SNAPSHOT` 提供 `Result`、`DbEntityBase`、`@HnMapper`、`@LoginUserId`、`RedisServer`、Sa-Token 登录态【推断：内部实现不在仓库】。
- `blxt.qjava:1.0.1-SNAPSHOT` 提供 `@SqlBean`/`@SqlColumn`，框架据此自动生成建表 SQL【推断】。

### 3.4 启动期数据保障
- `TableSchemaInitializer`（监听 `ApplicationReadyEvent`）：幂等补列/建表/建索引（15 处显式 CREATE TABLE + 大量 ADD COLUMN IF NOT EXISTS），另有 `scripts/sql/` 7 个 SQL 脚本。

## 四、数据访问与 Redis

### 4.1 数据库【源码确认】
- PostgreSQL（docker-compose 用 `postgres:12.5`），`application.yml` 配 JDBC URL。
- Mapper 全部是 HNSP `@HnMapper` 空接口；**仓库内无任何 `*Mapper.xml`**。
- 表来源两部分：框架 `@HnMapper(createTable=true)` 自动建表【推断，jar 内】+ `TableSchemaInitializer` 显式建表。**框架自动建表不在仓库源码中，表总数无法精确得出，可确认显式建表 ≥15 张**。
- 关键表：`userbase`/`role`/`unit`（权限）、`aicalllogbean`（审计，含 `costCents` 毫分）、`aiuserquotabean`（配额+成本预算）、`modelsconfigbean`（模型配置/价格）、`difyconfigbean`、`kbdocbean`/`kbchunkbean`（RAG）、`rageval*`（4 张评估表）、`agent*`（4 张）、`aiapitokenbean`（只存 tokenHash）、`notificationbean`、`chat*`。

### 4.2 Redis 使用【源码确认，逐 key】
| 用途 | key 形态 | TTL / 机制 |
|---|---|---|
| 限流 | `ai:gateway:rate:{uid}:{yyyyMMddHHmm}` | 每分钟计数 |
| Token 配额 | `todayTokenKey(uid)` + `unit:` 部门池 | 双池预扣/结算 |
| 预扣台账 | `ai:gateway:reservation:{UUID}` | 2h |
| 结算补偿 | `ai:gateway:compensation:{UUID}` | 2 天，Lua 原子调整 |
| 幂等 | `ai:gateway:idem:{uid}:{module}:{key}` | SETNX 10min |
| 并发 | `ai:gateway:concurrent:{module}` | ZSET + Lua，Redis 挂退本地 Semaphore |
| 定时任务锁 | `ScheduledTaskGuard` | Lua 加/解锁 + TTL |
| 登录态 | Sa-Token | — |
| **熔断** | **不用 Redis**，`GatewayCircuitBreaker` 进程内 `ConcurrentHashMap` | 多实例各自独立（设计取舍） |

### 4.3 熔断的多实例容量规划（P2-5 决策记录）

熔断状态刻意放在**进程内**，不做 Redis 共享——代码注释（`GatewayCircuitBreaker:32-34`）已明确这是有意的取舍：熔断保护的是**本实例的线程与延迟**，而非全局精确计数。共享状态会引入 Redis 依赖和跨实例竞态，收益有限。

**多副本部署时的容量规划建议**：

| 副本数 | 单实例熔断阈值建议 | 说明 |
|---|---|---|
| 1（默认） | 默认（连续失败 5 次） | 无需调整 |
| 2~3 | 保持默认或微调至 4 | 各实例独立计数，整体触发失败量约为「副本数 × 阈值」，仍可接受 |
| 4+ | 调低至 3，并依赖网关层整体限流兜底 | 单实例阈值过高会让整体故障响应变慢；此时应更多依赖 `GatewayConcurrencyGuard`（Redis 全局并发闸门）与限流 |

> 注意：限流、配额、幂等、并发闸门都是 **Redis 全局状态**，只有熔断是进程内。
> 因此多实例下的"全局保护"主要由这四个组件承担，熔断是每实例的最后一道本地防线。
> 若将来确实需要全局精确熔断（如强一致的故障隔离），再单独评估改 Redis 共享状态，不纳入本次升级。

## 五、AI 网关调用链路（核心）

### 5.1 完整链路【源码确认，主干逐行】
```
前端请求 (X-Request-Id + Idempotency-Key)
 → AiGatewayController /api/aiGateway/{module}/**  [module=chat/knowledgeChat/file/models]
 → LoginAuthInterceptor 鉴权
 → AiGatewayAsyncDispatcher.dispatch (WebAsyncTask 异步, 不占 Web 线程)
 → AiGatewayService.doProxyEntry:
     ├ 配置/uid/module 校验 → DifyEndpointPolicy 路径白名单
     ├ AiGatewayConfigResolver 取地址密钥 (DB 配置 > 环境变量)
     ├ AiGatewayGuard.check 限流+配额 → reserve 预扣 token
     └ doProxy:
         ├ AiIdempotencyGuard.acquire 幂等
         ├ GatewayConcurrencyGuard.tryAcquire 并发 (429)
         ├ GatewayCircuitBreaker.tryAcquire 熔断 (503)
         ├ 构造上游请求 + X-Request-Id 透传 + 取消即 abort
         ├ SSE 边读边写 (心跳 : ping) / JSON 中继
         ├ AiGatewayUsageParser 嗅探 usage / 终止信号
         └ finally: settle 预扣多退少补 + record 审计落 aicalllogbean
```

### 5.2 关键组件职责
| 组件 | 职责 |
|---|---|
| `AiGatewayGuard` | 限流、每日 token 配额、预扣/结算、补偿队列；fail-closed |
| `AiIdempotencyGuard` | 写请求 10min 幂等占位 |
| `GatewayConcurrencyGuard` | 每模块并发许可，Redis ZSET + Lua |
| `GatewayCircuitBreaker` | CLOSED→OPEN→HALF_OPEN 状态机（进程内） |
| `AiGatewayUsageParser` | 从 SSE/JSON 提取 tokens/model/会话 ID，兼容 Dify 与 OpenAI 字段 |
| `ModelGatewayResolver` | 按 iid/平台名/上游名解析模型，5min 缓存 + 变更事件失效 |
| `ModelPriceResolver` | token×单价→成本（毫分），整数运算，5min 缓存 |
| `GatewayMetrics` | Prometheus 业务指标（调用量/成本/延迟/失败数） |
| `CostBudgetAlertScheduler` | 每日 02:00 扫昨日成本，超预算发通知（本次新增） |

### 5.3 两套 AI 接口的区别
- `/api/aiGateway/**` — 站内浏览器登录态，转发 Dify（module=chat/knowledgeChat/file），错误体 HTTP 200 + `{code,message,requestId}`。
- `/v1/chat/completions`、`/v1/models` — 外部 SDK 用平台 `sk-` API Key，走 `ModelGatewayResolver` 到 OpenAI 兼容上游（不是 Dify），错误体 OpenAI 形状 + 真实 401/503。
- 两者共用治理与审计链路，靠 `ThreadLocal<Boolean> openAiErrorShape` 切换错误形状。

## 六、Dify 集成

- 配置存 `difyconfigbean`（`apiKey` 查询时脱敏为空串）；`DifyConfigDataRegister` 启动时插入 3 个模块默认行。
- 解析优先级：**DB 配置 > application 配置/环境变量**（`DIFY_CHAT_URL/KEY` 等）。
- `DifyEndpointPolicy` 按"模块+方法+路径形状"白名单放行，拒绝 `%`/`\`/`..`/查询符等，只放行前端实际调用的接口。
- 网关模式下密钥只存服务端；直连模式（`VITE_AI_GATEWAY=0`）仅排障保留。

## 七、本地 RAG 流程

### 7.1 文档处理链路【源码确认】
```
uploadFile (KbRagController)
 → KbDocPipelineHolder.uploadFile (解析/去重/queued/正文入库)
 → kbDocExecutor 线程池 (core1/max2/queue20/AbortPolicy)
 → KbDocRunner:
     QUEUED→CHUNKING→分块→EmbeddingClient 分批向量化(批32,重试2)
     → 全部向量算完一次性写 kbchunkbean → READY + 站内通知
 → 僵死回收 @Scheduled 每5min (Redis 锁 + CAS 状态)
```

### 7.2 检索链路【源码确认】
```
search → 向量路(内存余弦, 上限 MAX_SCAN_CHUNKS)
       + 关键词路(PG to_tsvector('simple') @@ plainto_tsquery, GIN 索引)
       → RRF 融合(RRF_K=60) → 可选 Rerank(异常降级)
```
- 知识增强：`AiGatewayService.applyKnowledgeContext()` 用最后一条 user message 检索，注入 system 消息（最多 8 片/6000 字），并发 `kb-sources` SSE 事件回前端。
- RAG 评估：`RagEvaluator` 只做检索侧确定性指标（Recall/Precision/MRR/NDCG@k），生成侧指标有意不做（注释说明适合人工月度抽检）。

## 八、权限体系

- 模型：`MyUserBaseDb`（表 `userbase`，字段 `uid/uaccess/upwd/rid/gid`）+ `MyRoleBean` + `UnitBean` + 标签体系。超管 = `rid == 99999`。
- 机制：`@LoginUserId` 注入 uid（框架 TokenArgumentResolver【推断】）→ **Holder 内**做归属/权限校验（Controller 不承担权限判断）。
- 知识库可见性三态（`KnowledgeBaseBeanHolder.isVisibleToUser`）：`public` / `only_me`（ownerUid==uid）/ `partial_invisible`（角色+部门黑名单，解析失败 fail-closed，未知类型拒绝）。
- 审计与配额接口仅超管（`AiGatewayAdminHolder.isAdmin`）。

## 十、不确定项（诚实标注）

1. **数据库表总数**：框架自动建表逻辑在私有 jar，仓库无源码 → 只能给"显式建表 ≥15 张"下限。
2. **`@LoginUserId` 解析实现**：`TokenArgumentResolver`/`RoleCheckService` 在私有框架内，依据项目注释确认语义，未读 jar 字节码。
3. **qjava/HNSP 内部机制**：`@SqlBean` 如何生成 DDL、`RedisServer` 角色缓存细节，仓库无源码。
4. **MyBatis 与 HNSP 协作**：配置有 mybatis-plus 段，项目自有 Mapper 全是 `@HnMapper` 空接口无 XML，框架内部协作方式未核实。

> 这些不确定项不影响本次审查结论（问题均定位在仓库自有代码），但在涉及框架行为时需留意。
