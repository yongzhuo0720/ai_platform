## 二、Bug 清单（按严重度）

### 🔴 P0 · 本地 RAG 跨用户数据泄露（新发现，前两轮审计未覆盖）

> 根因：本地 RAG 是 2026-10-22 才提交的功能（commit `8d63e57`），10-15 与 10-17 两轮系统性审计都在此之前，因此完全没审到它。

`KbRagController` 只校验「已登录」，三个接口全部**不校验资源归属**：

| 接口 | 问题 | 后果 |
|---|---|---|
| `POST /api/kbRag/listDocs` | `KbRagHolder.listDocs(uid)` 把 uid 只用于判登录，**从不作为查询条件**（`kbDocBeanMapper.select(null, new KbDocBean())`） | 任意登录用户可看到**所有用户**的文档名、分块数、状态 |
| `POST /api/kbRag/deleteDoc` | `deleteDoc` 只按 `iid` 删，无 ownerUid 校验 | 任意登录用户可**删除他人文档**（连分块一起删） |
| `POST /api/kbRag/search` | `search` 只按 `kbName` 过滤 chunks，与 uid 无关 | 任意登录用户可**检索并读取他人文档正文分块** |

**修复方向**：`KbDocBean` / `KbChunkBean` 查询统一带 `ownerUid = uid`；`deleteDoc` 先查出文档校验 ownerUid 再删；`search` 的 chunks 查询加 ownerUid 过滤。**这是当前最该先修的一条。**

### ⚠️ 有意不做的两项（都有明确理由，不是遗漏）

| 项 | 理由 |
|---|---|
| **密码哈希换 bcrypt** | 哈希与校验都在私有框架里（`UpwdTools.makePwdMD5` + 框架的登录 Controller），改格式必须同步改校验路径。本地没有可用的登录链路端到端验证，**贸然改会把所有存量账号锁死**。正确做法是先确认框架是否开放密码校验钩子，再设计双写过渡（新密码 bcrypt、校验兼容旧 MD5、登录成功静默升级）。 |
| **`isAdmin` 加缓存** | 这是性能优化而非缺陷。缓存管理员状态有权限 staleness 风险——刚被降级的管理员在缓存期内仍放行，那是安全洞。收益（每请求少一两次查询）远小于风险，项目的调用量级也谈不上瓶颈。 |
| **`FileTreeUtil` 改相对路径** | `TreeNode.vue:102` 用 `node.path` 作为 `filePath` 调下载接口，服务端再靠它做 canonical 前缀校验。改成相对路径会**同时搞坏下载功能和安全校验**，且用户本就已授权浏览该目录。记为已评估风险。 |

### 阶段 2 · RAG 质量跃升（2-3 周）— ✅ 核心部分已完成 2026-10-24

> 当前本地 RAG 是"能用"而非"好用"：JSON 字段存向量、内存全表余弦、无重排、无混合检索、无评估。

**已完成：混合检索 + RRF 融合**

- **两路互补**：向量路（余弦，全量自有分块）+ 关键词路（PostgreSQL 全文检索召回）
  - 纯向量路的盲区：专有名词/版本号/SKU 的 embedding 区分度差；问法与文档用词不一致时漏检
  - 纯关键词路的盲区：不懂同义词
- **RRF 融合**（k=60）：只看排名不看原始分，因此不需要把余弦分和词频归一到同一量纲——这是它比加权求和更适合这里的原因
- **关键词路用 PG 全文检索做候选召回**（GIN 表达式索引，精排在内存），与当前"万块以内"规模匹配
- **中文分词**：不引外部分词器，用**二元滑窗**（「报销流程」→ 报销/销流/流程）。中文词以二字居多，且避免单字噪声
- **SQL 注入防护**：`plainto_tsquery`（不解析布尔语法）+ 单引号转义
- **降级策略**：关键词路任何异常都静默降级为纯向量路——检索是增强而非依赖
- **可解释性**：`KbSearchItem` 新增 `denseScore`/`lexicalScore`/`channel`(both/dense/lexical)，排查"为什么这条没检索到"时一眼看出是哪一路的问题
- **新增 GIN 索引**：`idx_kbchunk_content_fts`，用 `simple` 配置（不依赖语言词典，中英混合更稳）
- **上下文注入改进**（`AiGatewayService.applyKnowledgeContext`）：按 RRF 分降序注入（对抗 lost-in-the-middle）+ 按字符预算截断而非固定条数

**已完成：检索评估能力**（`docs/eval/`）

- **指标库** `RagEvaluator`：Recall@k / Precision@k / MRR / NDCG@k，纯函数、确定性、可进 CI。
  刻意**不用** RAGAS 的 context precision / faithfulness——那些需要 LLM-as-judge，
  每次评估花钱且同数据跑两次结果可能不同，不能作为回归门禁。生成侧指标适合人工月度抽检。
- **受控对照实验** `KbRetrievalEvalTest`：构造 RAG 最典型的失败——**语义陷阱**
  （目标分块含精确型号 `BGE-M3`，但向量相似度低于 3 个讲同主题、只是型号不同的干扰项）。
  6 个用例实测：

  | 方案 | Recall@3 | MRR | NDCG@3 | 完全漏召 |
  |---|---|---|---|---|
  | 纯向量 | 0.00% | 0.250 | 0.000 | 6/6 |
  | 混合检索 | **100.00%** | **1.000** | **1.000** | **0/6** |

  说明：这是**合成语料上的受控实验**，证明混合检索在语义陷阱场景有结构性优势，
  不等于线上召回率 100%。真实语料数字待测（记录表已在 `docs/eval/README.md`）。
- **黄金评估集**：6 篇虚构企业制度文档（约 6500 字）+ **55 道题**，覆盖 6 类题型，

  无重复题、CSV 列数完整、题量 ≥30、覆盖全部文档。**它已经真实抓到过一次漂移**
  （q49 的关键词 `200000` 与文档里的 `200,000` 不一致）。
- 排序逻辑与 DB I/O 解耦：`hybridRank` 的关键词召回改为入参，使算法可被单测直接驱动。

## 三之二、启动项目时发现的两个真实 bug（2026-10-24 晚补充）

这两条都是**只有在真跑起来才会暴露**的问题，静态审计和单元测试都发现不了。

### 🔴 登录接口返回 HTTP 500（前端 bug，导致根本登不进去）

**现象**：`POST /ai/uaccess/logintest` 返回 `500 Internal Server Error`，
日志里只有 `java.lang.IllegalArgumentException: null`，看不出是哪个字段。

**根因**：框架的 `logintest` 签名是

```java
logintest(String app, String uaccess, String upwd, boolean keepUser, HttpServletRequest req)
```

第 4 个参数是 **primitive boolean**。前端只发了 `{uaccess, upwd}`，
参数解析器解析不到 `keepUser` 就塞 `null`，而 `Method.invoke` 无法把 `null`
赋给基本类型 → 抛 `IllegalArgumentException` → Spring 包成 500。

**修法**（`frontend/src/api/user.ts`）：请求体固定带上 `keepUser: false`。

**顺带发现的坑**：`app` 参数**必须为空**。它是应用级账号隔离标识，
传任何非空值（`ai`、`aiproject`、`admin`）都会被判成「该应用下不存在这个账号」，
返回「用户不存在或密码错误」——很容易误判成密码错了。

### 🟠 我自己引入的回归：`@JsonIgnore` 把反序列化也挡掉了

阶段 1 我给 `MyUserBaseDb.upwd` 加 `@JsonIgnore` 想防止密码泄露到响应里。
它确实挡住了输出，但**连反序列化一起挡掉了**——于是 `/myuser/create` 和
`/myuser/update` 收不到密码字段，建用户和改密码直接失效。

我当时的核对方式是「框架是否用 Jackson 序列化 Bean 来生成 SQL」，
确认了不会，**但漏掉了 HTTP 请求体的反序列化方向**。

**修法**：改用 `@JsonProperty(access = Access.WRITE_ONLY)`——可写入、不可输出。

**补了回归测试** `MyUserBaseDbJsonTest`（3 个用例，两个方向都测）：
- 入方向：`{"upwd":"P@ssw0rd!"}` 必须能反序列化进来（否则建用户/改密码失效）
- 出方向：序列化结果里不能出现 `upwd` 字段或密码值
- 集合方向：分页返回 `List` 同样不能泄露

> 教训：凡是给敏感字段加序列化防护，**入和出两个方向都必须测**，
> 只测一个方向必然重蹈覆辙。
